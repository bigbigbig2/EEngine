# 1. 先说最直接的参考：NVIDIA 对这种 global atomic contention 怎么处理

你现在这个：

```wgsl
if (valid) {
    atomicAdd(&control.valid_pixel_count, 1u);
}
```

在近景几乎就是最坏情况：

```text
Pixel 0 ─┐
Pixel 1 ─┤
Pixel 2 ─┤
Pixel 3 ─┤
...      ├──→ 一个 global u32
Pixel N ─┘
```

WGSL 对同一个 atomic object 的修改必须形成一致的修改顺序；storage-space atomics 又是 queue-family scope。因此即使 GPU 有非常高的并行度，同一个地址仍天然形成同步热点。([GPU Web](https://gpuweb.github.io/gpuweb/wgsl/?utm_source=chatgpt.com))

NVIDIA 很早就在 histogram 问题上专门研究过这个模式。他们的优化不是“换一个更快的 atomic”，而是：

```text
Naive
──────────────

pixel
pixel
pixel ──────────→ Global Counter
pixel
pixel


Optimized
──────────────

64 / 128 / 256 threads
       ↓
Shared / Local Count
       ↓
每个 block 只提交一次
       ↓
Global Counter
```

即两阶段：

```text
Per-block local accumulation
          ↓
Global reduction
```

这样减少 global contention。NVIDIA 在 Maxwell 的 histogram 测试中，shared-memory atomic 版本比直接 global atomic 版本接近 2×；具体倍数不能直接套到 GTX 1650 Ti，但算法原则完全对应你的问题。([NVIDIA Developer](https://developer.nvidia.com/blog/gpu-pro-tip-fast-histograms-using-shared-atomics-maxwell/?utm_source=chatgpt.com))

所以你现在：

```wgsl
atomicAdd(&control.valid_pixel_count, 1u);
```

最起码应该变成：

```text
每 pixel:
    valid = 0 / 1

       ↓

workgroup reduction

       ↓

localValidCount

       ↓

thread 0:
atomicAdd(globalValidCount, localValidCount)
```

假设是：

```text
8 × 8 = 64 threads
```

1080p：

```text
当前：
最多 ~2,073,600 次
global atomicAdd

workgroup reduction：
最多 ~32,400 次
global atomicAdd
```

直接少：

```text
64×
```

如果进一步两阶段 reduction：

```text
pass 1:
每个 workgroup 写一个普通 u32

pass 2:
reduce workgroup counters
```

甚至可以：

> **0 个竞争同一地址的 per-pixel global atomic。**

# 2. WebGPU 本身现在已经有很适合你的 subgroup 路径

WGSL 当前已经提供：

```wgsl
subgroupAdd()
subgroupExclusiveAdd()
subgroupInclusiveAdd()
subgroupBallot()
subgroupElect()
subgroupBroadcastFirst()
```

等 subgroup primitives。([GPU Web](https://gpuweb.github.io/gpuweb/wgsl/))

而你的 EEngine 本来就在 device negotiation 里机会性启用：

```text
subgroups
```

所以非常适合继续保持你之前 MeshletWork 的双路径哲学：

```text
Material Classification
│
├── Portable path
│
│   workgroup memory
│   + workgroupBarrier
│   + one global commit
│
└── Subgroup path
    subgroupAdd / ballot
    + subgroup leader
    + one workgroup commit
```

比如：

```wgsl
let local_valid = select(0u, 1u, valid);

let wave_valid = subgroupAdd(local_valid);

if (subgroupElect()) {
    atomicAdd(&workgroup_count, wave_valid);
}
```

然后整个 workgroup 最后：

```wgsl
if (local_invocation_index == 0u) {
    atomicAdd(
        &global.valid_pixel_count,
        atomicLoad(&workgroup_count)
    );
}
```

这就变成：

```text
64 pixels
↓
可能 2 个 subgroup reduction
↓
1 个 global atomic
```

而不是：

```text
64 pixels
↓
64 个 global atomic
```

。

# 4. Wicked Engine 有一个非常具体的开源实现可以参考

这个我觉得你尤其值得直接读源码。

Wicked Engine 的 tiled light culling shader 没有让所有 pixel 直接更新全局结构。

它先使用：

```hlsl
groupshared uint uMinDepth;
groupshared uint uMaxDepth;
groupshared uint uDepthMask;

groupshared uint tile_opaque[];
groupshared uint tile_transparent[];
```

把 tile 内数据放在 LDS/groupshared。

计算 tile depth 时，它甚至不是每线程：

```hlsl
InterlockedMin(...)
```

而是先：

```hlsl
WaveActiveMin()
WaveActiveMax()
```

然后只有：

```hlsl
if (WaveIsFirstLane())
{
    InterlockedMin(uMinDepth, ...);
    InterlockedMax(uMaxDepth, ...);
}
```

。

也就是：

```text
pixel/thread
    ↓
wave reduction
    ↓
wave leader
    ↓
groupshared atomic
```

这就是你 MaterialTile Classification 很应该采用的模式。

# 17. 论文方面：Visibility Buffer 本身没有要求你必须这样分类

经典论文 **The Visibility Buffer: A Cache-Friendly Approach to Deferred Shading** 的核心论点是：

> Visibility pass 只记录 triangle/instance identity，材质相关计算延迟到可见性确定后执行，从而降低 G-buffer 带宽和 overshading。

([计算机图形技术期刊](https://jcgt.org/published/0002/02/04/paper.pdf?utm_source=chatgpt.com))

论文：[[Bur13\]](https://www.semanticscholar.org/paper/35e422454fe9f9f94c8ed35529f7b60a87184492)

这篇论文支持：

```text
VisibilityKey
→ deferred material reconstruction
```

但不意味着：

```text
每个 pixel 必须做 global atomic validation
```

。

那个是你 ADR-0009 correctness migration 的实现选择，不是 Visibility Buffer 架构的必要代价。

这点非常重要。

# 18. 另外两篇论文提醒了另一个问题：Compute shading scheduler 本身也可能变成瓶颈

**Deferred Adaptive Compute Shading** 研究的是通过层级/自适应 shading 把平均 shading 次数压到每 pixel 一次以下：[[Mal18\]](https://doi.org/10.1145/3231578.3232160)

后续 **Efficient Adaptive Deferred Shading with Hardware Scatter Tiles** 更直接指出，纯软件 compute scheduling 会产生额外 memory bandwidth；他们提出硬件 scatter tile 支持来降低这种成本：[[Mal20\]](https://doi.org/10.1145/3406184)

这对于 EEngine 的启示不是“我们去实现硬件 scatter tile”——WebGPU 做不到。

而是：

> **不要让 MaterialTile scheduler 写太多 global-memory bookkeeping。**

也就是说你现在：

```text
classification
pixelClaims
queues
control
validation
```

这些 auxiliary memory traffic 应该尽量减少。

## 当前我认为最值得直接借鉴的三个实现

如果你准备接下来真正改代码，我优先级会是：

**第二参考：Nanite GPU-Driven Materials。**
重点不是它的 geometry，而是 `Visibility → Shading Bin → Compute Material`，尤其是 material/shading bin 的静态注册、GPU classification 和 empty-bin culling。([Unreal Engine](https://www.unrealengine.com/blog/take-a-deep-dive-into-nanite-gpu-driven-materials?utm_source=chatgpt.com))

**第三参考：Horizon Forbidden West Deferred Texturing。**

这条路线既符合 **Nanite/Decima 这类现代 GPU-driven renderer 的实践**，也非常适合 WebGPU 当前能提供的 subgroup + workgroup primitives，而且不需要依赖 DX12 Work Graph 这种 WebGPU 没有的能力。

可以，而且既然你的目标明确是 **WebGPU 2026 高性能主线，不优先照顾旧浏览器/旧 GPU 的最低公分母**，我会比上一版更激进。

# 2026 WebGPU 能给方案 A/B 带来哪些新东西

这次我会明确把这些能力纳入 EEngine 的 High Performance Tier：

```text
WebGPU 2026 Performance Tier
│
├─ subgroups
├─ subgroup_id
├─ subgroup_uniformity
├─ subgroup-size-control
├─ primitive-index
├─ shader-f16
├─ linear_indexing
├─ immediates
└─ transient attachments
```

其中真正直接帮助这次问题的主要是前四个。

------

## `subgroup_id`

以前做：

```text
wave local scratch
```

可能得自己推算“我是哪个 subgroup”。

现在直接：

```wgsl
@builtin(subgroup_id)
@builtin(num_subgroups)
```

。([Chrome for Developers](https://developer.chrome.com/blog/new-in-webgpu-144?utm_source=chatgpt.com))

非常适合：

```text
per-subgroup counters
per-subgroup prefixes
per-subgroup masks
```

。

------

## `subgroup_uniformity`

让 subgroup op 能在更多合理控制流里通过 WGSL uniformity analysis，不需要为了编译器限制把算法写得很别扭。Chrome 145 已提供该语言扩展。([Chrome for Developers](https://developer.chrome.com/blog/new-in-webgpu-145?utm_source=chatgpt.com))

------

## `subgroup-size-control`

这是我觉得对 EEngine 这种“我要榨硬件”的项目非常有价值的新东西。

例如：

```text
NVIDIA:
wave32

AMD:
可以 A/B wave32 / wave64

Intel:
按 adapter 验证
```

你甚至可以建：

```text
ComputePerformanceProfile
```

：

```ts
{
    subgroupSize: 32,
    materialTileSize: 64,
    meshletCompaction: "subgroup",
    materialCompaction: "subgroup"
}
```

不同 GPU 后端第一次启动做 pipeline capability probe。

Chrome 当前实现已经允许通过：

```text
subgroup-size-control
```

feature request 固定 compute subgroup size。([Chrome for Developers](https://developer.chrome.com/blog/new-in-webgpu-151-152?utm_source=chatgpt.com))

# `immediates` 也值得用，但不是解决这次问题

Chrome 149–150 已提供 WebGPU Immediates，也就是接近 Vulkan push constants / D3D root constants 的东西，小量频繁变化数据可以直接 `setImmediates()`，避免小 uniform buffer/bind group 路径。([Chrome for Developers](https://developer.chrome.com/blog/new-in-webgpu-149-150?utm_source=chatgpt.com))

例如非常适合：

```text
frameIndex
width/height
kernel class
debug flags
small pass constants
```

。

可以减少：

```text
CPU update
buffer writes
small dynamic binding
```

但对你现在：

```text
near cube GPU 91%
```

不是主药。

------

# Transient Attachment 也不是主药

WebGPU 146 加入了 `TRANSIENT_ATTACHMENT`，可以让只在 render pass 内临时使用的 attachment 留在 tile memory，减少 VRAM traffic。([Chrome for Developers](https://developer.chrome.com/blog/new-in-webgpu-146?hl=zh-TW&utm_source=chatgpt.com))

但你的：

```text
VisibilityKey
Depth
```

后面 Compute 阶段还要读取。

所以不能简单变 transient。

它适合未来那些：

```text
MSAA temporary
temporary depth/stencil
pass-local attachments
```

。

对这次 Material Classification 问题帮助有限。

## 最关键的一点

我不会因为你使用 WebGPU，就采取“WebGPU 比原生 API 弱，所以保守点”的策略。

到 2026 这套：

```text
subgroups
subgroup_id
subgroup size control
primitive index
f16
immediates
```

已经足以让你做一套相当激进的 GPU-driven scheduler。([GPU Web](https://gpuweb.github.io/gpuweb/wgsl/))

真正不能用的是目前还没成熟进入标准主线的：

```text
Bindless Resource Tables
Work Graphs
Mesh Shader API
```

所以我建议 EEngine 的理念直接定成：

> **Core fallback 保正确，2026 Performance Tier 才是主优化目标。**
>
> 对支持 `subgroups + subgroup-size-control` 的现代 GPU，走高度特化的 wave-level MaterialTile/ShadingBin 路径；旧设备只保留 portable workgroup fallback。

这非常符合你现在“极致压榨”的目标。
