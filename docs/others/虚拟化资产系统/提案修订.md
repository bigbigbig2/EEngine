结论：总体方向正确，而且核心算法目标没有问题；但这份提案目前不能原样作为最终可执行架构。它更适合作为 docs/others/ 下的完整研究母稿。当前拆分后的 ADR、Spec、Implementation 路线反而更合理。
真正阻碍“极致性能”的不是算法不够激进，而是以下几个基础合同还没有闭合。
必须先修正的设计问题
1. 纹理“渐进驻留”目前不等于 GPU 显存驻留
这是最严重的问题。
提案设想通过 TextureHandle + residentMinMip，先驻留 mip tail，再逐渐加入高分辨率 mip。但当前实现创建纹理时已经指定完整的 mipLevelCount，并按完整 mip 链计入显存：
- [TextureResidency.ts (line 1053)](/D:/code/EEngine/OEngine/src/gpu/TextureResidency.ts:1053)
- [TextureResidency.ts (line 1509)](/D:/code/EEngine/OEngine/src/gpu/TextureResidency.ts:1509)
在 WebGPU 合同中，GPUTexture.mipLevelCount 创建时固定，GPUTextureView 的 mip 范围也是不可变 descriptor。晚一点上传高 mip 可以节省网络和上传带宽，但不能被架构宣称为可控的 GPU 显存释放；驱动可能懒分配，但引擎不能依赖这一点。GPUTexture、GPUTextureView descriptor
应明确拆成两种模式：
- 网络渐进模式：预分配完整纹理，只减少下载、解码和上传成本，不声明节省显存。
- 真实显存驻留模式：使用 mip-tier texture array 或 BC physical atlas。promotion 时创建/选择更高一级物理纹理，上传完成后更新逻辑句柄，旧资源延迟退休。
推荐真实路径：
TextureHandle
  -> TextureResidencyTable
  -> bindingSet + physicalTier + layer + generation
  -> immutable GPUTextureView / BindGroup
当前 GpuTextureRef 只包含 bank、routing、layer，没有 residency generation，并且 shader 通过固定的 9 个 bank 分支采样：[GpuTextureRefAbi.ts (line 17)](/D:/code/EEngine/OEngine/src/gpu/GpuTextureRefAbi.ts:17)、[GpuTextureRefAbi.ts (line 121)](/D:/code/EEngine/OEngine/src/gpu/GpuTextureRefAbi.ts:121)。所以不能只加一个 residentMinMip 字段就认为完成了真驻留。
2. 提案混淆了 Group DAG 与 Page
提案的 GeometryPageRecord.parentPageId 把 LOD/refinement 关系放在了 page 上：[终极提案:397 (line 397)](/D:/code/EEngine/docs/others/虚拟化资产系统/EEngine_ADR-0016_Nyx_WebGPU2026_虚拟化资源加载与GPU驱动终极架构提案.md:397)。
这是结构性错误。Page 是传输、压缩和物理驻留单位；Group 才是几何 DAG 和合法 cut 的单位。同一 page 可以装多个具有不同父子关系的 group，不能共享一个可靠的 parentPageId。
正确分层应是：
层	职责	应保存的信息
Group	逻辑 LOD/DAG	bounds、error、refine group、pageId、page offset
Page	I/O 与压缩	file offset、codec、encoded/decoded size、hash
Physical slot	GPU 驻留	bank、slot/offset、generation、flags


当前 cooker 已经把细化关系表达为 refineGroupId：[GeometryCooker.cpp (line 532)](/D:/code/EEngine/OEngine/tools/oengine-asset-core/src/geometry/GeometryCooker.cpp:532)。这个 Nyx 派生的 Group/DAG 算法应完整保留，不应降级成 page parent。
缺页 fallback 也必须是“保持合法 group cut”，不能简单画 parentPageId。
3. Bootstrap 元数据和永久 root residency 没有全局上限
当前 reader 会先把 0..pageBlobOffset 的整个 metadata prefix 读入内存，然后为 asset、hierarchy、group、page 等逐条生成 JS 对象：[OegPackV3.ts (line 116)](/D:/code/EEngine/OEngine/src/assets/OegPackV3.ts:116)。
小包没问题，但百万 group/page 时会造成：
- 首帧前大范围下载；
- metadata hash 延迟；
- 大量 JS 对象与 GC；
- GPU 几何还没请求，CPU 已经加载全部 refinement metadata。
提案虽然强调“小 Manifest”，但没有给 bootstrap index 的字节上限，也没有定义 refinement metadata 的分片。
应选择其一：
- 先限制单个 pack 的 metadata/asset/page 数量，通过空间或资产 shard 拆包；
- 或在后续版本引入二级 metadata：
  PackCatalog -> BootstrapIndex -> RefinementMetadataPage -> GeometryPage。
同时必须定义：
sum(activePack.bootstrapDecodedBytes) <= bootstrapGeometryBudget
sum(activeTexture.mipTailBytes) <= bootstrapTextureBudget
超预算时要有 pack/asset admission、排队和占位资源，不能让“永不驱逐的 root”变成无界常驻集合。
4. 四个 Geometry Bank 和“2～4 draw”缺少真实绑定预算
[FAIL 2.3] Geometry bank 数量没有与实际 shader binding layout、device limits 闭合。
Detection：提案计划同时绑定 4 个 128 MiB bank，但当前 Visibility vertex stage 已经使用 8 个 storage buffer：[MeshletBucketRaster.ts (line 24)](/D:/code/EEngine/OEngine/src/render/MeshletBucketRaster.ts:24)。当前能力合同要求 10 个 storage buffer：[GpuSparseShadingCapability.ts (line 14)](/D:/code/EEngine/OEngine/src/gpu/GpuSparseShadingCapability.ts:14)。
Fix：为最终 V3 raster 写出逐 binding 的完整预算，并按实际 adapter limit 验证；对应 limits/features 与 bind-group 设计。
四 bank 并非一定不可行——V3 cutover 可以删除旧的 meshlet/vertex buffer bindings——但提案必须证明替换后的总数，而不能只定义 maxStorageBufferBindingSize >= 128 MiB。
“每个 major view 只有 2～4 次 draw”同样过于乐观：
- 当前按 32/64/96/128 triangle capacity、decode profile、单双面、coverage、route 划分，最多 64 个 indirect record：[GpuMeshletRasterWorkAbi.ts (line 9)](/D:/code/EEngine/OEngine/src/gpu/GpuMeshletRasterWorkAbi.ts:9)。
- MASK raster 必须采样 alpha，并按 TextureBindingSet 重复 draw：[MeshletBucketRaster.ts (line 153)](/D:/code/EEngine/OEngine/src/render/MeshletBucketRaster.ts:153)。
- primitive-index 能减少 primitive identity varying，但不会自动消除 bank、MASK、双面和容量分桶。
如果坚持 2～4 draw，需要额外设计 visibility-only alpha atlas，使 MASK 不再依赖普通材质 TextureBindingSet。否则 KPI 应改成“有界固定 draw 数 + useful triangle/vertex invocation 比率”，由 benchmark 决定保留多少容量桶。
5. 提案中的 Page ABI 与已经实现的 OEGPACK V3 不是同一个 ABI
提案同时描述了：
- page size 可在 64/128/256/512 KiB 间选择；
- page 内 SoA；
- page-AABB position quantization；
- meshoptimizer stream 再叠加 LZ4。
而现有 V3 是：
- 固定 256 KiB、128 MiB bank：[GeometryAbiV3.ts (line 2)](/D:/code/EEngine/OEngine/src/assets/GeometryAbiV3.ts:2)；
- reader 严格拒绝非 V3.0/256 KiB：[OegPackV3.ts (line 162)](/D:/code/EEngine/OEngine/src/assets/OegPackV3.ts:162)；
- per-meshlet AABB position quantization；
- interleaved vertex stride；
- group header、meshlet header、triangle、vertex 顺序；
- outer codec 只有 raw/LZ4：[GeometryCooker.cpp (line 461)](/D:/code/EEngine/OEngine/tools/oengine-asset-core/src/geometry/GeometryCooker.cpp:461)。
这不是可随意调参的差异。
我的建议是：
- 保留现有 OEGPACK V3 作为 candidate baseline；
- 先接入真实生产 Visibility consumer；
- SoA、其他 page size、meshopt encoded stream 作为 V4 或明确的 layout/codec profile；
- 分别 benchmark raw / LZ4 / meshopt / meshopt+LZ4，不能默认双重编码一定更快。
这不会简化 Nyx 算法，只是防止尚未验证的存储实验破坏已实现 ABI。
其他需要收紧的合同
- GPU feedback 不能让 CPU 每帧扫描整个 page bitset。建议 atomicOr 去重后，由第一次置位者追加到有界 compact queue；只清理 touched words。请求必须包含 pack/global-page identity、pack generation、frame epoch、count、capacity 和 overflow。
- publication 不应等待 queue.onSubmittedWorkDone()。page copy 与 page-table entry publication 应按顺序放入同一提交，下一帧消费；eviction 先撤销映射，再异步等待旧 submission 安全后复用 slot。
- SourceContentHash -> 唯一 TextureAssetId 不够。颜色空间、normal-map 语义、alpha coverage/cutoff、cook recipe、压缩格式都会改变物理结果。当前实现把 semantic、alpha cutoff 和 codec recipe 纳入 identity 是正确的：[TextureAssetPackage.ts (line 194)](/D:/code/EEngine/OEngine/src/assets/TextureAssetPackage.ts:194)。可以共享 source hash，但物理 dedup key 必须基于 cooked payload 与解释语义。
- shader-f16 不应仅因为资产里存了 half 就成为硬要求；只有 WGSL 真正使用 f16 算术/存储并有性能证据时才要求。
- primitive-index 的用法本身是正确的，包括每个 instance 重新从 0 开始；但当前 portable varying 路径已经存在，因此更适合作为 specialization，而非无证据硬门槛。WGSL primitive_index
- BC-only 会不必要地排除只提供 ETC2+ASTC 的实现。当前代码从 BC/ASTC/ETC2 中选择实际可用家族更合理：[MainRenderPipeline.ts (line 1597)](/D:/code/EEngine/OEngine/src/render/pipeline/MainRenderPipeline.ts:1597)。WebGPU 也建议只请求真实需要的 feature，并要求对具体 limit 做协商。GPUWeb optional capabilities
- OPFS 应继续是可选加速层，不能成为 correctness 或首帧依赖。
- staging-buffer ring 不应被写成天然更快。生产实现应先比较合并后的 queue.writeBuffer 与 staging-copy；当前 bootstrap 的逐页串行读取、额外复制和逐页写入只能作为 proof，不能直接扩展：[GeometryBootstrapResidencyV3.ts (line 21)](/D:/code/EEngine/OEngine/src/gpu/GeometryBootstrapResidencyV3.ts:21)。
我建议的最终落地顺序
当前实施文档的垂直切片实际上比终极提案的 Stage 1～5 更合理：[0016 implementation (line 15)](/D:/code/EEngine/docs/implementation/0016-virtualized-assets.md:15)。
建议保持：
1. V3 bootstrap page 真正进入现有 MeshletBucketRaster -> VisibilityKey -> Sparse Shading。
2. GPU Group DAG 选择 desired LOD，缺页保持 resident ancestor cut，并产生 demand。
3. 接入有界 range/decode/verify/batched upload/generation publication。
4. 完成 eviction、replace、cancel、device loss 和 ABA 防护。
5. main view、shadow 全部切到 V3，再删除 V2 geometry path。
6. 先证明纹理渐进下载，再实现能真实降低显存 accounting 的 mip-tier residency。
7. 只有 profiling 证明 source/decode 是瓶颈时才加入 OPFS。
8. GPU decode、SW microtriangle raster、VT 各自单独立项，不混入基础闭环。
尤其不应建立独立的 “Nyx Raster Backend”。它应该替换现有主管线里的 geometry producer/consumer，而不是复制第二套 renderer。
最终评价
可以保留并应完整保留的部分：
- Native cooker 和可追溯算法移植；
- Group/DAG、bootstrap cut、resident ancestor fallback；
- GPU demand → 延迟 readback → 异步 residency → GPU consumer 闭环；
- 固定容量、overflow、generation 和 fail-visible；
- authoring asset 与 runtime package 分离；
- GPU decode、VT、software raster 均以证据门禁进入。
必须重写或降级为实验项的部分：
- parentPageId LOD 模型；
- 仅靠 residentMinMip 实现真实纹理显存驻留；
- 未核算 binding 的四 bank；
- 绝对的 2～4 draw KPI；
- 在 V3 中同时承诺可变 page、SoA、page-AABB 和 meshopt+LZ4；
- 无界 metadata/bootstrap 常驻。
因此，我的结论不是“推翻提案”，而是：核心算法与总体方向值得采用，但 ABI 和资源模型必须以上述方式收紧后，才能称为极致性能架构。当前 ADR + specs + implementation 的轻量化拆分是正确的，终极提案继续留在 others 作为研究来源最合适。
