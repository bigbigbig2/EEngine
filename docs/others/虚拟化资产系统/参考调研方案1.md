你这个质疑是对的。上一轮我把重点放在了**“当前仓库到底哪里慢、哪里会爆内存”**，所以更像一次代码审计；但如果目标是你说的**“WebGPU 下尽可能接近终极形态的资源系统”**，只分析自己代码是不够的，必须把 Unreal / Unity / Nanite / Virtual Texturing / DirectStorage / Cesium / meshoptimizer / KTX2 / Three.js / Bevy / 一些开源 Nanite-like 项目和相关论文放在一起看。

而且比较完之后，我对上一轮方案会做一个重要升级：

> **EEngine 最终不应该只是“GLB + C++/WASM 多线程加载器”。**
>
> 更应该变成一个
> **Virtualized Asset System：虚拟化几何 + 虚拟化纹理 + 离线 Cooker + 页面化存储 + GPU/CPU Feedback Streaming + Content-addressed Cache + 渐进式 Residency。**

这和单纯“把 GLB 加载快一点”已经完全不是一个层次了。

# 二、Unreal Zen Loader：我认为资源层最值得你抄“思想”的部分

UE5 的 Zen Loader 做了一件特别关键的事情：

> **把原来 Runtime 要做的资源依赖解析，尽量提前到 Offline Cook 阶段。**

它不会让正式版本游戏运行的时候：

```text
打开 FBX
解析 FBX
分析引用
解析贴图
构造运行时结构
```

而是提前变成：

```text
Cook
↓
Package Store
↓
Chunk ID
↓
.utoc 元数据
.ucas 数据
↓
Runtime IO Dispatcher
```

Zen Loader 官方说明中明确提到，它在 staging 阶段提前生成优化过的 package/object dependency graph，把 package data、bulk data、shader data 放进 container；运行时使用 Chunk ID 定位资源，减少文件系统和依赖解析开销。很多原先 Runtime 的 EDL 逻辑被搬到了 Offline。([Epic Games Developers][1])

这个思想对 EEngine 极重要。

你现在还是：

```text
BistroExterior.glb
        ↓
GltfLoader
        ↓
JSON
bufferView
accessor
images
materials
nodes
        ↓
SourceGeometry
        ↓
Geometry Cooker
        ↓
Runtime package
```

而最终应该变成：

```text
                       OFFLINE

BistroExterior.glb
        ↓
 OEngine Cooker
        ↓
 scene.oemeta
 geometry.pack
 texture.pack
 material.pack
        ↓
 Content Hash / Chunk ID


                       RUNTIME

scene.oemeta
      ↓
必要 Chunk IDs
      ↓
Streaming Scheduler
      ↓
Residency
```

也就是说：

> **glTF 最终只是 Import Format。**

不是 Runtime Asset Format。

这其实是我现在认为 ADR-0016 应该定死的一条原则。

# 三、Nanite：Geometry Streaming 应该怎么想

Nanite 的意义不仅仅是“Meshlet”。

真正重要的是：

> **Geometry 也可以像 Virtual Texture 一样成为虚拟资源。**

Epic 的 Nanite 技术讲解把它明确类比 Virtual Texturing：

```text
GPU 发现需要更高细节
        ↓
发出 geometry demand
        ↓
CPU asynchronously fulfills
        ↓
加载 geometry page
        ↓
更新 resident set
```

同时它维护 Cluster Hierarchy / DAG，加载和卸载之后都必须保证当前 resident geometry 构成一个合法的 LOD cut，不能出现几何裂缝。([实时渲染进展][2])

官方文档也把 Nanite 描述为 virtualized geometry system，使用高度压缩的内部 mesh format，按感知需要处理几何细节。([Epic Games Developers][3])

这和你当前 EEngine 已经非常接近了一半。

你现在已经有：

```text
SourceGeometry
↓
Meshlet
↓
Renderable Hierarchy
↓
BVH8
↓
GeometryAssetPackage
```

而且现在 Cooker 使用 meshoptimizer、LOD simplification、16-bit position quantization、compact PBR profile。

你缺的不是 Meshlet。

你缺的是：

```text
GeometryAssetPackage
          ↓
       分 PAGE
          ↓
Residency table
          ↓
GPU visibility demand
          ↓
Streaming request
```

也就是把：

```text
Geometry Package
```

升级为：

```text
Virtual Geometry Pages
```

这是两个完全不同的阶段。

# 五、Meshoptimizer 2026 的发展其实很适合你的路线

你现在 Geometry Cooker 已经在用 meshoptimizer，这个选择很好。

因为 meshoptimizer 的目标不是简单：

> 压得越小越好。

它非常强调：

```text
压缩
+
GPU-friendly layout
+
decode speed
+
vertex locality
```

官方现在甚至明确讨论了 Meshlet compression。

meshoptimizer 的 meshlet codec 针对 meshlet vertex reference + triangle 数据进行独立压缩，而且官方说明现代 CPU decoder 可以达到约 7–10 GB/s；另外还提供 GPU meshlet decode shader 示例。([GitHub][5])

JavaScript/WASM Meshopt decoder 使用 SIMD 时也可以达到现代桌面机约 1–3 GB/s 的量级。([GitHub][6])

所以对于 EEngine，我会更倾向：

```text
Draco
    ↓
支持 Source Import

Meshopt
    ↓
作为主要 Runtime Geometry Codec
```

原因很简单。

Draco 更偏：

```text
最大化传输压缩率
```

而 meshopt 更偏：

```text
GPU-friendly
+
快速解码
+
保持优化后的顺序
```

meshoptimizer 官方自己也指出，传统 mesh compression 方案为了压缩率可能破坏 vertex/index order，并引入 Runtime reorder / requantization 成本。([GitHub][5])

这正好符合你“极致运行性能优先”的目标。

# 七、但是要注意：WebGPU 并没有 DirectStorage

这里必须把现实边界讲清楚。

DirectStorage + RTX IO 最理想的是：

```text
NVMe
 ↓
compressed data
 ↓
GPU
 ↓
GPU decompression
 ↓
VRAM
```

RTX IO / GDeflate 的目标就是把大量 decompression 从 CPU 移到 GPU；NVIDIA 的资料强调 GPU decompression 可以避免 CPU 成为 NVMe 吞吐瓶颈。([NVIDIA Developer][8])

DirectStorage 甚至围绕高 IO queue depth、64 KiB tile 和 GPU decompression 做了专门设计。([Microsoft for Developers][9])

而 WebGPU 2026 当前标准 feature list 里包括：

```text
texture-compression-bc
texture-compression-etc2
texture-compression-astc
shader-f16
subgroups
subgroup-size-control
...
```

但没有：

```text
DirectStorage
Sparse Buffer
Sparse Texture Residency
NVMe → GPU DMA
```

([W3C][10])

所以 WebGPU 最终最多可以做：

```text
HTTP / OPFS
    ↓
compressed bytes
    ↓
CPU address space
    ↓
GPUBuffer
    ↓
Compute decompression
```

而不是：

```text
SSD
 ↓
GPU VRAM
```

这点不能吹过头。

但即使这样，也已经可以大幅减少：

```text
CPU decode
CPU intermediate copies
JS typed-array transform
```

这些成本。

# 八、Unreal Virtual Texture 对你这 405 张贴图非常重要

你这个 Bistro 的主要问题恰恰是 Texture。

传统 texture streaming：

```text
Texture A
↓
load whole mip 6

Texture B
↓
load whole mip 5
```

UE Streaming Virtual Texture 则是：

```text
Mip
↓
切 Tile

GPU
↓
实际看到了哪些 texel
↓
反馈 tile request
↓
只加载这些 tile
```

UE 官方文档明确说明，它把所有 mip 切成固定大小 tile，GPU 根据屏幕上真正访问的 tile 发出需求，从而避免“对象只露出来一点，却把整张高 mip 载入”的保守加载方式。([Epic Games Developers][11])

这对 Bistro 特别明显。

你现在是：

```text
一个 Material 出现在屏幕上
        ↓
整个 2048² texture resident
```

终极应该趋向：

```text
2048²
┌───────────────┐
│ □ □ □ □ □ □ □ │
│ □ ■ ■ □ □ □ □ │
│ □ ■ ■ □ □ □ □ │
│ □ □ □ □ □ □ □ │
└───────────────┘

只加载 ■
```

# 九、这里还有 1998 年的经典 Clipmap 思路

Virtual Texture 并不是新概念。

SIGGRAPH 1998 的 **The Clipmap: A Virtual Mipmap** 就提出：

> 用固定物理内存缓存任意大的纹理。

其展示系统甚至虚拟化过约 170 GB 的 texture dataset 并维持实时运行。([SciSpace][12])

后来 Software Virtual Texturing 的典型逻辑逐渐变成：

```text
Virtual Address
       ↓
Page Table
       ↓
Physical Texture Cache
```

现代 UE SVT 其实也是这条思想线的工业化版本。

# 十、而且纹理 Streaming 不应该“加载越快越好”，要有 Frame Budget

这一点很重要。

有篇针对大型城市的 texture streaming 研究，核心贡献之一就是：

> 根据实际 frame latency 自适应调整 streaming workload。

目的不是：

```text
尽可能疯狂加载
```

而是：

```text
不影响当前帧
前提下尽可能加载
```

因为一旦 Streaming 引起：

```text
GPU resource creation spike
upload spike
binding changes
cache eviction
```

画面反而会顿。

论文处理了数百万 textures，以及 40GB 级压缩纹理数据。([施普林格自然链接][13])

这和你的追求特别一致：

> 极致性能不是“Loading Thread 100% 跑满”。

而应该是：

```text
Frame Time Budget
        ↓
允许 Streaming 的 CPU/GPU/Upload budget
```

比如：

```text
16.67 ms frame budget

Rendering      11.2 ms
Streaming GPU   ≤0.5 ms
CPU streaming   ≤1 ms
Upload          ≤X MB/frame
```

如果 GPU 已经到 15.8ms：

```text
Streaming throttle
```

这才是 AAA engine 的思路。

# 二十、Geometry 和 Texture 我甚至建议分两种虚拟化程度

Geometry：

```text
真正 Page Virtualization
```

因为你已经是 storage-buffer / GPU-driven 架构。

这最适合：

```text
GeometryPageID
↓
PhysicalAddressTable
↓
GPU Buffer Pool
```

甚至以后：

```text
Visibility
↓
Missing Page Feedback
```

---

Texture 则分阶段。

因为 WebGPU 没有真正的 sparse texture API。

第一阶段可以继续沿用你目前：

```text
Texture Array Banks
```

但支持：

```text
mip-level progressive residency
```

第二阶段如果场景规模进一步变大，再上：

```text
Software Virtual Texture

VirtualPage
    ↓
Page Table Texture
    ↓
Physical Cache Atlas
```

这就类似 UE SVT。

# 二十二、Bistro 最后就不应该再是 988 MB “一次加载”

假设最终：

```text
Bistro Source GLB
988 MiB
```

Runtime 根本不应该关心这个数字。

应该关心的是：

```text
Bootstrap
    +
visible geometry
    +
visible mip tail
```

比如真正第一帧可能只需要整个资产的一小部分。

重点 KPI 应该变为：

| 指标                   | 意义                             |
| -------------------- | ------------------------------ |
| TTFMF                | Time To First Meaningful Frame |
| TTI                  | Time To Interactive            |
| Bootstrap Bytes      | 第一帧前必须下载多少                     |
| CPU Peak Memory      | Loader 峰值                      |
| Worker Peak Memory   | Cooker/Codec 峰值                |
| Upload MB/frame      | 每帧 GPU 上传压力                    |
| Streaming CPU ms     | 加载系统 CPU 成本                    |
| Streaming GPU ms     | GPU decode/copy 成本             |
| Residency Miss Rate  | 缺页程度                           |
| Page Thrash Rate     | 抖动程度                           |
| Time To Full Quality | 全质量完成时间                        |

而不是只测：

```text
load() 花了几秒
```

# 二十三、如果让我现在给技术路线排优先级

我不会第一步就写完整 Virtual Texture，也不会第一步就搞 GPU decompression。

真正合理的是：

1. **先把 Runtime Asset 和 Source Asset 完全分家。**建立 Scene Manifest + Pack Container + Chunk/Page ID。
2. **Offline C++ Cooker。**先解决 dedup、geometry optimize、meshopt、texture native compression、Mip Tail。
3. **Progressive Geometry Streaming。**Geometry Package 改成 Geometry Pages，先 coarse LOD，后高 LOD。
4. **Texture Mip Streaming。**Mip tail 先 resident，高清 mip 按可见性/距离异步提升。
5. **统一 Streaming Scheduler。**Priority + bandwidth + CPU budget + GPU upload budget + cancellation。
6. **OPFS Persistent Cache。**Content-addressed。
7. **GPU Feedback Geometry Streaming。**
8. **Software Virtual Texture。**
9. **WebGPU Compute Geometry Decompression。**
10. **Adaptive frame-time streaming budget。**

到这里，才真正开始接近：

> **Nanite + Zen Loader + Streaming Virtual Texture + DirectStorage 思想在 WebGPU 环境下的重新实现。**

而不是简单：

> “Three.js GLTFLoader 加 Worker 的加强版。”

---

所以你刚才提醒得非常关键。**如果目标只是解决 Bistro 加载失败，之前那套诊断够用；但如果目标是“最终 EEngine 的极致资源体系”，我们必须把问题提升到 Virtual Asset Architecture 层面。**

我建议我们后面的 ADR-0016 就不要叫简单的 `Asset Loading Optimization`，而直接定成：

> **ADR-0016 — Virtualized Asset Cooking, Streaming and Residency Architecture**

然后里面专门做 **Unreal Zen/Nanite/SVT、Unity AssetBundle、Cesium 3D Tiles、meshoptimizer、KTX2、DirectStorage/RTX IO、Three.js、Bevy、Granite、Nyx 和相关论文的逐项对比**，最后再收敛成适合 WebGPU/EEngine 的架构，而不是照搬任何一个。
