> 文档类型：架构审视 / 性能优化提案 / 后续测试计划  
> 项目：EEngine WebGPU GPU-Driven Renderer  
> ADR：ADR-0015 — Visibility-Native PBR Receiver & Lighting Pipeline  
> 审视基线：`master`，核心实现提交 `588e6e1684f7e676b039820eee4467f98381cad4`  
> 提交信息：`feat(renderer): complete ADR-0015 implementation stages`  
> 日期：2026-09-15

---

# 1. 文档目的

这份文档不是单纯解释 ADR-0015“做了什么”，而是从 **EEngine 当前源码、WebGPU 约束、GPU-Driven Renderer 结构、实际性能风险与后续可验证优化路径** 几个维度，对 ADR-0015 进行一次工程审视。

重点回答以下问题：

1. ADR-0015 当前代码是否真正实现了设计目标；
2. 当前架构是否合理，哪些决策值得保留；
3. 哪些性能收益目前只是“理论成立”，尚未被 GPU 数据证明；
4. 当前最可能残留的性能瓶颈是什么；
5. 后续应该如何测试，避免继续无证据地大改架构；
6. 哪些问题应该继续放在 ADR-0015 收口，哪些应该独立为下一份 ADR；
7. 如何形成一个可重复、可比较、可回退的性能优化流程。

本文的核心原则是：

> **先区分 correctness、architecture improvement 与 actual GPU performance improvement。**

ADR-0015 当前已经基本证明前两项，但第三项还没有完整闭环。

---

# 2. 当前结论摘要

ADR-0015 当前实现方向总体合理，而且比 ADR-0013 后期“所有 opaque 都先 Sparse Bin，再 Surface，再后置 Lighting”的固定组织明显更适合 EEngine 当前追求的高性能路线。

当前最重要的改进包括：

- 从固定 Surface 输出改为 **Demand-Driven Opaque Receiver**；
- 基础 PBR 可以直接完成：Material Evaluation、Direct Lighting、Environment IBL、HDR 输出；
- 没有高级间接光消费者时，不再强制生成完整 Surface/provider/lighting resolve；
- opaque bin 根据 immutable publication 选择：
  - `0 bin → None`
  - `1 bin → DirectSingleBin`
  - `>1 bin → SparseMicrotile`
- 单 bin 路径已经可以移除 `ShadingBinId` MRT、classifier、sparse heap、finalizer、indirect args；
- Shader/BGL/WGSL 已开始根据 output dependency、shadow、texture-bank mask、velocity、environment IBL 做物理 specialization；
- `TextureResidencyEvidence` 已能继续提供较细的 texture ledger；
- Triangle Setup Cache 没有因为“设计上很高级”就强行启用，而是保持 evidence-gated。

这些都是正确方向。

但是，当前仍然不能把 ADR-0015 写成：

> “性能优化已经成功。”

因为目前最大的几个问题仍然需要实测：

1. `DirectSingleBin` 全屏固定网格是否真的比 `SparseMicrotile` 更快；
2. 近景 PBR 是否主要被 `sparse_evaluate_geometry` / triangle reconstruction 主导；
3. Texture sampling / bank routing / high-resolution mip 是否已经成为近景第二主因；
4. pipeline/revision 生命周期是否会在动态材质、streaming、texture relocation 时形成 CPU hitch；
5. 高级效果开启后，当前 `needsIndirectComponents` 粒度是否仍生成了不必要的 Surface 数据。

因此，本阶段最优策略不是再做一次大架构改造，而是：

> **冻结 ADR-0015 当前结构 → 做受控 A/B → 找真实 GPU dominant cost → 再进入下一轮局部优化。**

# 3. ADR-0015 要解决的原始问题

ADR-0015 的根本目标不是“重新设计整个 Renderer”，而是解决 ADR-0013 收敛后暴露出的基础 PBR 像素成本问题。

典型旧链：

```text
Hardware Visibility
    ↓
ShadingBin classify / queue / finalize
    ↓
specialized material + direct lighting
    ↓
SurfaceLite
    ↓
LongRangeDiffuseProvider
    ↓
OpaqueLightingResolve
    ↓
HDR
```

这条链在高级效果全部关闭时仍可能保留：

- 全分辨率 Surface 写入；
- provider pass；
- lighting resolve；
- 多余纹理中间结果；
- 单 bin 仍进行 classification；
- 单 bin 仍维护 ShadingBinId MRT；
- 单 bin 仍维护 heap / indirect args；
- receiver shader 仍可能携带未使用 texture bank / sampler / output；
- velocity-off 时仍可能保留相关资源。

这些问题共同指向：

> **基础 PBR 路径仍携带为高级路径准备的结构成本。**

ADR-0015 的第一价值，就是把这些固定成本重新变为 demand-driven。

---

# 4. 当前真实生产架构

当前生产架构可以抽象为：

```text
GPU Work Generation
        ↓
Hardware Visibility
        ↓
Immutable Opaque Publication Summary
        │
        ├── 0 published opaque bins
        │       ↓
        │      None
        │
        ├── 1 published opaque bin
        │       ↓
        │   DirectSingleBin
        │
        └── >1 published opaque bins
                ↓
            SparseMicrotile
                ↓
        Specialized Receiver
                ↓
        Geometry Reconstruction
                ↓
        Material Evaluation
                ↓
        Clustered Direct Lighting
                ↓
        ┌───────────────────────────────┐
        │                               │
No complex indirect consumer      Complex indirect consumer exists
        │                               │
Environment IBL in receiver        Demand Surface outputs
        │                               │
        HDR                        AO/GI/SSR/Spatial GI
                                        ↓
                               Indirect Composition
                                        ↓
                                       HDR
```

关键不是“三条路径”本身，而是：

> **Physical pipeline topology 现在开始由 immutable publication + consumer demand 决定，而不是由每帧 GPU visible state 临时决定。**

这是后续应该长期保留的架构原则。

# 5. Stage 1：Demand-Driven 基础光照融合审视

## 5.1 当前实现

`OpaqueShadingDemand.ts` 当前把 opaque consumer 的需求统一收敛成：

```text
hasOpaqueReceiver
hasOpaqueLitReceiver
hasOpaqueUnlitReceiver
needsHdr
needsSurface
needsDiffuseSurface
needsVelocity
needsPreviousDepth
needsIndirectComponents
needsLightingDebug
needsEnvironmentIbl
shadowSamplingEnabled
outputDependencyMask
```

输入主要包括：

```text
shadows
gtao
ssgi
ssr
spatialGiQuery
needsPreviousDepth
motionBlur
debugView
```

核心逻辑可概括为：

```text
没有复杂间接光需求：
    Lit Receiver
    → Material
    → Direct
    → Environment IBL
    → HDR

存在复杂间接光需求：
    Lit Receiver
    → Material
    → Direct
    → demanded Surface
    → downstream indirect owner
```

这是 ADR-0015 最重要的结构变化。

## 5.2 为什么这个方向合理

旧式固定链的主要问题是：

```text
基础 PBR
也必须支付
高级效果数据准备成本
```

而现在：

```text
consumer 没有请求
→ 不生成对应 FrameProduct
→ 不创建资源
→ 不增加 BGL
→ 不写 StorageTexture
→ 不执行 downstream pass
```

这已经不只是“FrameGraph 上少一个节点”，而是 shader resource ABI 也开始被反向收窄。

正确链应该是：

```text
Feature Demand
    ↓
FrameProduct Demand
    ↓
Pipeline Descriptor
    ↓
Bind Layout
    ↓
WGSL Source
    ↓
Actual GPU Resource
```

当前 ADR-0015 已经开始做到这一点。

# 6. Stage 1 仍存在的设计改进空间

当前最大的问题是 `needsIndirectComponents` 仍然是一个比较粗的总开关。

目前 GTAO、SSGI、SSR、Spatial GI、Lighting Debug 任何一个出现，都倾向于进入：

```text
needsSurface = true
needsDiffuseSurface = true
needsEnvironmentIbl = false
```

这在 correctness 上稳妥，但对未来 AAA 全效果路径不一定是最优。

理想情况下不同效果需求应更细：

```text
GTAO
→ Depth + Normal

SSR
→ Depth + Normal + Roughness + Specular baseline

SSGI
→ Depth + Normal + Diffuse Reflectance

Spatial GI
→ Position / Normal / Receiver BRDF terms

Motion Blur
→ Velocity

TAA / NSS
→ Velocity / reactive / history confidence
```

未来可考虑从：

```text
needsSurface
needsDiffuseSurface
```

进一步演化成一个更细的 `OpaqueReceiverOutputMask`：

```text
Normal
GeometricNormal
Roughness
Metallic
DiffuseReflectance
MaterialAO
Velocity
ReceiverFlags
SpecularBaseline
...
```

然后让 GTAO、SSR、SSGI、SpatialGI、Temporal、Debug 分别声明真实 read-set。

### 建议

暂时不要立刻大改。

先用当前 Stage 1 做 performance validation。如果高级效果打开以后 Surface write bandwidth 重新成为明显瓶颈，再开始做第二代 demand mask。

# 7. Stage 2：0 / 1 / >1 Bin 调度审视

当前调度：

```text
publishedOpaqueBinCount == 0
    → None

publishedOpaqueBinCount == 1
    → DirectSingleBin

publishedOpaqueBinCount > 1
    → SparseMicrotile
```

这个判断来自 immutable publication，而不是当前帧 camera visibility。

这是一个非常重要的正确决策。

---

# 8. 为什么不应该用 visible-bin / coverage 动态切换

一个看起来“聪明”的方案是：

```text
这一帧 coverage 高 → Direct
下一帧 coverage 低 → Sparse
```

或者：

```text
visible bins == 1 → Direct
visible bins > 1 → Sparse
```

但这样会引入：

```text
camera movement
    ↓
visible state change
    ↓
execution mode change
    ↓
attachment layout change
    ↓
FrameGraph key change
    ↓
pipeline / BGL change
    ↓
resource identity change
```

最终可能造成 graph rebuild、pipeline variation、bind-group churn、history invalidation、CPU branch explosion 和 frame-time jitter。

因此当前策略：

> **publication 决定 physical topology，camera 只影响 actual workload**

应继续保留。

---

# 9. DirectSingleBin 当前做了什么

DirectSingleBin 当前主要收益：

```text
不需要 ShadingBinId attachment
不需要 classifier
不需要 sparse heap
不需要 finalizer
不需要 indirect args
不需要 ShadingBin settings
```

同时 `VisibilityKey` 仍然保留。

Compute 使用：

```text
ceil(width / 8) × ceil(height / 8)
```

固定全屏网格。

每个 lane：

```text
读取 VisibilityKey
↓
background 立即 return
↓
有效 pixel 才执行真正 receiver
```

这个实现简单，正确性边界也很好控制。

---

# 10. DirectSingleBin 最大的性能悬念

它的问题也非常直接：

> **即使背景立即退出，lane 仍然被 dispatch。**

定义：

```text
N = internal resolution pixel count
P = valid foreground pixel count
coverage = P / N
```

DirectSingleBin 的基础调度量更接近 `N`。

SparseMicrotile 的 receiver 实际工作更接近 active microtiles，也就是前景区域。

因此：

```text
coverage ≈ 100%
```

Direct 很有希望占优，因为 classifier + heap + finalize 的固定成本不再值得支付。

但：

```text
coverage ≈ 10% ~ 30%
```

时，Direct 可能为大量 background lane 支付：

```text
dispatch
textureLoad VisibilityKey
branch
return
```

这是否仍优于：

```text
classifier
+ compact microtile queue
+ indirect resolve
```

不能靠架构推导决定，必须测试。

# 12. 是否需要 coverage heuristic

现阶段建议：**不要。**

即使测试得到：

```text
coverage > 70% → Direct 更快
coverage < 40% → Sparse 更快
```

也不应该马上做当前帧 coverage threshold。

如果 Direct 在低 coverage 下真的明显劣化，更好的方向是研究：

```text
SingleBinSparse
```

即：

```text
一个 bin
+ GPU compact work
+ 无 64-bin classification
+ 一个 specialized receiver
```

它可能同时保留：

```text
single-bin specialization
+
sparse spatial workload
```

这是未来值得验证的候选。

---

# 13. Fullscreen Fragment Receiver 候选

另一个值得保留的备选是：

```text
Fullscreen Fragment Visibility Shading
```

即：

```text
fullscreen triangle
    ↓
VisibilityKey
    ↓
fragment receiver
    ↓
HDR render attachment
```

潜在优势：

- render attachment 写路径；
- 不需要 storage texture HDR；
- 可能更接近部分桌面 GPU 对 fullscreen shading 的成熟调度路径；
- 某些 GPU 上 fragment/cache behavior 可能更好。

潜在问题：

- 当前 receiver 代码主要围绕 compute 构建；
- 输出组合方式变化；
- 需要新的 correctness / performance validation；
- 不应长期同时维护两套 single-bin backend，除非数据证明有明确设备分层收益。

因此建议：先测现有 DirectSingleBin；只有现有 compute Direct 在高 coverage 下仍明显不理想时，再实验 fullscreen fragment。

# 14. Stage 2 当前明确需要修正的文档问题

真实 Visibility：

```text
VisibilityKey = r32uint
ShadingBinId  = r8uint
```

SparseMicrotile：

```text
r32uint VisibilityKey
+
r8uint ShadingBinId
```

DirectSingleBin：

```text
r32uint VisibilityKey
```

因此省掉的是：

```text
r8uint ShadingBinId
```

不是 `r32uint`。

建议 ADR 修正为：

> DirectSingleBin 减少一份全内部分辨率 `r8uint ShadingBinId` attachment 的创建、clear、store 与后续 sampling/read dependency。

同时避免直接宣称“节省 4 B/pixel”，因为 `r8uint` 是逻辑格式，但底层 tile/storage/compression/alignment 仍由 GPU 实现决定。

# 15. Stage 3：Receiver Hot Path 审视

ADR-0015 Stage 3 当前主要做的是：

- velocity-off 物理裁剪；
- texture-bank read set；
- slot-specific texture access；
- source audit；
- texture ledger；
- 保持 Triangle Setup Cache disabled。

这些逻辑合理。

但 Stage 3 当前仍没有解决最可能的近景核心成本：

> **Triangle / Attribute Reconstruction 仍然按 pixel 执行。**

# 16. 当前 Receiver 逐像素工作模型

当前有效 PBR pixel 大体要做：

```text
VisibilityKey
    ↓
MeshletWork Slot
    ↓
MeshletWork Record
    ↓
Instance Record
    ↓
Geometry Slot
    ↓
Asset Metadata
    ↓
Triangle local primitive
    ↓
3 vertices
    ↓
decode packed position / normal / UV / tangent / color
    ↓
world transform
    ↓
clip / barycentric reconstruction
    ↓
perspective-correct interpolation
    ↓
UV gradients
    ↓
material texture sampling
    ↓
normal mapping
    ↓
PBR terms
    ↓
clustered lighting
    ↓
shadow
    ↓
IBL / output
```

这是一条很长的 per-pixel dependency chain。

当镜头拉近时，同一三角形可能从远景覆盖几十像素变为近景覆盖几千甚至几万像素，于是很多 triangle-level 数据被重复读取和计算。

这非常可能是 Near-camera GPU utilization / Receiver time 大幅增长的主要来源之一。

---

# 17. 为什么现在仍不应该立刻开启 Triangle Setup Cache

因为 cache 也不是免费的。

新增：

```text
TriangleSetup Producer
    ↓
Setup Buffer
    ↓
Extra Dispatch
    ↓
Extra Storage Traffic
    ↓
Synchronization
    ↓
Receiver Lookup
```

如果 primitive 很小，例如平均只覆盖 1~4 pixel，则 setup once + buffer write + buffer read 可能比重复重建还贵。

只有当：

```text
large triangle
coverage high
receiver reconstruction dominant
```

时 setup reuse 才真正可能有收益。

当前 `packed_triangle_setup_enabled = false` 建议继续保持。

# 18. Triangle Setup 优化应该如何验证

先测 Receiver 的 scaling。

建立：

```text
trianglePixelCoverageHistogram
```

例如：

```text
1–4 px
5–16 px
17–64 px
65–256 px
257–1024 px
>1024 px
```

同时记录：

```text
visible triangle count

receiver GPU time
```

如果 Near 场景表现为：

```text
P 大幅增长
visible triangle 基本不变
receiver GPU time 与 P 强相关
```

就说明 per-pixel reconstruction 值得进一步拆。

# 19. 推荐的 Triangle Setup 优化路线

不要一开始做“全局所有 triangle setup cache”。

优先尝试：

```text
LargeTriangleSetupCache
```

门槛形式：

```text
estimated coverage > threshold
```

例如：

```text
32 px
64 px
128 px
```

Setup record 可以考虑存：

```text
screen-space triangle edges
perspective reciprocal terms
world-space interpolation basis
UV interpolation basis
normal/tangent basis
material/instance validated identity
```

然后 pixel receiver 变成：

```text
VisibilityKey
↓
setup lookup
↓
barycentric
↓
attribute interpolation
↓
material / lighting
```

但 record 大小必须非常克制，否则可能出现：

```text
ALU ↓
Bandwidth ↑↑
```

最终总时间反而更慢。

# 20. 推荐 Triangle Setup A/B

测试组：

```text
A: setup off
B: setup threshold = 128 px
C: threshold = 64 px
D: threshold = 32 px
```

记录：

```text
setup triangle count
setup bytes
setup producer GPU ms
receiver GPU ms
total opaque GPU ms
P50/P95/P99
```

保留条件：

```text
Receiver 时间下降
且
Total Opaque 时间下降
且
P95 不恶化
```

如果只是：

```text
Receiver -0.5 ms
Setup +0.7 ms
```

则直接删除。

# 21. Texture Bank Specialization 审视

当前 `GpuTextureRefAbi` / shader generation 已开始根据 `textureBankMask` 生成静态 bank read-set。

这个方向合理，因为它避免所有 textured program 都携带完整 9-bank 读取路径。

对例如 `PbrOrm`，当前 audit 已能证明只生成真实 slot 的访问。

这个方向应保留。

---

# 22. 不建议继续无止境增加 Shader Permutation

当前 specialization 已经包含：

```text
programId
textureBindingSetId
outputDependencyMask
shadowSamplingEnabled
executionMode
textureBankMask
capabilityFingerprint
formatProfile
```

这已经是一个不小的 permutation 空间。

继续增加：

```text
roughness mode
normal map mode
IBL mode
AO mode
individual sampler classes
...
```

可能带来：

```text
shader compile cost
pipeline cache pressure
code size
warm-up time
revision rebuild cost
```

因此后续应该遵循：

> **只有 source audit + GPU timing 同时证明某个 runtime branch 是 hot cost，才继续 creation-time specialization。**

---

# 23. Texture Residency 现在应该重点测什么

当前 ledger 已经可以用于核对：

```text
source width / height
decoded width / height
GPU width / height
format
mip count
logical bytes
resident bytes
allocated bytes
segment
layer
binding set
```

下一步不应该只是看总显存，而要回答：

```text
近景时 GPU 真的在访问什么 mip？
```

推荐新增或临时 instrumentation：

```text
per material:
    bank class
    texture dimensions
    mip count
    estimated sampled lod distribution
```

重点排查：

```text
近景
→ 高分辨率 mip
→ cache pressure
→ receiver latency
```

是否和 GPU time 同步变化。

---

# 24. Pipeline Lifetime：当前 correctness 很好，但性能边界需要继续收

`SparseShadingGpuRevisionOwner` 当前生命周期做得比较严谨：

```text
Prepare new revision
↓
CPU transaction commit
↓
Atomic publish
↓
Old revision stays alive
↓
submitted work complete
↓
destroy old revision
```

这对 resize、patch、device loss、abort、revision retirement 都非常正确。

当前 resize validation 也已经验证旧 GPU revision 最终会 drained。

这一点应该保留。

---

# 25. Pipeline Lifetime 当前潜在性能问题

当前 GPU revision creation 仍可能走：

```text
SparseShadingGpuRevisionOwner.prepare
↓
createGpuRevision
↓
SparseShadingResolvePass.create
↓
createSparseShadingShaderVariant
↓
createShaderModule
↓
createBindGroupLayout
↓
createPipelineLayout
↓
createComputePipeline
```

也就是说：

```text
publication revision lifetime
```

和：

```text
native GPU pipeline lifetime
```

还没有完全解耦。

稳定帧不会重复创建，所以 basic static scene 没问题。

# 28. 当前一个小架构问题：Direct 仍在执行 Sparse Sizing

当前 publication 先：

```text
activeBins
↓
executionMode
↓
preflightGpuShadingBinSizing(...)
```

即使 mode 是 `none` 或 `direct-single-bin`，也会做 sparse microtile sizing。

这通常不是 GPU 性能问题，但会产生抽象不一致：

> Direct publication 仍然被 Sparse heap 的 limit 逻辑约束。

更干净的设计应该是：

```ts
type ShadingPhysicalSizing =
  | { mode: "none" }
  | {
      mode: "direct-single-bin"
      dispatchWidth: number
      dispatchHeight: number
    }
  | {
      mode: "sparse-microtile"
      microtilesX: number
      microtilesY: number
      heapBytes: number
      indirectBytes: number
      ...
    }
```

这样 snapshot physical description 和 actual GPU resource closure 完全一致。

建议列为 `P1 architecture cleanup`，不是当前性能阻塞项。

# 42. 不建议当前做的事情

## 42.1 不建议重写成传统 Deferred GBuffer

当前 Hardware Visibility 已经形成完整 GPU-driven identity。除非明确证明 triangle reconstruction 无法通过局部优化解决，否则现在直接回到传统 GBuffer 成本太高。

## 42.2 不建议加入每帧 coverage heuristic

会破坏 stable topology。

## 42.3 不建议立即引入 ReSTIR GI

它和当前 effects-off PBR receiver cost 不是同一个问题。

## 42.4 不建议为了“高级”开启 Triangle Setup Cache

必须 GPU data 证明。

## 42.5 不建议只看 GPU Utilization

例如 30% → 80% 不能解释成某 shader 慢了 2.67 倍。必须使用 GPU timestamps + workload counters。

# 43. ADR-0015 建议验收标准

ADR 可以从 `proposed / implementation-complete` 升级为 `accepted`，至少应满足以下条件。

## Correctness

- Basic / Full 固定机位无明显视觉回归；
- Direct / Sparse 输出语义一致；
- Shadow on/off 一致；
- Environment IBL 与 DeferredIndirect 语义一致；
- resize 正确；
- material patch 正确；
- texture relocation 正确；
- device-loss rebuild 正确；
- old revision 正常 retirement；
- Final Output fail-closed 正常。

## Resource

- effects-off 不存在无 consumer Surface；
- Direct 不存在 ShadingBin heap/args；
- Direct 不存在 ShadingBinId attachment；
- velocity-off 不存在 velocity storage；
- textureless program 不携带 texture bank；
- static frame resource creation plateau。

## Performance

至少应证明：

```text
ADR-0015 当前基础链
没有显著回退于 ADR-0013 基线
```

并且至少有一个明确可归因的收益，例如：

```text
effects-off PBR
or
single-bin high coverage
```

而不是只证明“Pass 数少了”。

# 48. 这份 ADR 当前最值得保留的架构原则

## 原则 1：Visibility 是 opaque identity 的唯一真实入口

不要再复制另一套 material/geometry classification truth。

## 原则 2：Publication 决定 physical topology

不要让 camera visibility 决定 pipeline topology。

## 原则 3：Consumer demand 反向决定 producer outputs

高级效果关闭时必须物理消失。

## 原则 4：Shader specialization 必须有真实 read-set 证据

不为想象中的性能制造 permutation。

## 原则 5：Resource lifetime 与 submitted GPU work 对齐

不能为了立即释放破坏 in-flight correctness。

## 原则 6：Performance optimization 必须验证 end-to-end GPU time

不能只看 Pass 数、代码行数、GPU utilization 或某一个局部 pass。

# 49. 最终评价

ADR-0015 当前已经不是一个“概念提案”，而是一个基本落地的生产架构重构。

总体评价：

| 维度 | 当前评价 |
| --- | --- |
| 架构方向 | 很好 |
| Demand-driven 思路 | 正确 |

| Shader specialization | 扎实 |
| Resource pruning | 明显改善 |
| GPU revision 生命周期 | 很强 |
| Pipeline lifetime | 仍可优化 |

| Near-camera receiver 成本 | 尚未解决 |
