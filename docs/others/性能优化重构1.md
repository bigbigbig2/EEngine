可以，而且这一次我会比前面更激进。

我重新把你当前 `2fe9d48c...` 版本的 GPU 链路、`GpuWorkGenerationAbi / GpuExactRasterAbi / PackedMaterialResolve / Surface ABI / Rendering Lab` 看了一遍，又对照了 Nanite、Nanite GPU-Driven Materials、meshlet/cluster rendering 和当前 WebGPU 能力。我的判断是：

# 1. 第一刀：彻底取消“正常路径的一 Triangle 一 Work Record”

这是我现在认为**收益第一名**的改造。

你当前 ABI 明确规定：

```text
GpuRasterWork = 24 B

instance_record_index
geometry_record_index
meshlet_record_index
local_triangle_index
material_handle
raster_flags
```

也就是说：

```text
1 triangle
=
1 RasterWork
```

然后 Exact Raster 又变成：

```text
32 B / triangle
```

增加：

```text
setup_index
exact_flags
```

所以一个拥有 80 triangle 的 meshlet，光 work record 层理论上就可能经历：

```text
第一阶段：

80 × 24 B
= 1920 B


Exact 后：

80 × 32 B
= 2560 B


合计：
≈ 4480 B
```

而我们真正需要描述这个 Meshlet 的核心信息可能只有：

```text
instance
geometry
meshlet
material
flags

≈ 16~20 B
```

不是说整个 GPU 流量能直接减少 200 倍，但是：

> **Work Queue 这一层的数据膨胀确实是两个数量级级别的机会。**

------

## 我建议新建 `GpuMeshletRasterWork`

例如：

```ts
struct MeshletRasterWork {
    instanceIndex: u32,
    geometryIndex: u32,
    meshletIndex: u32,
    materialHandle: u32,
}
```

16 B。

甚至 flags 可以和 material/kernel 信息 pack。

然后：

```text
Hierarchy
 ↓
Selected Meshlet
 ↓
一个 MeshletWork
```

不再：

```text
Selected Meshlet
 ↓
for triangle in meshlet:
    append RasterWork
```

Meshoptimizer 本身就把 meshlet 定义成 GPU 处理的工作单元，并强调 cluster culling 应在比最终 mesh shading 更粗的频率进行；常见建议也接近 64 vertices / 64～126 triangles 的规模。([网格优化库](https://meshoptimizer.org/))

------

## WebGPU 没 Mesh Shader，怎么做？

这个是最关键的。

不用 Mesh Shader。

我建议做：

# `Meshlet Bucket Raster`

例如按照 triangle 数分：

```text
Bucket 0: <= 32 triangles
Bucket 1: <= 64
Bucket 2: <= 96
Bucket 3: <= 128
```

GPU Work Generator 最终输出：

```text
meshletQueue32
meshletQueue64
meshletQueue96
meshletQueue128
```

然后四次：

```text
drawIndirect
```

例如 128 bucket：

```text
vertexCount   = 128 × 3
instanceCount = visibleMeshletCount
```

Vertex Shader：

```text
instance_index
    ↓
MeshletWork

vertex_index / 3
    ↓
localTriangle

vertex_index % 3
    ↓
corner
```

于是：

```text
一个 drawIndirect
→ N 个 meshlet
→ 每个 meshlet 最多 128 triangle
```

而不是：

```text
N × triangle record
```

WebGPU 本身支持 GPU-buffer 驱动的 `drawIndirect()`，所以这条方案不依赖 mesh/task shaders。([MDN Web Docs](https://developer.mozilla.org/en-US/docs/Web/API/GPURenderPassEncoder/drawIndirect))

------

## 为什么分 Bucket

如果所有 meshlet 都：

```text
draw 128 triangles
```

但某个 meshlet 只有：

```text
36 triangles
```

就浪费很多 vertex invocation。

所以：

```text
32
64
96
128
```

四档已经够了。

尾部无效 triangle：

```text
tri >= meshlet.triangle_count
```

生成 degenerate primitive 即可。

这点浪费和你现在：

```text
24B queue
+
32B queue
+
Exact compute
```

相比，值得交换。

## ExactTriangleFilter 不应该再是所有 Triangle 的必经之路

这是这一刀的第二部分。

我建议变成：

```text
MeshletWork
   │
   ├─ Normal
   │    ↓
   │ Hardware Raster
   │
   └─ Risky
        ↓
      ExactTriangleFilter
        ↓
      special Raster
```

Risky 可以包括：

```text

```

正常 triangle：

> 让硬件 Rasterizer 自己 clip、setup、cull。

Nanite 公开资料反而明确提到它没有做 per-triangle culling；它依赖 cluster 级可见性，并根据三角形大小决定 raster 策略。([实时渲染进展](https://advances.realtimerendering.com/s2021/Karis_Nanite_SIGGRAPH_Advances_2021_final.pdf))

你现在的路径：

```text
Cluster Cull
+
Triangle Exact Cull
+
Hardware Raster
```

对普通大三角形来说有明显“过度管理”的嫌疑。

## 这一步我希望看到的结果

```text
至少下降 25%

下降 > 80%

```

如果实现得对，这一刀很可能是目前最大的单项收益。

# 2. 第二刀：删掉 `MaterialClassDepth + N × Fullscreen Material`

这是第二个我非常建议直接换掉的架构。

你的代码自己已经写得非常清楚：

> ```
> Resolve Surface with one bounded fullscreen draw per active kernel class.
> ```

然后：

```ts
for (
    let kernelClass = 0;
    kernelClass < GPU_MATERIAL_KERNEL_CLASS_COUNT;
    kernelClass++
) {
    ...
    pass.draw(3, 1, 0, 0);
}
```

而前面还先跑：

```text
PackedMaterialClassDepthPass
```

也就是：

```text
Visibility
 ↓
Fullscreen classify depth

 ↓

Kernel 0 Fullscreen
Kernel 1 Fullscreen
Kernel 2 Fullscreen
Kernel 3 Fullscreen
...
```

这是你现在 Surface 后端非常明显的固定成本。

------

## 这件事甚至 Nanite 自己后来也改了

Nanite 早期也采用 Visibility Buffer 后用 material fullscreen pass 做 resolve；公开分析也指出每 material fullscreen pass 在高分辨率下可能成为问题。([Tricky Bits](https://trickybitsblog.github.io/2024/04/20/nanite.html))

到了 UE 5.4，Epic 的 GDC 2024 **Nanite GPU-Driven Materials** 已经转向：

```text
Shading Binning
      ↓
Compute Shading
```

对 pixel/shading work 进行重新分类和压缩，而不是继续依赖原来那套 pixel material pass。([GDC Vault](https://media.gdcvault.com/gdc2024/Slides/GDC%2Bslide%2Bpresentations/Nanite%2BGPU%2BDriven%2BMaterials.pdf))

这和你现在所处阶段非常像。

------

## 我建议 EEngine 做 `Tile-Class Compute Shading`

先不要上 GPU radix sort，那太重。

第一版做：

```text
VisibilityKey
 ↓
ShadeClassifyCS
 ↓

8×8 Tile
检查 64 pixels

 ↓

local bitmask:
Class0?
Class1?
Class2?
...
```

然后输出：

```text
Class0 Tile Queue
Class1 Tile Queue
Class2 Tile Queue
...
```

例如：

```text
Tile A:
Class 1 only

Tile B:
Class 1 + 3

Tile C:
empty
```

最后：

```text
Class1:
dispatchWorkgroupsIndirect()

Class3:
dispatchWorkgroupsIndirect()
```

WebGPU 已经支持 GPU buffer 决定工作量的 `dispatchWorkgroupsIndirect()`。([MDN Web Docs](https://developer.mozilla.org/en-US/docs/Web/API/GPUComputePassEncoder/dispatchWorkgroupsIndirect))

------

## 为什么这特别适合你

因为你现在 Material Resolve 已经没怎么享受 Pixel Shader 的核心优势了。

正常 Fragment Shader：

```text
Rasterizer
 ↓
硬件插值
 ↓
fragment
```

而你现在：

```text
fragment
 ↓
VisibilityKey
 ↓
triangle
 ↓
vertex0/1/2
 ↓
自己算 barycentric
 ↓
自己算 ddx/ddy
```

代码里确实每个 visible pixel 都会重新加载 triangle/vertex，并计算 perspective barycentric，随后读取 3 normal、3 tangent、3 color 和各套 UV。

既然：

> **插值本来就是你自己算的**

那搬去 Compute Shader 的阻力比传统 renderer 小很多。

------

## 第一版甚至不要 Pixel Compaction

可以：

```text
一个 workgroup = 一个 tile
```

里面：

```text
64 threads
```

每个线程对应 pixel。

如果：

```text
pixel.class != currentClass
```

退出。

这样虽然还有少量无效线程，但：

```text
没有 ClassDepth texture
没有 N 次 fullscreen raster
没有 early-z trick
没有 fragment helper lane 约束
```

实现简单。

等证据证明 Shader class divergence 很大，再升级：

```text
Tile Class
↓
Pixel compaction
```

------

## Compute 写现在这些 Surface format 可不可行？

这是一个需要按 adapter feature 做的地方。

2026 WebGPU 已经把更多 texture format 的 storage 用法纳入 `texture-formats-tier1/tier2`；例如 `rg8unorm` 等格式可在 Tier 1 下用于 storage binding。([MDN Web Docs](https://developer.mozilla.org/en-US/docs/Web/API/GPUDevice/createTexture))

因此可以：

```text
Tier1 available
→ 直接 storage texture Surface

否则
→ packed RGBA storage
或 buffer backend
```

不要为了所有浏览器最低公分母把核心架构锁死。


只要 SSE 要求继续细化就继续。

## 我建议引入 `GeometryWorkBudget`

类似：

```text
targetVisibleMeshlets

targetRasterVertices

targetGeometryGpuMs
```

Hierarchy selector：

```text
SSE quality requirement
+
current work budget
```

共同决定。

最终：

```text
Camera 越近

旧：
GPU work 无限上涨

新：

直到达到预算

之后：

```

## 再加 Hysteresis

不能：

```text
Frame N      LOD 3
Frame N+1    LOD 4
Frame N+2    LOD 3
```

而应该：

```text
refine threshold   = 4.0

```

之类的滞回。

这条对平均 FPS 不一定是收益最大的，

但它会非常有效地解决：

> **“某些视角突然 40 FPS”**

这种 worst-case。

# 8. 第八刀：Full 模式再做 Effects Pipeline 瘦身

前面几刀结束后再做这个。

因为现在如果 Geometry + Material 本身已经浪费很多，先优化 Bloom 0.1ms 没意义。


# 三、Compute Material 后，还有一个很大的后续机会：软件 VRS

这不是第一阶段，但值得提前把架构留出来。

一旦 Material 变成：

```text
Compute Shading
```

Visibility 和 Shading Rate 就真正解耦了。

例如平坦区域：

```text
2×2 pixels

只 shade 1 次
```

边缘：

```text
每 pixel shade
```

Epic 的 Nanite GPU-driven Materials 也在 compute shading 基础上进一步处理 coarse shading rate / 2×2 quad 等问题。([GDC Vault](https://media.gdcvault.com/gdc2024/Slides/GDC%2Bslide%2Bpresentations/Nanite%2BGPU%2BDriven%2BMaterials.pdf))

这也是 Visibility Buffer 真正强于普通 Forward 的地方之一：

> **Visibility resolution 可以是 1080p，但 shading resolution 不必永远是 1080p。**

早期 decoupled/adaptive shading 研究也正是利用“visibility sampling rate ≠ shading rate”减少昂贵 shading。([NVIDIA](https://research.nvidia.com/publication/decoupled-sampling-graphics-pipelines))

这会是 EEngine 后面真正能体现架构优势的地方。

# 四、还有一个我认为很漂亮的优化：TriangleSetup 不应该被删除，而应该升级定位

你现在已经有：

```text
TriangleSetupRecord
= 40 B
```

缓存：

```text
qCenter
dqDx
dqDy
```

并且只对覆盖超过阈值的三角形生成。

这个思想是对的。

但是现在它夹在：

```text
ExactTriangleFilter
```

体系里。

我以后会把它重新定义成：

# `LargeTriangle Shading Cache`

即：

```text
Triangle screen coverage > 32 / 64 pixels
        ↓
值得花一次 setup 成本
        ↓
几十/几百个 pixel 重用
```

小 triangle：

```text
直接算
```

大 triangle：

```text

```

这就是：

> **按摊销收益决定 cache，而不是所有 triangle cache。**

可以继续保留。

# 七、这套新架构为什么更适合 WebGPU

我不会照抄 Nanite。

Nanite 能用很多更底层的 native GPU 能力，而 WebGPU 要考虑 portability。

但我们现在需要的关键能力：

```text
drawIndirect
dispatchWorkgroupsIndirect
storage buffers
storage textures
compute
workgroup atomics
normal raster pipeline
```

WebGPU 都已经提供。([MDN Web Docs](https://developer.mozilla.org/en-US/docs/Web/API/GPURenderPassEncoder/drawIndirect))

甚至 2026 的 WebGPU 已经在推进/暴露：

```text
primitive-index
更多 texture format tiers
multi-draw CTS
```

但我不会让 V2 必须依赖这些可选/较新能力。([GPU Web](https://gpuweb.github.io/cts/standalone/?compatibility=1&q=webgpu%3Aapi%2Cvalidation%2Cencoding%2Ccmds%2Crender%2Cindirect_multi_draw%3Abuffers%2Cdevice_mismatch%3A*&runnow=1))

所以我设计的：

```text
Meshlet Bucket Raster
+
Tile Compute Shading
```

是刻意为 WebGPU 限制设计的。

# 九、我甚至会给这次性能重构定明确的验收目标

不是：

> “代码看起来像 Nanite 了。”

而是：

| Migration           | 必须看到的证据                                              |
| ------------------- | ----------------------------------------------------------- |
| Meshlet Work        | Geometry phase **≥20% 改善**，queue bytes 大幅下降          |
| Selective Exact     | normal scene exact-triangle work **下降 ≥90%**              |
| Compute Material    | Material Resolve **≥20～25% 改善**才考虑替换                |
| Canonical Vertex    | Resolve/Visibility 至少有可测 improvement，asset bytes 下降 |
| Surface V2          | full GPU frame **≥10% 改善**才值得 ABI 迁移                 |
| Adaptive LOD        | near-camera / far-camera GPU cost 比例明显收敛              |
| Small Geometry path | Dungeon / 中型场景必须显著缩小与 three.js 的差距            |

特别是：

> **没有 ≥10% 总体收益的“大架构迁移”，原则上就不应该为了漂亮而合进去。**

# 十、第一步甚至不是写 Meshlet V2，而是先修真正的性能测量

这个虽然不提升 FPS，但一定先做。

你现在 profiler 有：

```text
gpu.passSumMs
```

它是：

```text
sum(all timestamp segments)
```

我建议增加一个真正独立的：

```text
gpu.frameEnvelopeMs
```

定义：

```text
第一个 OEngine GPU command 前
        ↓ timestamp

整个 frame GPU commands

最后一个 OEngine GPU command 后
        ↓ timestamp
```

得到真正的：

```text
GPU frame envelope
```

以后所有 migration 都看：

```text
gpu.frameEnvelopeMs

+
Geometry
Material
Lighting
Effects
```

而不是继续看容易误读的：

```text
gpuFrameMs
```

否则你很容易再次遇到：

```text
Profiler 好像 1.5 ms
```

但：

```text
Task Manager 99%
FPS 47
```

这种完全对不上的情况。

## 我对潜在收益的判断

我不会承诺：

```text
47 FPS
→
120 FPS
```

这种没有证据的数字。

但从当前代码结构看，如果 profiling 最终确认我们现在看到的这几个热点，我认为：

> **47 FPS → 稳定跨过 60 FPS 是一个完全值得以此为目标进行重构的幅度，而不是只能期待 47 → 50。**

因为我们讨论的不是：

```text
一个 shader 少 5 条 ALU
```

而是在尝试直接删除：

```text
逐 Triangle queue expansion

大部分 ExactTriangleFilter

第二份逐 Triangle queue

MaterialClassDepth fullscreen

N 个 Material fullscreen raster

通用 vertex decode 热路径

一部分 26B/pixel 中间 Surface traffic
```

这些都是**结构性工作量**。

还有一点：你截图里 GTX 1650 Ti 已经到约 90°C，这可能让不同轮测试受 GPU boost/热状态影响，所以正式 A/B 时需要把温度/功耗状态也尽量控制一致。但这不会推翻核心判断——**99% GPU utilization 已经足以说明当前首先应该砍 GPU workload。**

------

我现在最推荐的是，**不要马上叫 Codex 一口气实现这五个 Phase**。下一步应该先把 **`Performance Pipeline V2` 做成正式架构设计**，其中第一阶段把 `Meshlet Bucket Raster` 的 ABI、VisibilityKey V2 位布局、四个 Raster Bucket、Normal/Risky 路径以及如何替换现有 `RasterWork → ExactRasterWork` 画到源码级别；第二阶段再设计 Compute Material Binning。

这两个设计定下来以后，基本就确定了 EEngine 下一轮真正以性能为目标的核心渲染架构。
