是，而且这一层我认为比单独优化 `SSRPass`、`TAAPass` 更重要。

重新审视你现在的代码、当前 2026 WebGPU 能力，再结合 Nanite GPU-Driven Materials、Filament、FidelityFX、Unreal TSR/VSM 和近几年 visibility-buffer / deferred compute shading 研究之后，我会进一步修改前面的方案：

> **EEngine 下一轮不应该只是“Geometry Pipeline V2 + Asset Pipeline V2”，还应该同时做一次 `Rendering Architecture V2`。**
>
> 目标不是把当前 GTAO、SSR、TAA 各自写快一点，而是重新决定：
>
> **什么阶段需要存在、什么数据值得落显存、什么效果应该低分辨率、什么结果应该时域重建、哪些 Pass 应该融合、哪些中间纹理根本不应该产生。**

而且我现在不建议你从当前架构退回传统 Deferred，也不建议全部改成 Forward+。

我认为最适合 EEngine 的路线是：

# Visibility-Driven Compute Hybrid Renderer

也就是：

```text
GPU-driven Geometry
        ↓
Visibility Buffer
        ↓
Compute Material Binning
        ↓
Material + Lighting Compute Shading
        ↓
Compact SurfaceLite + HDR
        ↓
Screen-space / GI / Reflection
        ↓
Forward Transparency
        ↓
Temporal Reconstruction
        ↓
Fused HDR Post
```

它本质上是：

> **Visibility Buffer + Compute Shading + Clustered Lighting + Temporal Reconstruction 的混合管线。**

这比“延迟还是前向二选一”更符合你这个引擎。

# 二、问题是：你现在虽然用了 Visibility Buffer，最后又造出了一个很重的 GBuffer

当前 `GpuSurfaceAbi`：

| Attachment | 格式         | B/pixel        |
| ---------- | ------------ | -------------- |
| PBR        | `rg8unorm`   | 2              |
| Normal     | `rgba16uint` | 8              |
| Albedo/AO  | `rgba8unorm` | 4              |
| Emissive   | `r32uint`    | 4              |
| Velocity   | `rg16float`  | 4              |
| Metadata   | `r32uint`    | 4              |
| **合计**   |              | **26 B/pixel** |

1920×1080：

```text
2,073,600 × 26 B
≈ 51.4 MiB
```

也就是说 Material Resolve：

```text
每一帧
至少写约 51 MiB Surface
```

然后 Lighting 又读取：

```text
PBR
Normal
Albedo
Emissive
Metadata
Depth
```

你的 `LightingFeature` 当前就是这样接入 `LightingPass` 的。

光是：

```text

+
Lighting 再读 Surface
```

理论数据量下限已经接近：

```text
~103 MiB/frame
```

60 FPS：

```text
≈ 6 GiB/s
```

还完全没有算：

```text
VisibilityKey
Depth
HDR
Texture fetch
SSR
AO
Temporal
Bloom
Post
```

而 Filament 当年放弃传统 Deferred 的一个核心原因，就是 160～192 bit/pixel GBuffer 带来的带宽成本；你的 Surface 当前是：

```text
26 × 8
=
208 bit/pixel
```

当然两边的数据语义并不完全相同，但已经说明你当前 Surface 确实属于一个很重的中间层。([Google GitHub](https://google.github.io/filament/main/filament.html))

2024 年 SIGGRAPH Real-Time Rendering 甚至专门有：

> **Variable Rate Shading with Visibility Buffer Rendering**

强调的正是：

> Visibility resolution 和实际 shading rate 可以解耦。

([实时渲染进展](https://www.advances.realtimerendering.com/s2024/index.html))

所以：

> **Visibility Buffer 不应该删。**
>
> 应该删的是 Visibility Buffer 后面那个“重新膨胀出来的大 Surface Deferred Pipeline”。

```text
dynamic page cache
```

Epic VSM 当前就是以 128×128 page 为单位按需分配，并高度依赖跨帧 cache；官方也特别强调 static/dynamic 分离以避免动态物体导致昂贵静态区域重画。([Epic Games Developers](https://dev.epicgames.com/documentation/unreal-engine/virtual-shadow-maps-in-unreal-engine))

# 二十五、这跟你新 Asset/Geometry 架构还能结合

比如 Shadow page 需要 Geometry：

```text
Shadow Page
   ↓
GPU Work Generator
   ↓
Meshlet Raster Work
```

而且 Shadow 自己有：

```text
更粗的 LOD budget
```

不应该：

```text
主相机看到 1-pixel triangle
Shadow 也全部画
```

甚至：

```text
far shadow
→ coarse parent cluster
```

这会是非常明显的组合收益。

# 二十六、再加一个便宜但质量很高的效果：Contact Shadows

VSM/CSM 解决大结构。

然后：

```text
DepthHierarchy
+
light direction
```

做短距离：

```text
screen-space contact shadow ray
```

只覆盖：

```text
脚底
接触面
细枝
小结构
```

这样 Shadow Map 本身不用追求无限 resolution。

Epic 的 VSM 文档也明确把 screen-space Contact Shadows 作为远/小变形物体的一种性能替代。([Epic Games Developers](https://dev.epicgames.com/documentation/unreal-engine/virtual-shadow-maps-in-unreal-engine))

# 二十七、GI：当前架构接口值得保留，但算法可以换代

你现在已经有：

```text
Lightmap
→ Probe Volume
→ IBL
```

provider abstraction。

这个接口我不会拆。

算法上我会改成：

```text
Static
→ compressed sparse lightmap / bricks

Dynamic
→ sparse radiance probe / SVLM / DDGI-style cache

Local correction
→ optional screen-space diffuse GI

Fallback
→ IBL
```

------

真正适合 WebGPU 的高质量 GI，我现在更看好：

```text
Sparse Probe / Radiance Cache
```

而不是把核心引擎押到 ReSTIR GI。

因为截至当前 WebGPU Feature 集仍没有标准硬件 Ray Query/RT pipeline。([GPU Web](https://gpuweb.github.io/types/types/GPUFeatureName.html))

所以 ReSTIR GI 如果没有硬件 visibility ray：

```text
每个 candidate
→ software BVH
```

代价很高。

------

动态 probe 路线已经有大量 production evidence；比如 *Scaling Probe-Based Real-Time Dynamic Global Illumination for Production* 就是这类路径的重要代表。你的现有 Probe Volume/SVLM 演进方向其实比“突然改成 path tracing GI”更现实。

------

# 二十八、但可以增加 Screen-Space GI

它不应该替代 Probe GI。

而是：

```text
Probe GI
=
稳定低频 baseline

SSGI
=
当前画面局部高频 correction
```

类似：

```text
IBL
+
Probe GI
+
Screen-space correction
```

SSR 也是同样思想：

```text
IBL baseline
+
SSR correction
```

你当前 ReflectionService 已经采用了“SSR miss 不覆盖 IBL baseline”的思想。

这个设计我建议继续坚持。

# 二十九、一个很重要但很便宜的新效果：Specular Anti-Aliasing

随着你：

```text
meshlet
dense geometry
normal maps
高光
```

越来越复杂，

会出现：

```text
specular sparkle
normal shimmer
```

单纯 TAA 并不能完美解决。

因此 Material Shading 中应该增加：

```text
normal variance
+
geometric footprint
      ↓
roughness adjustment
```

这种 specular AA。

它对画质提升很明显，运行成本通常远低于：

```text
多采样
或者让 TAA 强行糊掉
```

我会把它当成 High Profile 的常开效果。

# 三十九、应该有真正的 `FrameBudgetController`

例如目标：

```text
GPU = 16.67 ms
```

分：

```text
Geometry          3.0 ms

Material/Lighting 4.0 ms

Shadow            2.0 ms

ScreenSpace       2.0 ms

Temporal/Post     2.5 ms

Headroom          3.17 ms
```

它不是每帧一定精确。

而是控制工作量：

```text
Geometry:
max refined meshlets

Shadow:
max dirty pages

SSR:
max ray tiles

GI:
max probe updates

Volumetric:
max froxels

Streaming:
max upload bytes
```

------

很有意思的是，2026 SIGGRAPH Real-Time Rendering 课程里也出现了类似的 GPU-driven frame-level scheduler：保持总 ray count 固定，在空间上重新分配工作，从而避免 camera motion 或动态事件导致 GPU cost spike。这个思想完全可以扩展到你这种非 HWRT 的 SSR/SSGI/Shadow/Probe work queue。([实时渲染进展](https://www.advances.realtimerendering.com/s2026/index.html))

这个设计比：

```text
每个 Feature 独立 quality setting
```

前卫得多。

# 四十四、如果让我现在给下一轮“大重构”定顺序

我会按下面这个顺序，而不是先单独重写 TAA：

| Phase   | 内容                                         | 原因                              |
| ------- | -------------------------------------------- | --------------------------------- |
| **P0**  | Performance Truth + GPU Frame Envelope       | 先建立可信基线                    |
| **P1**  | OAsset/Cooker + compact geometry/texture     | 后续 GPU ABI 基础                 |
| **P2**  | Geometry Frontend V2                         | 解决 triangle work amplification  |
| **P3**  | VisibilityKey V2 + Compute Material Binning  | 重构 shading 核心                 |
| **P4**  | SurfaceLite + Material/Lighting fusion       | 大幅降低 MRT/带宽                 |
| **P5**  | Shared Depth/Color Pyramid                   | 给所有 screen effect 提供共同基础 |
| **P6**  | GTAO / SSSR / Shadow V2                      | 重写昂贵空间效果                  |
| **P7**  | Temporal Reconstruction V2                   | 把动态分辨率变成正式策略          |
| **P8**  | Bloom/Exposure/Post Fusion                   | 收尾 full-screen 带宽             |
| **P9**  | Sparse GI / VSM / Volumetrics / software VRS | 高级游戏特性                      |
| **P10** | Global Frame Budget Controller               | 全系统稳定 60/120 FPS             |

------

这里最重要的一点：

> **P6/P7 的 AO、SSR、TAA 重构应该在 P3/P4 的新 Surface 合同确定以后做。**

否则你现在先花大量时间把：

```text

```

```text

```

过两个月 Surface V2 一改：

```text

```

会非常浪费。

所以我现在不建议马上开始“优化 TAA shader”。

应该先把：

# `EEngine Performance + Rendering Architecture V2`

这个总架构定下来。

然后 Asset、Geometry、Shading、Effect 都围绕同一套：

```text

```

去设计。

这会比单独把现在的 Deferred 管线修得越来越复杂，更有长期价值。
