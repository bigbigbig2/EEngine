有，而且我现在会把方向进一步收紧：

> **只做方案 B：Visibility Buffer → GPU Shading Bin → 稀疏 Compute Shading。**

而且你后面不需要“从论文开始自己手搓整个算法”。我把 GitHub 上能真正拿来当移植参考的项目翻了一遍，已经可以拼出一套相当完整的实现路线。

# 1. 第一参考：NaniteMaterialCulling —— 和你现在的问题几乎一模一样

这是这次找到最重要的源码。

UE Nanite：

```text
Engine/Shaders/Private/Nanite/NaniteMaterialCulling.usf
```

源码里直接有：

```hlsl
groupshared uint TileMaterialBins[...];

[numthreads(16, 16, 1)]
void ClassifyMaterials(...)
```

。

它做的事情和我们想给 EEngine 做的方案 B 高度一致：

```text
ShadingMask / Visibility
        ↓
64 × 64 Macro Tile
        ↓
扫描当前 Tile 出现了哪些 ShadingBin
        ↓
groupshared Material Bin Bitset
        ↓
MaterialTileRemap
        ↓
MaterialIndirectArgs
        ↓
每个 Material/Shading Bin 独立 Dispatch
```

最关键的是，Epic 源码里甚至直接写了你现在碰到的问题：

```cpp
// Scalarize to get rid of duplicate updates
// that would otherwise result in atomic contention
```

。

也就是说：

> **Nanite 本身就在专门避免“同一个 wave 的一堆 pixel 对同一个 material counter 做 atomic”的竞争。**

它不是：

```text
pixel
pixel
pixel
pixel
 └────→ global atomic
```

而是先：

```text
Wave
 ↓
找出唯一 Material/ShadingBin
 ↓
只允许代表 lane 更新
 ↓
groupshared bitset
```

------

# 2. Nanite 的完整分类逻辑非常值得直接移植算法

它不是简单统计 pixel 数。

实际是：

```text
InitializeMaterials
        ↓
ClassifyMaterials
        ↓
FinalizeMaterials
        ↓
Indirect Material Shading
```

### Initialize

每个 material/bin：

```text
IndirectArgs = 0
TileRemap = 0
```

。

### Classify

一个 macro tile 中：

```text
Visibility/ShadingMask
        ↓
找 ShadingBin
        ↓
wave 去重
        ↓
groupshared bitset
```

然后：

```hlsl
InterlockedAdd(
    MaterialIndirectArgs[
        MaterialSlot * stride + ...
    ],
    1
);
```

注意这里 atomic 的粒度已经不是：

```text
pixel
```

而是：

```text
当前 material 是否出现在这个 tile
```

。

这就是质变。

------

# 3. 然后建立 `MaterialTileRemap`

Nanite：

```hlsl
InterlockedOr(
    MaterialTileRemap[...],
    TileBit
);
```

本质上形成：

```text
Material A
  ├ Tile 2
  ├ Tile 7
  ├ Tile 13
  └ Tile 61

Material B
  ├ Tile 4
  └ Tile 19
```

。

而不是建立：

```text
Material A:
Pixel(10,20)
Pixel(11,20)
Pixel(12,20)
...
```

这一点我现在反而建议 **EEngine 也采用 Nanite 的 Tile Remap，而不是第一版就建立全局 PixelQueue**。

因为全屏 1080p 如果每个 pixel 写：

```text
x : u32
y : u32
```

又是：

```text
8 bytes × 2,000,000
≈ 16 MB/frame
```

额外 bandwidth。

Nanite-style：

```text
Sparse Tile Remap
```

会便宜很多。

# 4. 所以我现在会修正之前方案 B 的具体实现

之前我说：

```text
Visibility
→ Compact Pixel Queue
→ Shading Bins
```

现在查完实际生产级实现后，我认为第一版应该改成：

```text

        ↓

        ↓

        ↓
Indirect Dispatch
        ↓
```

这基本就是我要推荐给 EEngine 的长期架构。

因为目前 GitHub 上我没有找到一个同时满足：

```text
WebGPU WGSL
+
Meshlet
+
Visibility Buffer
+
Nanite-style Material Shading Bins
+
2026 subgroup scheduler
+
成熟 production quality
```

的单一项目。

但现在已经有比这更现实的方案：

```text
                 Nanite
                    │
           Classifier Architecture
                    │
                    ▼
              EEngine Scheduler
                    ▲
                    │
       PlayCanvas subgroup primitives
                    │
           count / scan / scatter

                    +
                 
                  Kooch
                    │
      WGSL Visibility/Material Resolve

                    +

               The Forge / Bevy
                    │
       reconstruction cross-reference
```

**这已经不是“自己写一个新算法”了，而是一次有明确上游实现依据的架构移植。**

其中我会把 **Nanite `NaniteMaterialCulling.usf` + PlayCanvas `onesweep-binning.js`** 定为这次重构最核心的两个参考源：前者决定 **Shading Bin 的数据结构和调度模型**，后者决定 **在最新 WGSL/WebGPU 下怎么把 wave-level count/prefix/scatter 写得足够激进**。然后用 Kooch 解决 compute material/surface reconstruction 的 WGSL 落地。这样最适合你当前 EEngine。
