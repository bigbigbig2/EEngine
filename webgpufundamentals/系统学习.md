# WebGPU 基础

> 原文：[WebGPU 基础](https://webgpufundamentals.org/webgpu/lessons/zh_cn/webgpu-fundamentals.html)  
> 本地示例：[index.html](./index.html)

WebGPU 的核心能力只有两类：

1. **渲染**：把点、线、三角形绘制到纹理上，Canvas 显示的也是一张 GPU 纹理。
2. **计算**：通过 Compute Shader 对 Buffer、Texture 中的数据进行并行处理。

WebGPU 与 WebGL 的主要区别不在于“能否画三角形”，而在于组织 GPU 工作的方式。WebGL 更像一个全局状态机；WebGPU 则显式创建资源、Pipeline 和绑定关系，先录制命令，再统一提交给 GPU。

---

## 一、WebGPU 的核心对象模型

```text
navigator.gpu
    └── requestAdapter()
            ↓
        GPUAdapter
            └── requestDevice()
                    ↓
                GPUDevice
                  ├── Shader Module
                  ├── Render / Compute Pipeline
                  ├── Buffer / Texture
                  ├── Bind Group
                  ├── Command Encoder
                  └── GPUQueue
```

Canvas 相关对象：

```text
canvas
  └── getContext("webgpu")
          ↓
    GPUCanvasContext
          └── getCurrentTexture()
                  ↓
              GPUTexture
                  └── GPUTextureView
```

| 对象 | 作用 |
| --- | --- |
| `GPUAdapter` | 表示浏览器选择的 GPU/驱动实现及其能力 |
| `GPUDevice` | 创建 GPU 资源、Pipeline 和命令编码器 |
| `GPUQueue` | 上传数据并提交 Command Buffer |
| `GPUCanvasContext` | 管理 Canvas 当前用于显示的 Texture |
| `GPUShaderModule` | 保存 WGSL 着色器程序 |
| `GPURenderPipeline` | 描述完整的渲染方式 |
| `GPUComputePipeline` | 描述 Compute Shader 的计算方式 |
| `GPUCommandEncoder` | 录制渲染、计算和资源复制命令 |
| `GPUCommandBuffer` | 已经录制完成、可以提交的 GPU 命令集合 |

初始化：

```js
const adapter = await navigator.gpu?.requestAdapter();
const device = await adapter?.requestDevice();

if (!device) {
  throw new Error('当前环境不支持 WebGPU');
}
```

可以这样记：

```text
Adapter：浏览器找到了什么 GPU 能力。
Device：程序实际操作的逻辑 GPU 设备。
Queue：CPU 把数据和命令交给 GPU 的入口。
```

几乎所有 GPU 资源都由 `device` 创建；数据上传和命令提交通过 `device.queue` 完成：

```js
device.queue.writeBuffer(buffer, 0, data);
device.queue.submit([commandBuffer]);
```

`queue.submit()` 只表示命令已经进入 GPU 队列，不表示 GPU 已经执行完成。CPU 和 GPU 通常异步工作。

## 二、绘制第一个三角形

以下是使用顶点着色器和片段着色器绘制三角形的 WebGPU 设置简图

![img](https://webgpufundamentals.org/webgpu/lessons/resources/webgpu-draw-diagram.svg)

完整流程：

```text
取得 Device
    ↓
配置 Canvas Context
    ↓
创建 Vertex / Fragment Shader
    ↓
创建 Render Pipeline
    ↓
取得 Canvas 当前 Texture
    ↓
录制 Render Pass
    ↓
draw(3)
    ↓
提交 Command Buffer
```

**配置 Canvas**

```js
const canvas = document.querySelector('canvas');
const context = canvas.getContext('webgpu');
const presentationFormat =
  navigator.gpu.getPreferredCanvasFormat();

context.configure({
  device,
  format: presentationFormat,
});
```

`GPUCanvasContext` 为 Canvas 提供当前可显示的 GPU Texture。

`presentationFormat` 同时用于 Canvas 配置和 Pipeline 的颜色目标：

```js
fragment: {
  module,
  targets: [{ format: presentationFormat }],
}
```

两者必须兼容：

```js
Canvas Texture Format
        =
Fragment Target Format
```

**顶点着色器**

```js
@vertex fn vs(
  @builtin(vertex_index) vertexIndex: u32
) -> @builtin(position) vec4f {
  let positions = array(
    vec2f( 0.0,  0.5),
    vec2f(-0.5, -0.5),
    vec2f( 0.5, -0.5)
  );

  return vec4f(positions[vertexIndex], 0.0, 1.0);
}
```

`@builtin(vertex_index)` 是 GPU 提供的顶点编号。调用 `draw(3)` 时，Vertex Shader 执行三次，本例的 `vertexIndex` 依次为 0、1、2，因此会取出三个不同的位置。

这个例子没有 Vertex Buffer，顶点位置直接写在 Shader 中，只是为了展示最小流程。实际模型通常从 Vertex Buffer 读取顶点。

返回值 `@builtin(position) vec4f` 是裁剪空间坐标 `(x, y, z, w)`：

```text
          (0.0, 0.5)
               ▲
              / \
             /   \
            /     \
(-0.5,-0.5) ───── (0.5,-0.5)
```

在这个简单例子中，可以把 X、Y 范围理解为 `-1` 到 `1`。`z = 0` 位于有效深度范围，`w = 1` 表示透视除法后 X、Y 不变。

**片元着色器**

```wgsl
@fragment fn fs() -> @location(0) vec4f {
  return vec4f(1.0, 0.0, 0.0, 1.0);
}
```

`@location(0)` 表示输出到 Pipeline 的第 0 个颜色目标，即 `fragment.targets[0]`。

返回值是 RGBA：红色为 1、绿色和蓝色为 0、Alpha 为 1，所以所有片元都输出纯红色。

**Shader Module 与 Pipeline**

```js
const module = device.createShaderModule({
  code: shaderCode,
});

const pipeline = device.createRenderPipeline({
  layout: 'auto',
  vertex: {
    module,
    entryPoint: 'vs',
  },
  fragment: {
    module,
    entryPoint: 'fs',
    targets: [{ format: presentationFormat }],
  },
});
```

Shader Module 保存 WGSL；Render Pipeline 把 Shader 和渲染状态组合起来。

Pipeline 不只包含 Shader，还会描述：

- 颜色输出格式；
- 图元拓扑；
- Vertex Buffer 布局；
- 深度测试；
- 混合方式；
- Shader 资源布局。

`layout: 'auto'` 表示根据 Shader 自动推断 Bind Group Layout。简单示例很方便；需要跨 Pipeline 共享 Bind Group 时通常使用显式 Layout。

默认图元拓扑是 `triangle-list`，因此每三个顶点组成一个三角形。

**Render Pass**

```js
const renderPassDescriptor = {
  colorAttachments: [{
    view: undefined,
    clearValue: [0.3, 0.3, 0.3, 1.0],
    loadOp: 'clear',
    storeOp: 'store',
  }],
};
```

Pipeline 描述“怎么画”，Render Pass 描述“这一次画到哪里”。

- `view`：渲染目标的 Texture View；
- `clearValue`：开始绘制前的清屏颜色；
- `loadOp: 'clear'`：开始时清空旧内容；
- `storeOp: 'store'`：结束时保存结果。

Canvas 当前纹理由浏览器轮换管理，因此每次渲染都重新获取：

```js
renderPassDescriptor.colorAttachments[0].view =
  context.getCurrentTexture().createView();
```

**编码和提交命令**

```js
const encoder = device.createCommandEncoder();

const pass = encoder.beginRenderPass(renderPassDescriptor);
pass.setPipeline(pipeline);
pass.draw(3);
pass.end();

const commandBuffer = encoder.finish();
device.queue.submit([commandBuffer]);
```

WebGPU 先录制命令，再统一提交：

```text
Command Encoder
    ↓
Render Pass
    ↓
setPipeline
    ↓
draw
    ↓
pass.end
    ↓
encoder.finish
    ↓
Command Buffer
    ↓
queue.submit
```

`draw(3)` 相当于：

```js
pass.draw(
  3, // vertexCount
  1, // instanceCount
  0, // firstVertex
  0, // firstInstance
);
```

它表示三个顶点调用，不是三个三角形。默认 `triangle-list` 使用这三个顶点组成一个三角形。

随后 GPU 会：

1. 执行三次 Vertex Shader，得到三个顶点位置；
2. 把三个顶点组装成三角形；
3. 光栅化出三角形覆盖的片元；
4. 对每个片元执行 Fragment Shader；
5. 把红色写入 Canvas Texture。

## 三、在 GPU 上进行计算

本章的 Compute 示例把 `[1, 3, 5]` 每个元素乘以 2，得到 `[2, 6, 10]`：

```text
Float32Array
    ↓ queue.writeBuffer
workBuffer
    ↓ Compute Shader
workBuffer
    ↓ copyBufferToBuffer
resultBuffer
    ↓ mapAsync
CPU 读取结果
```

**Compute Shader**

```ts
@group(0) @binding(0)
var<storage, read_write> data: array<f32>;

@compute @workgroup_size(1)
fn computeSomething(
  @builtin(global_invocation_id) id: vec3u
) {
  let i = id.x;
  data[i] = data[i] * 2.0;
}
```

`var<storage, read_write>` 表示 `data` 来自可读写的 Storage Buffer。

`@group(0) @binding(0)` 定义资源在 Shader 接口中的位置：

```text
Bind Group 0
    └── Binding 0
            └── data
```

`@workgroup_size(1)` 表示每个 Workgroup 只有一个 Invocation。

调用：

```js
pass.dispatchWorkgroups(3);
```

时，本例的 `global_invocation_id.x` 分别为 0、1、2，三个调用处理三个不同元素。

GPU 并行计算的基础模式：

```text
所有调用执行相同代码
        +
每个调用拥有不同 ID
        =
不同调用处理不同数据
```

**Buffer**

```js
const input = new Float32Array([1, 3, 5]);

const workBuffer = device.createBuffer({
  size: input.byteLength,
  usage:
    GPUBufferUsage.STORAGE |
    GPUBufferUsage.COPY_SRC |
    GPUBufferUsage.COPY_DST,
});

device.queue.writeBuffer(workBuffer, 0, input);
```

`Float32Array` 每个元素占 4 字节，所以这里 `input.byteLength` 为 12。Buffer 的 `size` 使用字节数。

Usage Flags 声明 Buffer 的用途：

| Usage | 作用 |
| --- | --- |
| `STORAGE` | Compute Shader 读写 |
| `COPY_DST` | 接收 CPU 上传的数据 |
| `COPY_SRC` | 把计算结果复制出去 |

用于 CPU 回读的 Buffer：

```js
const resultBuffer = device.createBuffer({
  size: input.byteLength,
  usage:
    GPUBufferUsage.MAP_READ |
    GPUBufferUsage.COPY_DST,
});
```

`workBuffer` 负责 GPU 计算，`resultBuffer` 负责 CPU 回读：

```text
GPU 工作 Buffer
        ↓ copy
CPU 可映射的 Result Buffer
```

**Bind Group**

```js
const bindGroup = device.createBindGroup({
  layout: pipeline.getBindGroupLayout(0),
  entries: [{
    binding: 0,
    resource: workBuffer,
  }],
});
```

Bind Group 把实际的 `workBuffer` 接到 Shader 的 `@group(0) @binding(0)`。它不是数据本身，而是 Shader 接口和实际 GPU 资源之间的绑定关系。

**计算、复制和回读**

```js
const encoder = device.createCommandEncoder();

const pass = encoder.beginComputePass();
pass.setPipeline(pipeline);
pass.setBindGroup(0, bindGroup);
pass.dispatchWorkgroups(input.length);
pass.end();

encoder.copyBufferToBuffer(
  workBuffer,
  0,
  resultBuffer,
  0,
  resultBuffer.size,
);

device.queue.submit([encoder.finish()]);
```

输入长度为 3，`@workgroup_size(1)`，因此共有三次 Compute Shader 调用。

复制命令排在 Compute Pass 后面，所以 GPU 会先计算，再把结果复制到 `resultBuffer`。

CPU 读取结果：

```js
await resultBuffer.mapAsync(GPUMapMode.READ);

const result = new Float32Array(
  resultBuffer.getMappedRange().slice()
);

resultBuffer.unmap();
```

`mapAsync()` 必须等待，因为 GPU 计算和复制是异步的。

`getMappedRange()` 返回映射内存。映射只在 Buffer 保持 mapped 时有效，所以先用 `slice()` 复制数据，再调用 `unmap()`。

## 四、Canvas 尺寸适配

Canvas 有两套尺寸：

```text
CSS width / height
    控制页面中显示多大

canvas.width / canvas.height
    控制内部实际有多少渲染像素
```

`<canvas>` 默认内部尺寸是 300×150。如果只用 CSS 把它放大，浏览器只是拉伸原有像素，边缘会模糊。

因此需要同步 Canvas 的内部尺寸：

```js
const observer = new ResizeObserver((entries) => {
  for (const entry of entries) {
    const canvas = entry.target;
    const width = entry.contentBoxSize[0].inlineSize;
    const height = entry.contentBoxSize[0].blockSize;

    canvas.width = Math.max(
      1,
      Math.min(width, device.limits.maxTextureDimension2D),
    );

    canvas.height = Math.max(
      1,
      Math.min(height, device.limits.maxTextureDimension2D),
    );
  }

  render();
});

observer.observe(canvas);
```

尺寸要限制在：

```text
1
≤ canvas width / height
≤ device.limits.maxTextureDimension2D
```

最小值避免零尺寸渲染目标；最大值避免超过设备支持的二维纹理尺寸。

尺寸变化后需要重新 `render()`。下一次 `context.getCurrentTexture()` 会提供与新 Canvas 尺寸匹配的 Texture，因此不用重新创建 Pipeline。

本章只做基础尺寸处理。高 DPI、`devicePixelRatio` 和 `devicePixelContentBoxSize` 属于更完整的 Canvas Resize 主题。

## 五、和 WebGL 对照：同样画三角形，组织方式不同

WebGL 和 WebGPU 最终都调用顶点着色器、光栅化三角形并调用片元着色器。差别主要在 JavaScript 如何组织状态和提交工作：

| 环节 | WebGL 2 | WebGPU |
| --- | --- | --- |
| 获取入口 | `canvas.getContext("webgl2")` | `requestAdapter → requestDevice`，再配置 `GPUCanvasContext` |
| 着色器语言 | GLSL ES | WGSL |
| 组合 Shader | 编译 Shader，再链接成 `WebGLProgram` | 创建 `GPUShaderModule`，再创建 `GPURenderPipeline` |
| 顶点、深度、混合等状态 | 通过一系列 `gl.*` 调用修改上下文状态 | 大部分固定进 RenderPipeline |
| 当前显示目标 | 默认 Framebuffer | `getCurrentTexture().createView()` |
| 发出绘制 | 设置当前状态后调用 `gl.drawArrays` | 在 Render Pass 中编码 `setPipeline/draw` |
| 提交方式 | API 调用进入 WebGL/驱动命令流 | `encoder.finish()` 后显式 `queue.submit()` |
| 通用 GPU 计算 | WebGL 2 没有 Compute Shader | ComputePipeline + `dispatchWorkgroups` |

最容易产生误解的是“命令提交”。WebGL 的 `drawArrays` 也不代表 CPU 会停下来等待 GPU 画完，但它依赖当前 WebGL 状态；WebGPU 则把要执行的状态和命令先明确记录进 CommandBuffer，再统一提交。

同一个三角形的大致对应关系：

```text
WebGL：
useProgram → bind/enable state → drawArrays

WebGPU：
beginRenderPass → setPipeline → setBindGroup/setVertexBuffer → draw
               → end → finish → queue.submit
```

因此，WebGPU 不是改变了“GPU 如何画三角形”，而是让资源用途、Shader 接口、渲染状态和命令边界更显式，也让浏览器能在提交前完成更多验证。

本章核心理解：

渲染和计算遵循同一个 WebGPU 结构：

| 阶段 | 渲染 | 计算 |
| --- | --- | --- |
| Shader | Vertex + Fragment | Compute |
| Pipeline | Render Pipeline | Compute Pipeline |
| 主要资源 | Canvas Texture | Storage Buffer |
| Pass | Render Pass | Compute Pass |
| 发起工作 | `draw` | `dispatchWorkgroups` |
| 提交 | `queue.submit` | `queue.submit` |
| 结果 | 显示 Texture | 映射 Buffer 回读 |

整体结构：

```text
Device 创建资源和 Pipeline
        ↓
Bind Group 连接 Shader 与资源
        ↓
Command Encoder 录制命令
        ↓
Render / Compute Pass 发起工作
        ↓
finish 得到 Command Buffer
        ↓
Queue 提交给 GPU
```

需要真正理解的核心：

- Canvas 展示的是 GPU Texture，Render Pass 使用它的 Texture View。
- Shader Module 是 WGSL 程序；Pipeline 是 Shader 加上固定渲染或计算状态。
- Vertex Shader 计算顶点位置，Fragment Shader 计算片元输出，Compute Shader 进行通用并行计算。
- `draw(3)` 表示三个顶点调用；默认 `triangle-list` 用它们组成一个三角形。
- WebGPU 先录制命令，再通过 Queue 提交，不是即时执行绘制。
- Bind Group 把 Buffer、Texture、Sampler 等资源接到 Shader 的 `group/binding` 接口。
- CPU 与 GPU 异步执行；回读结果需要可映射 Buffer 和 `mapAsync()`。
- CSS 尺寸不等于 Canvas 实际像素尺寸，Canvas Resize 后需要重新渲染。

三条关键数据流：

```text
渲染：
Vertex Shader → 光栅化 → Fragment Shader → Texture

计算：
CPU Data → Storage Buffer → Compute Shader → Result Buffer → CPU

命令：
Command Encoder → Pass → Command Buffer → Queue → GPU
```

后续的 Inter-stage、Uniform、Storage Buffer、Vertex Buffer 和 Texture，都是在这套骨架上继续解决“数据如何进入 Shader、又如何在不同阶段之间传递”。

- [官方三角形示例](https://webgpufundamentals.org/webgpu/webgpu-simple-triangle.html)
- [官方 Compute 示例](https://webgpufundamentals.org/webgpu/webgpu-simple-compute.html)

# Inter-stage 变量

原文：[WebGPU Inter-stage 变量](https://webgpufundamentals.org/webgpu/lessons/zh_cn/webgpu-inter-stage-variables.html)

配套示例：[`inter-stage-variables.html`](./inter-stage-variables.html)

Inter-stage 变量解决的是：Vertex Shader 每个顶点算出的额外数据，怎样经过光栅化阶段传给 Fragment Shader。

```text
Vertex Shader 为三个顶点分别输出值
               ↓
GPU 组装并光栅化三角形
               ↓
在三角形内部插值这些值
               ↓
Fragment Shader 得到当前片元对应的值
```

颜色、UV、法线等通常通过这条路径传递。

## 一、用 @location 连接两个 Shader 阶段

顶点着色器不能只返回颜色，因为 GPU 还必须得到 `@builtin(position)`。最方便的做法是返回结构体：

```wgsl
struct VSOutput {
  @builtin(position) position: vec4f,
  @location(0) color: vec4f,
};

@vertex
fn vs(@builtin(vertex_index) vertexIndex: u32) -> VSOutput {
  let positions = array(
    vec2f( 0.0,  0.5),
    vec2f(-0.5, -0.5),
    vec2f( 0.5, -0.5),
  );

  let colors = array(
    vec4f(1, 0, 0, 1),
    vec4f(0, 1, 0, 1),
    vec4f(0, 0, 1, 1),
  );

  var output: VSOutput;
  output.position = vec4f(positions[vertexIndex], 0, 1);
  output.color = colors[vertexIndex];
  return output;
}

@fragment
fn fs(input: VSOutput) -> @location(0) vec4f {
  return input.color;
}
```

两个输出的用途不同：

- `@builtin(position)` 是 GPU 组装和光栅化图元所需的内置顶点位置。
- `@location(0)` 才是从 Vertex Stage 传向 Fragment Stage 的用户数据通道。

阶段之间按 location 编号和类型连接，不按字段名连接。因此 Fragment Shader 也可以直接写成：

```wgsl
@fragment
fn fs(@location(0) interpolatedColor: vec4f) -> @location(0) vec4f {
  return interpolatedColor;
}
```

Vertex 输出叫 `color`、Fragment 输入叫 `interpolatedColor` 没关系；两端的 `@location(0)` 和数据类型能匹配才是关键。

这里还有两个不同的 `@location(0)`：参数上的 location 0 是 Fragment Shader 的输入；返回值上的 location 0 是写往 `fragment.targets[0]` 的颜色输出。它们处在不同接口上，不是同一个变量。

## 二、插值发生在光栅化阶段

Vertex Shader 只执行三次，分别输出红、绿、蓝；Fragment Shader 却会对三角形覆盖的大量片元执行。中间缺少的值由光栅化器插值：

```text
顶点 A：红色 ─┐
顶点 B：绿色 ─┼→ 根据当前片元在三角形内的位置混合 → input.color
顶点 C：蓝色 ─┘
```

因此 Fragment Shader 中简单返回 `input.color`，就能得到 RGB 渐变。后续纹理章节会用相同机制插值 UV，光照章节会插值法线。

默认插值是透视正确插值。可以使用 `@interpolate` 修改：

| 写法 | 含义 |
| --- | --- |
| 省略或 `@interpolate(perspective, center)` | 默认：透视正确，在像素中心求值 |
| `@interpolate(linear, center)` | 不做透视校正的线性插值 |
| `@interpolate(flat)` | 完全不插值，使用图元某个顶点的值 |
| `@interpolate(perspective, centroid)` | 在图元实际覆盖区域中的某点求值 |
| `@interpolate(perspective, sample)` | 按 MSAA 样本求值，Fragment Shader 可能逐样本执行 |

整数无法表达插值产生的小数，所以整数类型的 Inter-stage 变量必须使用 `flat`：

```wgsl
@location(1) @interpolate(flat) objectId: u32,
```

`first` 和 `either` 只与 `flat` 搭配，用来描述从图元哪个顶点取得不插值的值；日常使用最常见的仍是默认插值和 `flat`。

## 三、@builtin(position) 不是普通 Inter-stage 变量

`@builtin(position)` 在两个阶段中名称相同，但含义不同：

| 所在阶段 | 方向 | 含义 | WebGL 对应物 |
| --- | --- | --- | --- |
| Vertex Shader | 输出 | 裁剪空间顶点位置 | `gl_Position` |
| Fragment Shader | 输入 | 当前片元在渲染目标中的像素坐标 | `gl_FragCoord` |

Fragment Shader 中的 position 不是 Vertex Shader position 经过普通 location 插值得到的。它由光栅化器产生，像素中心通常是半整数坐标，例如第一行第一列像素中心约为 `(0.5, 0.5)`。

可以用它生成屏幕空间棋盘格：

```wgsl
@fragment
fn fs(@builtin(position) pixelPosition: vec4f) -> @location(0) vec4f {
  let cell = vec2u(pixelPosition.xy) / 8;
  let checker = (cell.x + cell.y) % 2 == 1;
  return select(
    vec4f(1, 0, 0, 1),
    vec4f(0, 1, 1, 1),
    checker,
  );
}
```

它生成的是相对于 Canvas 像素的图案，不是贴在三角形自身坐标上的纹理；Canvas 尺寸改变时，棋盘格与三角形的相对关系也会改变。

VS 和 FS 写在同一个 WGSL 字符串中只是为了共享结构、函数和绑定声明。Pipeline 会从指定的 `entryPoint` 出发，只使用该入口点能访问到的代码；两个阶段也完全可以来自两个不同的 ShaderModule。

## 四、和 WebGL 对比

WebGL 1 使用 `varying`，WebGL 2 使用 Vertex `out` 与 Fragment `in`：

```glsl
// WebGL 2 Vertex Shader
out vec4 v_color;

void main() {
  gl_Position = vec4(a_position, 0.0, 1.0);
  v_color = a_color;
}
```

```glsl
// WebGL 2 Fragment Shader
in vec4 v_color;
out vec4 outColor;

void main() {
  outColor = v_color;
}
```

GLSL Program 链接器通常根据变量名和类型匹配 `out/in`；WGSL 明确使用数字 location 匹配阶段接口：

| 概念 | WebGL / GLSL | WebGPU / WGSL |
| --- | --- | --- |
| 顶点位置输出 | `gl_Position` | Vertex `@builtin(position)` |
| 顶点传给片元的数据 | `varying` 或 Vertex `out` | Vertex 输出的 `@location(n)` |
| 片元接收数据 | `varying` 或 Fragment `in` | Fragment 输入的同一个 `@location(n)` |
| 片元像素坐标 | `gl_FragCoord` | Fragment `@builtin(position)` |
| 默认插值 | `smooth`，透视正确 | `perspective, center` |
| 不插值 | `flat` | `@interpolate(flat)` |

两套 API 的光栅化和插值原理相同；主要区别是 WGSL 用 Attribute 明确标注 builtin、location 和插值规则，不依赖跨 Shader 字符串的变量名。

这一章记住：

**普通阶段间数据靠相同的 `@location` 从 Vertex Shader 连接到 Fragment Shader，并在光栅化时默认插值；`@builtin(position)` 是 GPU 定义的阶段专用值，不是普通 location 变量。**

# Uniforms

原文：[WebGPU Uniforms](https://webgpufundamentals.org/webgpu/lessons/zh_cn/webgpu-uniforms.html)

Uniform 用来把 JavaScript 中的数据传给 Shader。它很像 Shader 的只读全局变量：在一次 `draw` 中，所有顶点着色器和片元着色器调用看到的是同一份值；下一次绘制前，JavaScript 可以更新它。

它和上一章的 Inter-stage 变量不是一回事：

```text
Inter-stage 变量：vertex shader 产生 → 光栅化插值 → fragment shader 接收
Uniform：JavaScript 写入 → GPUBuffer 保存 → 各个 Shader 阶段共同读取
```

适合放进 Uniform 的数据通常包括颜色、缩放、位置、时间、分辨率、相机矩阵和光照参数。

对于这个三角形，我们在执行绘制命令时的状态是这样的

![img](https://webgpufundamentals.org/webgpu/lessons/resources/webgpu-draw-diagram-triangle-uniform.svg)

## 二、WebGL 和 WebGPU 的区别

WebGL 通常按变量找到 location，再逐个设置：

```glsl
// GLSL
uniform vec4 u_color;
uniform vec2 u_scale;
uniform vec2 u_offset;
```

```js
gl.useProgram(program);
gl.uniform4fv(colorLocation, color);
gl.uniform2fv(scaleLocation, scale);
gl.uniform2fv(offsetLocation, offset);
```

WebGPU 不提供 `uniform4fv` 这种逐变量接口，而是先把多个值排进一块内存，再把整块 Buffer 绑定给 Shader：

```wgsl
struct Uniforms {
  color: vec4f,
  scale: vec2f,
  offset: vec2f,
};

@group(0) @binding(0) var<uniform> uniforms: Uniforms;
```

```js
device.queue.writeBuffer(uniformBuffer, 0, uniformValues);
pass.setBindGroup(0, bindGroup);
```

| 问题 | WebGL | WebGPU |
| --- | --- | --- |
| Shader 如何声明 | `uniform vec4 u_color` | `var<uniform>` 和结构体 |
| JavaScript 如何传值 | `gl.uniform*` | 写入 `GPUBuffer` |
| Shader 如何找到数据 | uniform location | `@group(n) @binding(n)` |
| 绘制前如何启用 | `gl.useProgram` 后设置 | `setBindGroup` |
| 数据组织方式 | 看起来像逐变量设置 | 明确的连续内存布局 |

WebGPU 写法更啰嗦，但数据布局和绑定关系都是显式的，更接近 Vulkan、Direct3D 12 和 Metal 的工作方式，也更适合批量管理 GPU 数据。

## 二、完整的数据通路

Uniform 从 JavaScript 进入 Shader，要经过五步：

```text
JavaScript 数值
    ↓ 写入
Float32Array（CPU 内存）
    ↓ device.queue.writeBuffer
GPUBuffer（GPU 可访问的内存）
    ↓ BindGroup 的 binding 0
@group(0) @binding(0)
    ↓
vertex shader / fragment shader
```

先创建 Uniform Buffer：

```js
const uniformBuffer = device.createBuffer({
  size: 32,
  usage: GPUBufferUsage.UNIFORM | GPUBufferUsage.COPY_DST,
});
```

两个 usage 分别表示：

- `UNIFORM`：这块 Buffer 可以被 Shader 当作 uniform 读取。
- `COPY_DST`：允许 `queue.writeBuffer` 把 CPU 数据复制进来。

再准备 CPU 侧数组：

```js
const uniformValues = new Float32Array(8);
```

它只是普通 JavaScript 内存，不是 GPU 内存。真正上传发生在：

```js
device.queue.writeBuffer(uniformBuffer, 0, uniformValues);
```

## 三、内存布局为什么是 32 字节

WGSL 结构体和 JavaScript 数组必须使用相同的字段顺序和偏移：

```wgsl
struct Uniforms {
  color: vec4f,
  scale: vec2f,
  offset: vec2f,
};
```

| 字段 | Float32 索引 | 字节偏移 | 字节大小 |
| --- | ---: | ---: | ---: |
| `color: vec4f` | 0～3 | 0 | 16 |
| `scale: vec2f` | 4～5 | 16 | 8 |
| `offset: vec2f` | 6～7 | 24 | 8 |
| 合计 | 8 个 float | 0～31 | 32 |

因此 JavaScript 中可以这样填写：

```js
const kColorOffset = 0;
const kScaleOffset = 4;
const kOffsetOffset = 6;

uniformValues.set([1, 0, 0, 1], kColorOffset);
uniformValues.set([0.5, 0.5], kScaleOffset);
uniformValues.set([0.2, -0.1], kOffsetOffset);
```

这里的 offset 是 **Float32 元素索引**，不是字节偏移；`kOffsetOffset = 6` 实际对应 `6 × 4 = 24` 字节。

更复杂的 WGSL 结构体必须严格考虑对齐和 padding，不能只把字段字节数简单相加。本例刚好由 `vec4f + vec2f + vec2f` 紧密组成 32 字节。

## 四、BindGroup 如何连接 Buffer 和 Shader

Shader 声明：

```wgsl
@group(0) @binding(0) var<uniform> uniforms: Uniforms;
```

JavaScript 创建对应的绑定组：

```js
const bindGroup = device.createBindGroup({
  layout: pipeline.getBindGroupLayout(0),
  entries: [{
    binding: 0,
    resource: { buffer: uniformBuffer },
  }],
});
```

绘制前再绑定：

```js
pass.setBindGroup(0, bindGroup);
pass.draw(3);
```

这些编号必须对应：

```text
Shader @group(0)   ↔ pipeline.getBindGroupLayout(0) ↔ pass.setBindGroup(0, ...)
Shader @binding(0) ↔ entries 中的 binding: 0
```

BindGroup 本身不保存颜色或缩放值，它只保存“第 0 个绑定位置应该使用哪一个 GPUBuffer”这样的资源连接关系。

## 五、更新和多次绘制

本章示例让 Uniform 同时控制三角形的颜色、缩放和位置：

```wgsl
let position = positions[vertexIndex] * uniforms.scale + uniforms.offset;
return vec4f(position, 0.0, 1.0);
```

```wgsl
return uniforms.color;
```

更新页面滑块时，JavaScript 修改 `Float32Array`，调用一次 `writeBuffer`，然后重新绘制。Pipeline、ShaderModule 和 BindGroup 都不需要重新创建。

多对象绘制时有一个重要陷阱：不要在录制同一个 CommandBuffer 的过程中反复改写同一个 Uniform Buffer，并期待每次 `draw` 看到不同值。`pass.draw()` 此时只是在编码；CommandBuffer 尚未提交。循环中的所有 `queue.writeBuffer()` 会先排进 Queue，最后提交的那些 Draw 都会读取同一块 Buffer 的最终内容，而不是分别保存每次写入时的快照。

常见解决方式是：

- 每个对象使用自己的 Uniform Buffer 和 BindGroup。
- 把多个对象的数据放进一个大 Buffer，配合 dynamic offset。
- 按更新频率拆分 Buffer，例如相机数据一份、材质数据一份、每对象变换一份。

原文最后采用的是“按更新频率拆分”：颜色和偏移只上传一次，缩放每次渲染更新。

```wgsl
struct StaticUniforms {
  color: vec4f,
  offset: vec2f,
};

struct ChangingUniforms {
  scale: vec2f,
};

@group(0) @binding(0) var<uniform> staticData: StaticUniforms;
@group(0) @binding(1) var<uniform> changingData: ChangingUniforms;
```

一个 BindGroup 可以同时引用两块 Buffer：

```js
entries: [
  { binding: 0, resource: { buffer: staticUniformBuffer } },
  { binding: 1, resource: { buffer: changingUniformBuffer } },
]
```

这样每帧只上传真正变化的 `scale`。WebGL 中也可以把稳定数据和变化数据拆成不同 Uniform/Uniform Block；WebGPU 的区别是这种分组直接表现为 Buffer、Binding 和内存范围。

这一章暂时记住一句话：

**WebGL 像是在逐个设置 uniform 变量；WebGPU 则是先按 WGSL 布局准备一块 GPUBuffer，再通过 BindGroup 把它接到 Shader。**

配套示例：[`uniforms.html`](./uniforms.html)

# Storage Buffer（存储缓冲区）

![60da06da-035d-43f5-a9d7-29a3f614fb34](./C:/Users/luxiding/Downloads/60da06da-035d-43f5-a9d7-29a3f614fb34.png)

原文：[WebGPU 存储缓冲区](https://webgpufundamentals.org/webgpu/lessons/zh_cn/webgpu-storage-buffers.html)

Storage Buffer 和 Uniform Buffer 都能把 Buffer 绑定给 Shader，但它更适合大量数据、数组数据以及需要由 GPU 写回的数据。

最小改动只有两处：

```js
// Uniform Buffer
usage: GPUBufferUsage.UNIFORM | GPUBufferUsage.COPY_DST

// Storage Buffer
usage: GPUBufferUsage.STORAGE | GPUBufferUsage.COPY_DST
```

```wgsl
// Uniform
@group(0) @binding(0) var<uniform> data: Data;

// 只读 Storage
@group(0) @binding(0) var<storage, read> data: Data;
```

但两者的设计用途不同：

| 对比 | Uniform Buffer | Storage Buffer |
| --- | --- | --- |
| 典型用途 | 少量、频繁读取的常量 | 大数组、对象列表、计算数据 |
| Shader 权限 | 只读 | 可只读，也可读写 |
| 保证支持的单次绑定上限 | 至少 64 KiB | 至少 128 MiB |
| 运行时长度数组 | 不适合 | 支持放在结构末尾或直接绑定数组 |
| 常见性能倾向 | 小型常量读取通常更合适 | 大量结构化数据更合适 |

这里的“至少 64 KiB / 128 MiB”是规范保证的最低上限，设备实际能力应查询：

```js
device.limits.maxUniformBufferBindingSize;
device.limits.maxStorageBufferBindingSize;
```

## 一、和 WebGL 对比

WebGL 2 没有 WebGPU 这种通用 Storage Buffer，也没有 Compute Shader。大量数据通常需要换一种形式传入：

- 普通顶点数据使用 `ARRAY_BUFFER` 和 attribute。
- 每实例数据使用 instanced attribute、`vertexAttribDivisor` 和 `drawArraysInstanced`。
- 更灵活的大数组有时会编码进 Texture，再由 Shader 采样。
- 少量共享常量可以使用 uniform 或 Uniform Buffer Object。

例如 WebGL 2 的实例化思路：

```js
gl.bindBuffer(gl.ARRAY_BUFFER, instanceBuffer);
gl.vertexAttribPointer(offsetLocation, 2, gl.FLOAT, false, stride, offset);
gl.vertexAttribDivisor(offsetLocation, 1);
gl.drawArraysInstanced(gl.TRIANGLES, 0, 3, instanceCount);
```

WebGPU 既支持下一章会讲的实例化 Vertex Buffer，也可以让顶点着色器主动从 Storage Buffer 中索引数据：

```wgsl
@group(0) @binding(0)
var<storage, read> objects: array<ObjectData>;

@vertex fn vs(
  @builtin(vertex_index) vertexIndex: u32,
  @builtin(instance_index) instanceIndex: u32,
) -> VSOutput {
  let object = objects[instanceIndex];
  // 使用当前实例自己的颜色、位置和缩放
}
```

```js
pass.draw(3, objectCount);
```

第二个参数 `objectCount` 是实例数量。GPU 会执行：

```text
instanceIndex = 0：执行 vertexIndex 0、1、2
instanceIndex = 1：执行 vertexIndex 0、1、2
instanceIndex = 2：执行 vertexIndex 0、1、2
...
```

所以一次 `draw(3, 100)` 可以绘制 100 个三角形，而不是在 JavaScript 中调用 100 次 `draw(3)`。

## 二、用数组保存所有对象

本章示例让每个对象占用一个结构体：

```wgsl
struct ObjectData {
  color: vec4f,
  offset: vec2f,
  scale: vec2f,
};

@group(0) @binding(0)
var<storage, read> objects: array<ObjectData>;
```

每个 `ObjectData` 是 32 字节：

| 字段 | Float32 索引 | 字节偏移 | 大小 |
| --- | ---: | ---: | ---: |
| `color` | 0～3 | 0 | 16 字节 |
| `offset` | 4～5 | 16 | 8 字节 |
| `scale` | 6～7 | 24 | 8 字节 |

100 个对象需要：

```text
32 × 100 = 3200 字节
```

JavaScript 侧创建一整块 Buffer：

```js
const storageBuffer = device.createBuffer({
  size: objectCount * 32,
  usage: GPUBufferUsage.STORAGE | GPUBufferUsage.COPY_DST,
});
```

再用一个连续的 `Float32Array` 填充所有对象：

```js
const values = new Float32Array(objectCount * 8);

for (let i = 0; i < objectCount; ++i) {
  const base = i * 8;
  values.set(color, base + 0);
  values.set(offset, base + 4);
  values.set(scale, base + 6);
}

device.queue.writeBuffer(storageBuffer, 0, values);
```

这里依然必须保证 JavaScript 内存布局与 WGSL 结构体完全一致。

## 三、一次 Draw 如何找到每个对象

完整关系是：

```text
Float32Array 中第 i 个 ObjectData
          ↓ writeBuffer
Storage Buffer 中 objects[i]
          ↓ @builtin(instance_index)
vertex shader 读取 objects[instanceIndex]
          ↓ Inter-stage 变量
fragment shader 得到该实例的颜色
```

顶点着色器可以取得实例颜色，但片元着色器没有 `instance_index`。因此要把颜色作为上一章学过的 Inter-stage 变量传过去：

```wgsl
struct VSOutput {
  @builtin(position) position: vec4f,
  @location(0) color: vec4f,
};

@vertex fn vs(...) -> VSOutput {
  let object = objects[instanceIndex];

  var output: VSOutput;
  output.position = /* 当前对象的位置 */;
  output.color = object.color;
  return output;
}

@fragment fn fs(input: VSOutput) -> @location(0) vec4f {
  return input.color;
}
```

这把前面三章连接起来了：

```text
Storage Buffer 提供每个实例的数据
instance_index 选择当前实例
Inter-stage 变量把颜色传给 fragment shader
```

## 四、只读与读写

原文还展示了 Storage Buffer 的另一个用途：保存顶点数据。Shader 用 `vertex_index` 主动索引，而不是让固定顶点获取阶段解释 Vertex Buffer：

```wgsl
struct Vertex {
  position: vec2f,
};

@group(0) @binding(2)
var<storage, read> vertices: array<Vertex>;

@vertex
fn vs(@builtin(vertex_index) vertexIndex: u32) -> @builtin(position) vec4f {
  let position = vertices[vertexIndex].position;
  return vec4f(position, 0, 1);
}
```

这种方式能用任意索引和结构组织顶点，灵活性高；但传统 Vertex Buffer 由专门的顶点获取阶段解码，表达固定顶点属性更直接，在部分旧设备上也可能更快。下一章正是比较这两条路径。

渲染示例只需要读取对象数据，所以声明：

```wgsl
var<storage, read> objects: array<ObjectData>;
```

Storage Buffer 也能让 GPU 写入：

```wgsl
@group(0) @binding(0)
var<storage, read_write> values: array<f32>;
```

`read_write` 最常见于 Compute Shader，例如粒子模拟、数据变换和并行计算。Uniform Buffer 永远只能由 Shader 读取，不能作为 GPU 写入目标。

但 Storage Buffer 并不是所有数据的默认选择：

- 少量相机、时间和材质参数，优先考虑 Uniform Buffer。
- 固定格式的顶点输入，传统 Vertex Buffer 往往更直接，部分旧设备也可能更快。
- 大量对象结构、运行时数组或 GPU 计算结果，Storage Buffer 更合适。

这一章暂时记住一句话：

**Uniform Buffer 是“一小份共享参数”；Storage Buffer 更像“一大张 GPU 可索引、必要时还能写入的数据表”。**

配套示例：[`storage-buffers.html`](./storage-buffers.html)

# Vertex Buffer（顶点缓冲区）

原文：[WebGPU 顶点缓冲区](https://webgpufundamentals.org/webgpu/lessons/zh_cn/webgpu-vertex-buffers.html)

上一章使用 Storage Buffer 保存顶点数据，Shader 通过 `vertex_index` 主动索引数组。Vertex Buffer 的思路不同：Shader 不直接访问 Buffer，而是由 WebGPU 按照 Pipeline 中声明的布局，从 Buffer 中自动提取当前顶点的属性。

```text
Storage Buffer：Shader 写 objects[index]，主动读取数组
Vertex Buffer：Pipeline 描述字节布局，GPU 自动把属性传给 @location
```

典型的顶点属性包括位置、颜色、纹理坐标、法线、切线和骨骼权重。

## 一、和 WebGL 对比

WebGL 的顶点属性通常这样配置：

```js
gl.bindBuffer(gl.ARRAY_BUFFER, vertexBuffer);
gl.bufferData(gl.ARRAY_BUFFER, vertexData, gl.STATIC_DRAW);

gl.enableVertexAttribArray(positionLocation);
gl.vertexAttribPointer(
  positionLocation,
  2,
  gl.FLOAT,
  false,
  20,
  0,
);
```

WebGPU 把同样的信息放在 RenderPipeline 中：

```js
vertex: {
  module: shaderModule,
  buffers: [{
    arrayStride: 20,
    attributes: [{
      shaderLocation: 0,
      offset: 0,
      format: "float32x2",
    }],
  }],
}
```

绘制前再指定实际 Buffer：

```js
pass.setVertexBuffer(0, vertexBuffer);
```

对应关系如下：

| 概念 | WebGL | WebGPU |
| --- | --- | --- |
| 顶点 Buffer 用途 | `ARRAY_BUFFER` | `GPUBufferUsage.VERTEX` |
| 属性位置 | attribute location | `shaderLocation` / `@location` |
| 每条记录大小 | `stride` | `arrayStride` |
| 字段起始位置 | `pointer` 的 offset | `attributes[].offset` |
| 字段类型 | size + type | `format` |
| 绑定实际 Buffer | `bindBuffer` | `setVertexBuffer` |

WebGL 的 `vertexAttribPointer` 修改当前上下文状态；WebGPU 把布局固定进 Pipeline，因此更容易提前验证，也减少绘制时的状态解释工作。

## 二、GPU 如何从字节中提取属性

假设每个顶点交错保存位置和颜色：

```text
一个顶点共 20 字节

字节  0～7  ：position，2 个 float32
字节  8～19 ：color，3 个 float32
```

连续三个顶点在内存中是：

```text
[position0, color0] [position1, color1] [position2, color2]
|<---- 20 字节 --->|<---- 20 字节 --->|<---- 20 字节 --->|
```

Pipeline 布局：

```js
buffers: [{
  arrayStride: 5 * 4,
  stepMode: "vertex",
  attributes: [
    { shaderLocation: 0, offset: 0, format: "float32x2" },
    { shaderLocation: 1, offset: 8, format: "float32x3" },
  ],
}]
```

WGSL 接收：

```wgsl
struct VertexInput {
  @location(0) position: vec2f,
  @location(1) color: vec3f,
};
```

这里四个字段必须正确配合：

- `arrayStride: 20`：从一个顶点的起点走到下一个顶点的起点需要 20 字节。
- `offset: 0`：position 从当前顶点第 0 字节开始。
- `offset: 8`：color 跳过两个 float32 后，从第 8 字节开始。
- `format`：告诉 GPU 应该把这些字节解码成几个、什么类型的数值。

常见格式只需要先记这些：

| format | Buffer 字节 | WGSL 类型 |
| --- | ---: | --- |
| `float32` | 4 | `f32` |
| `float32x2` | 8 | `vec2f` |
| `float32x3` | 12 | `vec3f` |
| `float32x4` | 16 | `vec4f` |
| `unorm8x4` | 4 | `vec4f`，自动从 0～255 转成 0～1 |
| `uint32` | 4 | `u32` |

创建和上传 Buffer：

```js
const vertexBuffer = device.createBuffer({
  size: vertexData.byteLength,
  usage: GPUBufferUsage.VERTEX | GPUBufferUsage.COPY_DST,
});

device.queue.writeBuffer(vertexBuffer, 0, vertexData);
```

`COPY_DST` 允许 JavaScript 上传数据；`VERTEX` 允许顶点获取阶段读取它。

原文特别提醒：Pipeline 中的 Vertex Format 与 WGSL 参数不必拥有完全相同的分量数量。顶点属性在进入 Shader 时按四个分量理解，缺少的分量使用 `(0, 0, 0, 1)` 补齐。例如 Buffer 只提供三个浮点颜色：

```js
{ shaderLocation: 1, offset: 8, format: "float32x3" }
```

WGSL 仍可以接收 `vec4f`：

```wgsl
@location(1) color: vec4f // 得到 (r, g, b, 1)
```

这不是任意类型自动转换；location、数值类别和允许的 Vertex Format 仍必须兼容。这个默认补值规则最常用于把 RGB 顶点颜色直接扩展成 RGBA。

## 三、按顶点还是按实例前进

`stepMode` 决定 GPU 什么时候移动到 Buffer 的下一条记录：

```js
stepMode: "vertex"   // 默认值：每处理一个顶点，前进一条
stepMode: "instance" // 每处理一个实例，前进一条
```

例如：

```text
Buffer 0，stepMode=vertex
  position0 → position1 → position2，每个实例重新开始

Buffer 1，stepMode=instance
  object0 → object1 → object2，每个实例只前进一步
```

这与 WebGL 2 的 `vertexAttribDivisor(location, 1)` 是同一个概念。上一章使用 Storage Buffer 和 `instance_index` 实现实例化；本章也可以把每实例颜色、位置和缩放放进 `stepMode: "instance"` 的 Vertex Buffer。

两种方案都合理：

- Vertex Buffer 适合固定格式、由顶点获取硬件直接提供的属性。
- Storage Buffer 更灵活，可以按任意索引读取复杂数组。

## 四、交错布局与压缩格式

把多个属性放在同一个 Buffer 中叫交错布局：

```text
position, color, position, color, position, color ...
```

也可以分开放进多个 Buffer：

```text
Buffer 0：position, position, position ...
Buffer 1：color, color, color ...
```

交错布局通常能让同一个顶点的数据靠得更近；分离布局则方便只更新其中一类数据。选择取决于数据如何生成和更新。

颜色没有必要总用四个 `float32`，可以使用 `unorm8x4`：

```text
float32x4：16 字节，直接保存 0.0～1.0
unorm8x4 ： 4 字节，保存 0～255，GPU 自动归一化到 0.0～1.0
```

这能让颜色占用空间减少 75%。Position 通常仍需要浮点精度，而颜色、法线或权重经常可以使用压缩格式。

## 五、Index Buffer 复用顶点

没有索引缓冲区时，`draw(6)` 按顺序处理：

```text
顶点 0、1、2 组成第一个三角形
顶点 3、4、5 组成第二个三角形
```

一个矩形其实只有四个不同顶点，但两个三角形需要六次引用。Index Buffer 保存的不是顶点数据，而是顶点访问顺序：

```js
const indices = new Uint16Array([
  0, 1, 2,
  2, 1, 3,
]);
```

创建和绘制：

```js
const indexBuffer = device.createBuffer({
  size: indices.byteLength,
  usage: GPUBufferUsage.INDEX | GPUBufferUsage.COPY_DST,
});

pass.setVertexBuffer(0, vertexBuffer);
pass.setIndexBuffer(indexBuffer, "uint16");
pass.drawIndexed(6);
```

WebGL 对应的是：

```js
gl.bindBuffer(gl.ELEMENT_ARRAY_BUFFER, indexBuffer);
gl.drawElements(gl.TRIANGLES, 6, gl.UNSIGNED_SHORT, 0);
```

索引通常使用 `uint16` 或 `uint32`。它既能减少重复顶点数据，也可能让 GPU 复用已经计算过的顶点着色器结果。

这一章暂时记住一句话：

**Vertex Buffer 保存原始顶点字节，Pipeline 负责解释字节，`setVertexBuffer` 提供实际数据，Index Buffer 决定复用和访问顶点的顺序。**

配套示例：[`vertex-buffers.html`](./vertex-buffers.html)

# Textures（纹理）

原文：[WebGPU 纹理](https://webgpufundamentals.org/webgpu/lessons/zh_cn/webgpu-textures.html)

Texture 可以理解为 GPU 擅长访问的多维数据。最常见的是二维图像，但纹理不仅仅用来保存颜色，也可以保存法线、深度、材质参数、查找表和计算结果。

与 Storage Buffer 相比，纹理最大的特殊能力是 **采样**：Sampler 可以根据 UV 坐标处理边界、混合相邻 texel，并选择合适的 mip level。

```text
原始像素数据
  ↓ writeTexture
GPUTexture
  ↓ createView
GPUTextureView ─┐
               ├→ BindGroup → textureSample → 像素颜色
GPUSampler ─────┘
```

## 一、和 WebGL 对比

WebGL 的基本纹理流程：

```js
const texture = gl.createTexture();
gl.activeTexture(gl.TEXTURE0);
gl.bindTexture(gl.TEXTURE_2D, texture);
gl.texImage2D(/* 像素数据 */);
gl.texParameteri(gl.TEXTURE_2D, gl.TEXTURE_MAG_FILTER, gl.LINEAR);
gl.uniform1i(textureLocation, 0);
```

WebGPU 把存储、观察方式和采样规则拆成独立对象：

```js
const texture = device.createTexture(/* 存储 */);
device.queue.writeTexture(/* 上传像素 */);

const textureView = texture.createView();
const sampler = device.createSampler(/* 采样规则 */);

const bindGroup = device.createBindGroup({
  entries: [
    { binding: 0, resource: sampler },
    { binding: 1, resource: textureView },
  ],
});
```

| 概念 | WebGL | WebGPU |
| --- | --- | --- |
| 创建纹理 | `createTexture` | `device.createTexture` |
| 上传数据 | `texImage2D` / `texSubImage2D` | `queue.writeTexture` |
| 过滤和环绕 | `texParameteri` 或 Sampler Object | 独立的 `GPUSampler` |
| 选择纹理单元 | `activeTexture` + `uniform1i` | `@group/@binding` + BindGroup |
| Shader 类型 | `sampler2D` | `texture_2d` 与 `sampler` 分开 |
| 采样 | `texture(u_texture, uv)` | `textureSample(texture, sampler, uv)` |

WebGPU 不依赖“当前激活纹理单元”这种全局状态，纹理视图和采样器都明确放进 BindGroup。

## 二、创建、上传和绑定纹理

创建一个 `rgba8unorm` 二维纹理：

```js
const texture = device.createTexture({
  size: [width, height],
  format: "rgba8unorm",
  usage:
    GPUTextureUsage.TEXTURE_BINDING |
    GPUTextureUsage.COPY_DST,
});
```

- `rgba`：每个 texel 有红、绿、蓝、Alpha 四个通道。
- `8`：每个通道占 8 bit，因此每个 texel 共 4 字节。
- `unorm`：Buffer 中的整数 0～255，在 Shader 中解释成浮点数 0.0～1.0。
- `TEXTURE_BINDING`：允许 Shader 绑定并采样它。
- `COPY_DST`：允许把外部数据复制进去。

上传原始 `Uint8Array`：

```js
device.queue.writeTexture(
  { texture },
  textureData,
  { bytesPerRow: width * 4 },
  { width, height },
);
```

`bytesPerRow` 是源数据中一行到下一行相隔多少字节。`rgba8unorm` 每像素 4 字节，所以紧密排列的数据是 `width × 4`。

Shader 声明两个绑定：

```wgsl
@group(0) @binding(0) var imageSampler: sampler;
@group(0) @binding(1) var imageTexture: texture_2d<f32>;
```

片元着色器采样：

```wgsl
let color = textureSample(imageTexture, imageSampler, uv);
```

三个参数分别是纹理、采样器和纹理坐标。

## 三、UV 与 Sampler

二维纹理坐标通常叫 UV，与纹理实际像素尺寸无关：

```text
U：水平方向，通常从 0.0 到 1.0
V：垂直方向，通常从 0.0 到 1.0
```

纹理坐标本身没有天然的“上”和“下”；`(0, 0)` 只是指向纹理数据中的第一个 texel。WebGL 教程常约定 `(0, 0)` 在左下，而浏览器图片数据通常从左上开始，这正是图片经常上下颠倒的来源。项目需要统一约定，而不是把某一种方向当作 API 永远固定的含义。

Vertex Buffer 为每个顶点提供 UV：

```wgsl
struct VertexInput {
  @location(0) position: vec2f,
  @location(1) texcoord: vec2f,
};
```

UV 经过光栅化插值后进入片元着色器。因此矩形内部每个片元都会得到不同坐标，再从纹理中读取对应颜色。

图像上下颠倒时，最常见的处理是翻转 V：

```wgsl
let flippedUV = vec2f(uv.x, 1.0 - uv.y);
```

Sampler 主要控制两类行为。

过滤方式：

```js
device.createSampler({
  magFilter: "nearest", // 放大纹理时
  minFilter: "linear",  // 缩小纹理时
});
```

- `nearest`：选择最近 texel，边缘清晰，适合像素画。
- `linear`：混合周围 texel，画面平滑。

超出 0～1 后的寻址方式：

```js
addressModeU: "clamp-to-edge";
addressModeV: "repeat";
```

- `clamp-to-edge`：固定在边缘颜色。
- `repeat`：从另一侧重新开始。
- `mirror-repeat`：每次重复时镜像翻转。

纹理和 Sampler 是独立对象。同一张 Texture 可以搭配多个 Sampler，以不同过滤和寻址规则绘制。

## 四、Mipmaps

把一张大纹理缩得很小时，一个屏幕像素会覆盖许多 texel。如果仍只从最大纹理中取少量 texel，容易产生闪烁和摩尔纹。

Mipmaps 是同一张纹理预先生成的多级缩小版本：

```text
Level 0：16 × 16
Level 1： 8 × 8
Level 2： 4 × 4
Level 3： 2 × 2
Level 4： 1 × 1
```

创建时声明级数：

```js
const texture = device.createTexture({
  size: [16, 16],
  mipLevelCount: 5,
  format: "rgba8unorm",
  usage: GPUTextureUsage.TEXTURE_BINDING | GPUTextureUsage.COPY_DST,
});
```

上传时指定级别：

```js
device.queue.writeTexture(
  { texture, mipLevel },
  mipData,
  { bytesPerRow: mipWidth * 4 },
  { width: mipWidth, height: mipHeight },
);
```

Sampler 再控制 mip level 之间如何选择：

```js
mipmapFilter: "nearest"; // 选择最近一级
mipmapFilter: "linear";  // 混合相邻两级
```

WebGPU 没有 WebGL 的 `generateMipmap()` 这种内置调用。Mip 数据需要由程序在 CPU、Render Pass 或 Compute Shader 中生成，也可以使用工具库。

## 五、TextureView 与纹理格式

`GPUTexture` 表示实际分配的纹理存储；`GPUTextureView` 表示 Shader 或 RenderPass 这次如何观察它。

```js
const view = texture.createView({
  baseMipLevel: 0,
  mipLevelCount: 1,
});
```

View 可以只暴露某几个 mip levels、数组层或特定维度。普通二维纹理通常直接使用：

```js
const view = texture.createView();
```

纹理可能拥有不同用途：

- `TEXTURE_BINDING`：被 Shader 采样。
- `COPY_DST`：接收上传或复制的数据。
- `COPY_SRC`：作为复制源。
- `RENDER_ATTACHMENT`：作为 RenderPass 的颜色或深度目标。
- `STORAGE_BINDING`：作为可读写 Storage Texture。

格式必须与 Shader 声明和用途兼容。例如 `rgba8unorm` 通常配合 `texture_2d<f32>`；整数纹理则使用 `texture_2d<u32>` 或 `texture_2d<i32>`，并且采样方式也不同。

这一章暂时记住一句话：

**GPUTexture 保存 texel，TextureView 决定看哪一部分，Sampler 决定怎么取样，UV 决定取哪里。**

配套示例：[`textures.html`](./textures.html)

# Importing Textures（加载图像纹理）

原文：[WebGPU 加载图像到纹理](https://webgpufundamentals.org/webgpu/lessons/zh_cn/webgpu-importing-textures.html)

上一章使用 `Uint8Array + writeTexture` 上传自己排列的像素。本章处理浏览器已经能解码的外部图像，例如 PNG、JPEG、Canvas 和视频帧。

核心流程是：

```text
URL / File
  ↓ fetch 或文件选择
Blob
  ↓ createImageBitmap
ImageBitmap
  ↓ copyExternalImageToTexture
GPUTexture mip level 0
  ↓ GPU Render Pass
其余 mip levels
```

## 一、和 WebGL 对比

WebGL 可以把图片对象直接交给 `texImage2D`：

```js
gl.bindTexture(gl.TEXTURE_2D, texture);
gl.texImage2D(
  gl.TEXTURE_2D,
  0,
  gl.RGBA,
  gl.RGBA,
  gl.UNSIGNED_BYTE,
  image,
);
gl.generateMipmap(gl.TEXTURE_2D);
```

WebGPU 将“分配纹理”“复制外部图像”“生成 mipmaps”拆成明确步骤：

```js
const texture = device.createTexture(/* 分配 */);

device.queue.copyExternalImageToTexture(
  { source: imageBitmap, flipY: true },
  { texture },
  [imageBitmap.width, imageBitmap.height],
);

generateMips(device, texture);
```

| 操作 | WebGL | WebGPU |
| --- | --- | --- |
| 解码图片 | `Image` / `ImageBitmap` | 通常使用 `ImageBitmap` |
| 上传外部图片 | `texImage2D` | `copyExternalImageToTexture` |
| Y 翻转 | `UNPACK_FLIP_Y_WEBGL` | 源参数中的 `flipY` |
| 自动生成 mip | `generateMipmap` | 没有内置函数，需要自己渲染或计算 |
| 纹理状态 | 依赖当前绑定纹理 | 显式 `GPUTexture`、View、BindGroup |

## 二、URL、Blob 和 ImageBitmap

从 URL 加载图像的常见辅助函数：

```js
async function loadImageBitmap(url) {
  const response = await fetch(url);
  const blob = await response.blob();

  return createImageBitmap(blob, {
    colorSpaceConversion: "none",
  });
}
```

每一步的意义：

```text
fetch：获取文件响应
Blob：保存尚未手工解析的图片文件数据
createImageBitmap：让浏览器解码成可复制的二维图像
```

`colorSpaceConversion: "none"` 表示不让解码过程主动转换像素色彩空间。对于法线贴图、高度图和数据纹理，这一点尤其重要，因为其中的数值不是普通显示颜色。普通照片是否使用转换，需要根据项目的颜色管理策略决定。

通过 `<input type="file">` 获得的 `File` 本身就是一种 Blob，也能直接传给 `createImageBitmap(file)`。

跨域 URL 必须满足 CORS，并且来源要允许读取；否则浏览器安全模型会阻止把它复制到 GPU。使用本地文件选择器或同源图片不会遇到这个问题。

## 三、创建纹理并复制外部图像

纹理尺寸应该匹配来源：

```js
const texture = device.createTexture({
  size: [source.width, source.height],
  format: "rgba8unorm",
  usage:
    GPUTextureUsage.TEXTURE_BINDING |
    GPUTextureUsage.COPY_DST |
    GPUTextureUsage.RENDER_ATTACHMENT,
});
```

这些 usage 分别表示：

- `TEXTURE_BINDING`：最终能被 Shader 采样。
- `COPY_DST`：能接收外部图像复制。
- `RENDER_ATTACHMENT`：能在 GPU 生成 mipmaps 时作为渲染目标。

复制 mip level 0：

```js
device.queue.copyExternalImageToTexture(
  {
    source,
    flipY: true,
  },
  {
    texture,
  },
  {
    width: source.width,
    height: source.height,
  },
);
```

三个参数依次是：

```text
从哪里复制：source、源区域、是否 flipY
复制到哪里：texture、目标 mip level、目标 origin
复制多大：width、height、depthOrArrayLayers
```

`flipY` 改变复制时的行顺序，用于协调图片的上方、纹理第一个 texel 和 UV 的 V 方向。看到图片上下颠倒时，可以选择在复制阶段翻转，也可以翻转模型的 UV；项目中最好统一一种约定。

## 四、在 GPU 上生成 Mipmaps

Mip 数量可以这样计算：

```js
function numMipLevels(width, height) {
  return 1 + Math.floor(Math.log2(Math.max(width, height)));
}
```

例如最大边为 256：

```text
256 → 128 → 64 → 32 → 16 → 8 → 4 → 2 → 1
共 9 级
```

WebGPU 没有 `generateMipmap()`。常见 GPU 生成方式是：

```text
采样 mip 0，渲染到 mip 1
采样 mip 1，渲染到 mip 2
采样 mip 2，渲染到 mip 3
...
```

每次使用两个只暴露单级 mip 的 View：

```js
const sourceView = texture.createView({
  baseMipLevel: level - 1,
  mipLevelCount: 1,
});

const destinationView = texture.createView({
  baseMipLevel: level,
  mipLevelCount: 1,
});
```

`sourceView` 进入 BindGroup，被片元着色器采样；`destinationView` 作为 RenderPass 的颜色附件。使用线性过滤绘制全屏四边形，就能缩小上一层并写入下一层。

这再次说明 TextureView 的作用：同一个 GPUTexture 可以在一次 Pass 中把某一层当输入，同时把下一层当输出。

## 五、其他外部来源与纹理图集

`copyExternalImageToTexture` 不只接受 ImageBitmap，常见来源还包括：

- `HTMLCanvasElement` 和 `OffscreenCanvas`
- `HTMLImageElement`
- `HTMLVideoElement` 和 `VideoFrame`
- `ImageData`

Canvas 很适合动态文字、图表和 2D 绘制。视频也能逐帧复制，但大分辨率视频每帧复制成本很高；下一章会介绍专门的 External Texture，直接使用视频帧而不是复制全部像素。

当一个模型需要许多小图片时，可以把它们合并成 Texture Atlas：

```text
多张小图片 → 一张大纹理
模型不同区域 → 使用不同 UV 范围
```

这样能减少纹理和 BindGroup 切换，但需要处理图集边缘、padding、mipmap 泄漏和 UV 计算。

建议把加载流程封装成三个职责明确的函数：

```text
loadImageBitmap(url)               负责下载和解码
createTextureFromSource(device...) 负责分配 GPUTexture
copySourceToTexture(device...)      负责复制并生成 mips
```

这一章暂时记住一句话：

**浏览器负责把文件解码成 ImageBitmap，copyExternalImageToTexture 负责复制 mip 0，其余 mip levels 由我们自己在 GPU 上生成。**

配套示例：[`importing-textures.html`](./importing-textures.html)

# External Video Textures（高效使用视频）

原文：[WebGPU 高效使用视频](https://webgpufundamentals.org/webgpu/lessons/zh_cn/webgpu-textures-external-video.html)

上一章使用 `copyExternalImageToTexture`，把图片或视频当前帧复制到普通 `GPUTexture`。如果视频每秒更新 30 或 60 次，反复复制整张画面会产生额外带宽和格式转换成本。

本章的核心是 `device.importExternalTexture()`：让 WebGPU 把浏览器的视频帧作为 `GPUExternalTexture` 提供给 Shader。它的设计目标是让浏览器尽量直接使用解码器已有的数据；是否完全零复制仍取决于浏览器、操作系统和驱动实现。

## 一、和 WebGL 对比：复制视频与外部视频纹理

典型 WebGL 视频纹理需要在每帧更新时再次上传：

```js
gl.bindTexture(gl.TEXTURE_2D, texture);
gl.texImage2D(
  gl.TEXTURE_2D,
  0,
  gl.RGBA,
  gl.RGBA,
  gl.UNSIGNED_BYTE,
  video,
);
```

WebGPU 也可以采用复制路线：

```js
device.queue.copyExternalImageToTexture(
  { source: video },
  { texture: normalTexture },
  [video.videoWidth, video.videoHeight],
);
```

但本章采用外部纹理路线：

```js
const externalTexture = device.importExternalTexture({
  source: video,
});
```

两条路线的差异：

| 问题 | 复制到普通纹理 | 导入外部纹理 |
| --- | --- | --- |
| API | `copyExternalImageToTexture` | `importExternalTexture` |
| JS 得到的对象 | `GPUTexture` | `GPUExternalTexture` |
| WGSL 类型 | `texture_2d<f32>` | `texture_external` |
| 采样函数 | `textureSample` | `textureSampleBaseClampToEdge` |
| 数据处理 | 把当前帧复制进自己的纹理 | 尽量直接引用浏览器的视频数据 |
| mipmap | 可以自己生成 | 不支持，只采样 base level |
| 地址模式 | 可以 repeat、mirror-repeat | 固定 clamp-to-edge |
| 生命周期 | 由应用持有，可长期复用 | 很短，视频渲染时通常每帧重新导入 |
| 灵活性 | 可复制、生成 mip、当附件使用 | 只能通过外部纹理接口采样 |

普通纹理更灵活，外部纹理更适合持续变化的视频。选择依据不是“哪个永远更好”，而是需不需要 mipmap、复制、Storage Texture 或 Render Attachment 等能力。

## 二、为什么通常每帧都要重新导入

从 `HTMLVideoElement` 导入的 `GPUExternalTexture` 只代表视频在这一刻可用的帧。原文给出的精确规则是：外部纹理只保证在当前 JavaScript 任务结束前有效。它不能像普通 `GPUTexture` 一样创建一次后长期保存；对多数渲染循环来说，就是每次 `requestAnimationFrame` 或 `requestVideoFrameCallback` 都重新导入。

典型渲染循环是：

```js
function render() {
  const externalTexture = device.importExternalTexture({
    source: video,
  });

  const bindGroup = device.createBindGroup({
    layout: pipeline.getBindGroupLayout(0),
    entries: [
      { binding: 0, resource: sampler },
      { binding: 1, resource: externalTexture },
    ],
  });

  // 录制 Render Pass 并提交……
  requestAnimationFrame(render);
}
```

流程可以记成：

```text
浏览器解码出当前 Video 帧
  ↓
importExternalTexture
  ↓
创建引用本帧外部纹理的 BindGroup
  ↓
录制并提交本帧 Render Pass
  ↓
下一帧再次导入
```

因为 BindGroup 内部引用了外部纹理，所以获得新的外部纹理后通常也要建立新的 BindGroup。规范允许实现重复返回同一个对象，但程序不能依赖这种优化。

`GPUExternalTexture` 也不是 `GPUTexture` 的一种 View。它没有 `createView()`，不能加入 `GPUTextureUsage`，绑定时直接把对象作为资源：

```js
{ binding: 1, resource: externalTexture }
```

## 三、WGSL 中的特殊类型和限制

普通二维纹理：

```wgsl
@group(0) @binding(0) var imageSampler: sampler;
@group(0) @binding(1) var imageTexture: texture_2d<f32>;

let color = textureSample(imageTexture, imageSampler, uv);
```

外部视频纹理必须改成：

```wgsl
@group(0) @binding(0) var videoSampler: sampler;
@group(0) @binding(1) var videoTexture: texture_external;

let color = textureSampleBaseClampToEdge(
  videoTexture,
  videoSampler,
  uv,
);
```

`textureSampleBaseClampToEdge` 这个名字已经说明两个限制：

- `Base`：只采样 mip level 0，外部纹理没有 mipmap chain。
- `ClampToEdge`：坐标超出 `[0, 1]` 后钳制到边缘，Sampler 的 `repeat` 设置不会改变它。

外部纹理也可以用 `textureLoad` 做精确 texel 读取；当需要带 Sampler 的过滤采样时，必须使用这里的 `textureSampleBaseClampToEdge`，不能换成普通 `textureSample`。

如果确实需要重复画面，可以先在 Shader 中把 UV 变回 `[0, 1)`：

```wgsl
let repeatedUV = fract(uv * 3.0);
let color = textureSampleBaseClampToEdge(
  videoTexture,
  videoSampler,
  repeatedUV,
);
```

这只是手动重复 base level，并没有解决远处物体缺少 mipmap 时的闪烁问题。如果视频要贴在远处、倾斜或大幅缩小的 3D 表面上，复制到普通纹理并生成 mipmaps 可能反而更合适。

## 四、为什么视频需要 `texture_external`

图片通常很容易理解成一张 RGBA 像素表，但视频解码器输出的数据不一定是 RGBA。常见视频会把亮度和色度分开保存，例如 YUV：

```text
Y：亮度，通常分辨率较高
U、V：颜色差异信息，可能使用更低分辨率
```

如果强制先转成普通 RGBA 纹理，流程可能是：

```text
压缩视频
  ↓ 视频解码器
Y 平面 + UV 平面
  ↓ 颜色转换和复制
RGBA GPUTexture
  ↓ Shader 采样
```

外部纹理允许浏览器保留更接近解码器的表示：

```text
压缩视频
  ↓ 视频解码器
Y 平面 + UV 平面
  ↓ importExternalTexture 建立抽象
texture_external
  ↓ WebGPU 在采样过程中处理 YUV → RGB
Shader 得到 RGBA 颜色
```

因此 `texture_external` 看起来是一张纹理，底层却可能对应两张或多张纹理、颜色转换矩阵以及特殊 UV 变换。`textureSampleBaseClampToEdge` 给浏览器一个固定的采样入口，使浏览器能根据真实视频格式注入正确的采样与色彩转换逻辑。

WebGPU 这样设计还有一个 Web 平台原因：浏览器支持的视频编码和硬件解码格式会变化。应用只处理统一的 `texture_external`，不必针对每种设备自己编写 YUV 布局与颜色转换代码。

## 五、示例中的完整数据流

配套示例不下载外部视频，也不请求摄像头权限，而是在单个 HTML 中生成视频：

```text
Canvas 2D 动画
  ↓ canvas.captureStream(30)
MediaStream
  ↓ video.srcObject
HTMLVideoElement 当前帧
  ↓ device.importExternalTexture
GPUExternalTexture
  ↓ BindGroup
textureSampleBaseClampToEdge
  ↓
WebGPU Canvas
```

示例把 UV 默认放大到 2 倍，并提供“使用 `fract(uv)` 手动重复”开关：

- 开启时，Shader 用 `fract` 把 UV 折回 `[0, 1)`，画面重复出现。
- 关闭时，即使 Sampler 设置了 `repeat`，画面仍会在边缘拉伸，证明外部纹理使用 clamp-to-edge。
- 页面同时统计导入外部纹理和创建 BindGroup 的次数，证明它们位于逐帧渲染路径中。

真实项目还可以把来源换成普通网络视频或摄像头：

```js
const stream = await navigator.mediaDevices.getUserMedia({
  video: true,
});
video.srcObject = stream;
```

摄像头需要 HTTPS 或 localhost 等安全上下文，并且必须得到用户授权。是否镜像摄像头画面只是 UV 或变换矩阵的选择，与 `importExternalTexture` 本身无关。

这一章暂时记住一句话：

**`importExternalTexture` 用受限制的 `texture_external` 换取更高效的视频帧访问；它通常每帧重新导入，只能采样 base level，并由浏览器负责底层视频格式到 RGBA 的转换。**

配套示例：[`external-video.html`](./external-video.html)

# Cube Maps（立方体贴图）

原文：[WebGPU 立方体贴图](https://webgpufundamentals.org/webgpu/lessons/zh_cn/webgpu-cube-maps.html)

普通二维纹理回答的是“这个 UV 位置是什么颜色”；Cube Map 回答的是“从中心朝这个三维方向看过去是什么颜色”。

Cube Map 由六张大小、格式一致的正方形图片组成，分别代表：

```text
layer 0：+X
layer 1：-X
layer 2：+Y
layer 3：-Y
layer 4：+Z
layer 5：-Z
```

它的核心不是“把图片贴到立方体模型上”，而是把周围所有方向的颜色存进一个可按 `vec3f` 方向查询的纹理。环境反射、天空盒和基于图像的光照才是它最典型的用途。

## 一、二维纹理与 Cube Map 的区别

普通二维纹理使用二维坐标：

```wgsl
@group(0) @binding(0) var imageSampler: sampler;
@group(0) @binding(1) var imageTexture: texture_2d<f32>;

let color = textureSample(imageTexture, imageSampler, vec2f(u, v));
```

Cube Map 使用三维方向：

```wgsl
@group(0) @binding(0) var cubeSampler: sampler;
@group(0) @binding(1) var cubeTexture: texture_cube<f32>;

let color = textureSample(
  cubeTexture,
  cubeSampler,
  normalize(direction),
);
```

GPU 根据方向向量中绝对值最大的分量选择面：

```text
direction = ( 1, 0, 0) → +X → layer 0
direction = (-1, 0, 0) → -X → layer 1
direction = ( 0, 1, 0) → +Y → layer 2
direction = ( 0,-1, 0) → -Y → layer 3
direction = ( 0, 0, 1) → +Z → layer 4
direction = ( 0, 0,-1) → -Z → layer 5
```

例如 `(0.9, 0.2, -0.4)` 中 `|x|` 最大且 x 为正，因此选择 +X 面；y 和 z 再用于计算这个面内部的二维采样位置。面选择和面内 UV 计算都由纹理采样单元完成。

方向的长度通常不决定采样结果，方向相同的 `(1, 0, 0)` 与 `(10, 0, 0)` 会指向同一位置。实践中仍建议 `normalize(direction)`，尤其是方向来自顶点阶段插值时。

## 二、创建六层纹理并上传六个面

Cube Map 的底层资源不是六个互不相关的 `GPUTexture`，而是一个具有六个 array layer 的二维纹理：

```js
const cubeTexture = device.createTexture({
  size: [faceWidth, faceHeight, 6],
  dimension: "2d",
  format: "rgba8unorm",
  usage:
    GPUTextureUsage.TEXTURE_BINDING |
    GPUTextureUsage.COPY_DST |
    GPUTextureUsage.RENDER_ATTACHMENT,
});
```

这里第三个尺寸是 `depthOrArrayLayers`。因为 `dimension` 是 `"2d"`，它表示二维数组纹理的层数，不是一个真正三维纹理的深度。

这里不能漏掉 `RENDER_ATTACHMENT`。`copyExternalImageToTexture` 的目标纹理需要同时具有 `COPY_DST` 和 `RENDER_ATTACHMENT`；浏览器可能使用内部渲染步骤完成外部图像的颜色空间转换与复制。只设置 `COPY_DST` 会产生验证错误，六个面都无法写入，最终 Cube Map 就会采样到全黑内容。

上传时，每个来源进入一个固定 layer：

```js
faceSources.forEach((source, layer) => {
  device.queue.copyExternalImageToTexture(
    { source },
    {
      texture: cubeTexture,
      origin: { x: 0, y: 0, z: layer },
    },
    {
      width: source.width,
      height: source.height,
      depthOrArrayLayers: 1,
    },
  );
});
```

六个面的要求：

- 宽度和高度必须相等，也就是正方形。
- 六层尺寸和像素格式必须一致。
- 层顺序必须严格是 `+X、-X、+Y、-Y、+Z、-Z`。
- 六张图片的边缘内容应该能互相衔接，否则采样到接缝时会很明显。

示例使用六个 Canvas 2D 动态生成带方向文字的图片，再把它们分别上传到 0～5 层，因此单个 HTML 不依赖外部图片。

## 三、GPUTexture、TextureView 和 Shader 类型

六层 `GPUTexture` 只说明“资源里有六层”，还没有说明 Shader 应该如何解释这些层。真正让它成为 Cube Map 的是 `GPUTextureView`：

```js
const cubeView = cubeTexture.createView({
  dimension: "cube",
  baseArrayLayer: 0,
  arrayLayerCount: 6,
});
```

三者必须匹配：

```text
GPUTexture：二维纹理，包含六层像素存储
    ↓
GPUTextureView：dimension = "cube"
    ↓
WGSL：texture_cube<f32>
```

如果创建的是 `dimension: "2d-array"` 的 View，Shader 就应该声明 `texture_2d_array<f32>`，并由程序显式提供 layer；它不会根据三维方向自动选面。

绑定 Cube View 与绑定普通 TextureView 没有形式上的区别：

```js
const bindGroup = device.createBindGroup({
  layout: pipeline.getBindGroupLayout(0),
  entries: [
    { binding: 0, resource: sampler },
    { binding: 1, resource: cubeView },
  ],
});
```

关键区别存在于 View 的维度、BindGroupLayout 推导出的纹理维度，以及 WGSL 的纹理类型中。

## 四、和 WebGL 对比

WebGL 创建 Cube Map 时，会分别指定六个枚举目标：

```js
const targets = [
  gl.TEXTURE_CUBE_MAP_POSITIVE_X,
  gl.TEXTURE_CUBE_MAP_NEGATIVE_X,
  gl.TEXTURE_CUBE_MAP_POSITIVE_Y,
  gl.TEXTURE_CUBE_MAP_NEGATIVE_Y,
  gl.TEXTURE_CUBE_MAP_POSITIVE_Z,
  gl.TEXTURE_CUBE_MAP_NEGATIVE_Z,
];

gl.bindTexture(gl.TEXTURE_CUBE_MAP, texture);
targets.forEach((target, i) => {
  gl.texImage2D(
    target,
    0,
    gl.RGBA,
    gl.RGBA,
    gl.UNSIGNED_BYTE,
    faceImages[i],
  );
});
```

GLSL 中使用 `samplerCube`：

```glsl
uniform samplerCube u_cubeMap;
vec4 color = texture(u_cubeMap, normalize(direction));
```

对应关系：

| 概念 | WebGL | WebGPU |
| --- | --- | --- |
| 六面资源 | `TEXTURE_CUBE_MAP_*` 六个 target | 一个六层 `GPUTexture` |
| 指定上传面 | `texImage2D(target, ...)` | `origin.z = layer` |
| 声明为 Cube Map | 绑定 `TEXTURE_CUBE_MAP` | `createView({ dimension: "cube" })` |
| Shader 类型 | `samplerCube` | `texture_cube<f32>` + `sampler` |
| 采样 | `texture(samplerCube, direction)` | `textureSample(texture, sampler, direction)` |

WebGL 把纹理对象和目标绑定状态组合在 API 中；WebGPU 把像素存储、资源解释方式和采样器拆成 `GPUTexture`、`GPUTextureView` 与 `GPUSampler`。

## 五、方向、接缝和 Mipmaps

Cube Map 最常见的错误不是 API 写错，而是六张图的方向约定不一致：

- 层顺序错误，会让左右、上下或前后互换。
- 某一面需要旋转或镜像时没有处理，会在边界看到图案突然翻转。
- 相机、模型或资源采用的左右手坐标系不同，可能造成 Z 方向与预期相反。
- 使用普通二维图片拼成六面时，如果边缘颜色对不上，会出现明显接缝。

最实用的排查方式，就是像示例一样先给每层放入不同颜色和大号的 `+X/-X/+Y/-Y/+Z/-Z` 文字，再传入六个轴向方向逐一验证。

生产环境通常还需要 mipmaps。Cube Map 的每个 mip level 都有六层，所以生成流程是双重循环：

```text
for 每个 mip level：
  for 六个 array layer：
    用 dimension="2d" 的 View 采样上一 mip
    渲染到同一 layer 的下一 mip
```

生成每一面 mip 时使用单层 `2d` View；最终交给业务 Shader 采样时，才使用覆盖六层的 `cube` View。用于高质量环境反射时，还会根据材质粗糙度预过滤不同 mip level，这属于后续环境贴图与基于图像光照的内容。

本例把 Cube Map 直接显示在一个立方体模型上，是为了让六个方向容易观察。真实项目更常见的数据流是：

```text
天空方向 / 反射方向 / 折射方向
  ↓
textureSample(cubeMap, sampler, direction)
  ↓
获得该方向对应的环境颜色
```

这一章暂时记住一句话：

**Cube Map 是一个按 `+X、-X、+Y、-Y、+Z、-Z` 排列的六层二维纹理，通过 cube TextureView 暴露给 `texture_cube<f32>`，Shader 使用三维方向而不是二维 UV 采样。**

配套示例：[`cube-maps.html`](./cube-maps.html)

# Storage Textures（存储纹理）

原文：[WebGPU 存储纹理](https://webgpufundamentals.org/webgpu/lessons/zh_cn/webgpu-storage-textures.html)

普通纹理通常由 Render Pass、复制命令或 CPU 上传间接更新；Storage Texture 允许 Shader 使用整数像素坐标直接读取或写入纹理。

它不是另一种特殊的 `GPUTexture` 类，仍然通过 `device.createTexture()` 创建。决定它能否作为存储纹理使用的是 `GPUTextureUsage.STORAGE_BINDING`，以及 WGSL 中的 `texture_storage_*` 声明。

## 一、Storage Buffer 与 Storage Texture

如果用 Storage Buffer 表示二维像素，需要自己把二维坐标转换为一维索引：

```wgsl
@group(0) @binding(0)
var<storage, read_write> pixels: array<vec4f>;

fn pixelIndex(position: vec2u, width: u32) -> u32 {
  return position.y * width + position.x;
}

pixels[pixelIndex(position, width)] = color;
```

Storage Texture 直接理解二维坐标：

```wgsl
@group(0) @binding(0)
var image: texture_storage_2d<rgba8unorm, write>;

textureStore(image, position, color);
```

主要区别：

| 问题 | Storage Buffer | Storage Texture |
| --- | --- | --- |
| 数据布局 | 一维字节或元素数组 | 具有宽、高、层和 mip 的纹理布局 |
| 二维寻址 | 自己计算 `y * width + x` | 直接传入 `vec2u(x, y)` |
| 尺寸 | 根据绑定范围计算长度 | `textureDimensions(texture)` |
| 格式转换 | 自己解释字节 | 按纹理格式自动打包和解包 |
| 后续普通采样 | 不能直接使用 Sampler | 同一 GPUTexture 可换 View 后作为普通纹理采样 |
| 可存数据 | 任意符合对齐规则的结构 | 受 Storage Texture 格式列表限制 |

例如 `rgba8unorm` 每个 texel 只占 4 字节。Shader 写入 `vec4f(1.0, 0.5, 0.0, 1.0)` 时，纹理格式会自动把四个 0～1 浮点数编码为四个 8 位通道。Storage Buffer 不会自动提供这种格式转换。

因此选择原则是：数据天然是图片、体素或规则网格时优先考虑 Storage Texture；数据是对象结构、变长列表或复杂记录时更适合 Storage Buffer。

## 二、创建与声明 Storage Texture

创建普通 GPUTexture 时加入 `STORAGE_BINDING`：

```js
const texture = device.createTexture({
  size: [width, height],
  format: "rgba8unorm",
  usage:
    GPUTextureUsage.STORAGE_BINDING |
    GPUTextureUsage.TEXTURE_BINDING |
    GPUTextureUsage.COPY_SRC,
});
```

每个 usage 都代表一种允许的角色：

- `STORAGE_BINDING`：允许作为 `texture_storage_2d` 绑定。
- `TEXTURE_BINDING`：允许之后作为普通 `texture_2d` 采样。
- `COPY_SRC`：允许把结果复制到 Buffer 或其他纹理。

WGSL 必须明确写出维度、像素格式和访问模式：

```wgsl
@group(0) @binding(0)
var outputTexture: texture_storage_2d<rgba8unorm, write>;
```

三个信息不能只写一部分：

```text
texture_storage_2d：二维存储纹理
rgba8unorm：内存中的确切纹理格式
write：本 Shader 只能写
```

普通 `texture_2d<f32>` 只声明采样结果类型，因为格式转换由采样系统处理；Storage Texture 直接执行 texel 读写，所以 Pipeline 必须提前知道真实存储格式。

访问模式包括 `read`、`write` 和 `read_write`，但不是所有格式都支持所有模式。核心规范中 `read_write` 主要适用于 `r32float`、`r32sint`、`r32uint`；其他可存储格式通常只能在单个绑定中选择只读或只写。

常见 Storage Texture 格式包括：

```text
rgba8unorm / rgba8snorm / rgba8uint / rgba8sint
rgba16float / rgba16uint / rgba16sint
rg32float / rg32uint / rg32sint
rgba32float / rgba32uint / rgba32sint
r32float / r32uint / r32sint
```

实际使用前应检查规范和 Adapter Features，因为可选特性会扩展格式能力。

## 三、textureLoad、textureStore 与普通采样

Storage Texture 使用整数 texel 坐标：

```wgsl
let size = textureDimensions(storageTexture);
let position = vec2u(20, 30);

let oldValue = textureLoad(storageTexture, position);
textureStore(storageTexture, position, newValue);
```

它不使用 `GPUSampler`，也没有普通纹理采样提供的功能：

- 不会根据浮点 UV 做过滤。
- 不会在线性过滤时混合周围多个 texel。
- 不会根据像素覆盖范围自动选择 mip level。
- 不会应用 repeat、mirror-repeat 或 clamp-to-edge 地址模式。

它表达的是精确的“读这个 texel”或“写这个 texel”。越界的 `textureStore` 不应该依赖某种自动钳制行为，Compute Shader 应在写入前检查：

```wgsl
let size = textureDimensions(outputTexture);

if (id.x >= size.x || id.y >= size.y) {
  return;
}

textureStore(outputTexture, id.xy, color);
```

同一个 GPUTexture 可以在一个 Pass 中作为 Storage Texture 写入，在后续 Pass 中通过 `texture_2d` 和 Sampler 采样。不能在同一个 Pass 中让重叠的纹理子资源既作为可写 Storage Binding，又作为普通采样输入；Pass 边界帮助 WebGPU 建立正确的资源状态和执行顺序。

## 四、直接把 Canvas 当作 Storage Texture

Canvas 的当前纹理同样可以增加 `STORAGE_BINDING`：

```js
context.configure({
  device,
  format: canvasFormat,
  usage:
    GPUTextureUsage.STORAGE_BINDING |
    GPUTextureUsage.TEXTURE_BINDING |
    GPUTextureUsage.RENDER_ATTACHMENT,
});
```

这里有一个格式问题：`navigator.gpu.getPreferredCanvasFormat()` 通常返回 `rgba8unorm` 或 `bgra8unorm`，但核心规范默认不能把 `bgra8unorm` 当作 Storage Texture。

需要检查并按需启用 `bgra8unorm-storage`：

```js
const preferredFormat = navigator.gpu.getPreferredCanvasFormat();
const hasBGRAStorage = adapter.features.has("bgra8unorm-storage");

const device = await adapter.requestDevice({
  requiredFeatures:
    preferredFormat === "bgra8unorm" && hasBGRAStorage
      ? ["bgra8unorm-storage"]
      : [],
});

const canvasFormat =
  preferredFormat === "bgra8unorm" && !hasBGRAStorage
    ? "rgba8unorm"
    : preferredFormat;
```

如果系统首选 BGRA 且支持该 Feature，就请求启用后继续使用 BGRA；如果不支持，则把 Canvas 明确配置成 `rgba8unorm`。

Canvas 当前纹理属于交换链，每帧都要重新获得：

```js
const currentTexture = context.getCurrentTexture();
const bindGroup = device.createBindGroup({
  layout: pipeline.getBindGroupLayout(0),
  entries: [
    {
      binding: 0,
      resource: currentTexture.createView(),
    },
  ],
});
```

示例没有创建 RenderPipeline，而是只运行 Compute Pass：

```js
const pass = encoder.beginComputePass();
pass.setPipeline(computePipeline);
pass.setBindGroup(0, bindGroup);
pass.dispatchWorkgroups(
  Math.ceil(texture.width / 8),
  Math.ceil(texture.height / 8),
);
pass.end();
```

Workgroup 使用 `8 × 8`，一次处理 64 个像素。dispatch 数量向上取整，保证覆盖完整纹理；边缘多出来的 invocation 由 WGSL 尺寸检查提前退出。

## 五、WebGL 对比与竞态条件

标准 WebGL 2 没有 Compute Shader，也没有与 `textureStore` 对应的通用 Storage Texture 写入。最接近的做法是把纹理挂到 Framebuffer，通过 Fragment Shader 绘制一个全屏三角形：

```text
WebGL：
全屏几何 → 光栅化 → Fragment Shader → Framebuffer Texture

WebGPU Storage Texture：
Compute invocation → textureStore → 指定 texel
```

WebGL 的方式仍由光栅化决定哪些片元运行；WebGPU Compute Shader 可以按一维、二维或三维任务网格调度，并自由计算要写入的坐标，更适合图像处理、模拟、程序化纹理、体素和通用 GPU 计算。

自由写入也意味着程序要自己避免竞态。GPU 不保证不同 invocation 的执行顺序：

```text
安全：每个 invocation 只写 global_invocation_id 对应的唯一像素
危险：很多 invocation 同时读取、修改、写回同一个像素
```

本章示例属于安全情况：一个 invocation 对应一个唯一像素。模糊、扩散、流体模拟等算法常使用两个纹理进行 ping-pong：本轮只读 A、只写 B，下一轮交换；这样不会在同一次 Dispatch 中一边更新、一边读取结果尚未确定的邻居。

这一章暂时记住一句话：

**Storage Texture 是带 `STORAGE_BINDING` usage 的普通 GPUTexture；WGSL 必须声明准确格式和访问模式，Compute Shader 用整数坐标通过 `textureLoad/textureStore` 精确读写 texel。**

配套示例：[`storage-textures.html`](./storage-textures.html)

# Multisampling / MSAA（多重采样抗锯齿）

原文：[WebGPU 多重采样](https://webgpufundamentals.org/webgpu/lessons/zh_cn/webgpu-multisampling.html)

屏幕是离散像素网格，三角形边缘却是连续直线。一条斜边穿过像素时，单采样通常只检查像素中心是否被三角形覆盖，于是边缘只能在“完整写入”和“完全不写”之间跳变，形成阶梯状锯齿。

MSAA 是 Multi-Sampling Anti-Aliasing。它在每个像素内部保存多个几何覆盖样本，让边缘像素能够表达“这个三角形覆盖了像素的四分之一、二分之一或四分之三”，最后把多个样本解析成一个普通像素。

## 一、MSAA 与提高渲染分辨率的区别

一种直接抗锯齿方法是把宽和高都放大两倍，再缩小到原分辨率：

```text
2 倍宽 × 2 倍高
= 4 倍像素
= Fragment Shader 最多执行 4 倍
```

这叫 Supersampling。它对几何边缘和 Shader 内部细节都有效，但成本很高，因为三角形内部那些本来已经完全覆盖的像素也会执行四次 Fragment Shader。

4× MSAA 仍然在一个最终像素中记录四个覆盖样本，但通常每个被覆盖像素只运行一次 Fragment Shader，然后把同一个结果写进三角形实际覆盖到的那些样本：

```text
单采样边缘像素：
检查 1 个位置 → 覆盖或不覆盖

4× MSAA 边缘像素：
检查 4 个非规则采样位置 → 记录 0～4 个覆盖结果
通常只运行 1 次 Fragment Shader → 写入被覆盖样本
```

最终 Resolve 会根据四个样本生成一个单采样像素。它不是把一个规则 `2 × 2` 像素网格做双线性缩小；具体采样位置和解析由 GPU 决定。

MSAA 的优势是比完整的 4 倍 Supersampling 少执行大量 Fragment Shader。代价是多重采样颜色附件、深度附件仍需要为每个像素保存多个样本，占用更多显存和带宽。

## 二、WebGPU 中需要匹配的三个 count

启用 4× MSAA 需要三个对象彼此匹配。

第一，RenderPipeline 声明自己要渲染到 4 样本附件：

```js
const pipeline = device.createRenderPipeline({
  // vertex、fragment 等配置……
  multisample: {
    count: 4,
  },
});
```

第二，创建真正保存四个样本的颜色纹理：

```js
const multisampleTexture = device.createTexture({
  size: [width, height],
  format: presentationFormat,
  usage: GPUTextureUsage.RENDER_ATTACHMENT,
  sampleCount: 4,
});
```

第三，Render Pass 的 `view` 必须来自这个 4 样本纹理：

```js
colorAttachments: [{
  view: multisampleTexture.createView(),
  resolveTarget: canvasTexture.createView(),
  loadOp: "clear",
  storeOp: "discard",
}]
```

对应关系：

```text
Pipeline multisample.count = 4
             ↓ 必须相等
颜色附件 texture.sampleCount = 4
             ↓ Resolve
resolveTarget.sampleCount = 1
```

Pipeline count 和颜色附件 sampleCount 不一致会产生验证错误。使用深度或模板时，深度纹理的 `sampleCount` 也必须等于颜色附件。

WebGPU 当前核心版本使用 `count: 1` 或 `count: 4`。1 是默认值，表示没有多重采样；不能假设 2、8 或 16 在 WebGPU 1 中可用。

## 三、Resolve 与附件生命周期

Canvas 的交换链纹理是单采样纹理，不能直接作为 4× MSAA Pipeline 的颜色附件。因此渲染路径中需要一个中间纹理：

```text
三角形
  ↓ 4× MSAA RenderPipeline
Multisample Color Texture
  ↓ Render Pass 结束时 Resolve
单采样 Canvas Texture
  ↓
显示器
```

`resolveTarget` 告诉 WebGPU：这个 Render Pass 结束时，把 `view` 中的多样本结果解析到目标单采样纹理。Resolve 后如果不再读取多重采样附件，可以使用：

```js
storeOp: "discard"
```

这表示无需保留中间附件内容，但不会丢弃已经写入 `resolveTarget` 的解析结果。

多重采样纹理必须与 Resolve Target 具有相同的宽、高和像素格式。Canvas 尺寸变化时，要销毁并重新创建 MSAA 纹理：

```js
if (
  !msaaTexture ||
  msaaTexture.width !== canvasTexture.width ||
  msaaTexture.height !== canvasTexture.height
) {
  msaaTexture?.destroy();
  msaaTexture = device.createTexture({
    size: [canvasTexture.width, canvasTexture.height],
    format: canvasTexture.format,
    usage: GPUTextureUsage.RENDER_ATTACHMENT,
    sampleCount: 4,
  });
}
```

如果多个 Render Pass 连续写同一个多重采样附件，不必每个 Pass 都 Resolve。通常在最后一个 Pass 才设置 `resolveTarget`；中间 Pass 使用 `loadOp: "load"` 继续保留已有样本。

## 四、MSAA 能解决什么，不能解决什么

MSAA 最擅长处理光栅化几何边缘：

- 三角形轮廓。
- 模型相互遮挡的边界。
- 深度测试形成的边缘。
- Alpha-to-coverage 等依赖覆盖样本的技术。

它通常不能自动解决三角形内部的高频变化：

- 纹理缩小时产生的闪烁，应使用 mipmaps 和各向异性过滤等方案。
- Shader 生成的细线、棋盘格或程序化高频图案，可能需要导数、过滤或后处理抗锯齿。
- 透明 Alpha 混合边缘不会只因为启用 MSAA 就自动正确，需要 alpha-to-coverage 或专门策略。
- Temporal Aliasing 是跨帧闪烁，通常需要 TAA 等时间方案。

默认情况下，MSAA 一个像素中的多个覆盖样本通常共享一次 Fragment Shader 结果。如果需要逐样本执行，可以使用 `@interpolate(..., sample)` 和 `@builtin(sample_index)`，但 Fragment Shader 成本会明显提高。

WGSL 还提供 `@builtin(sample_mask)`：作为 Fragment 输入时可查看哪些样本被覆盖，作为输出时可以屏蔽部分样本。它属于高级逐样本控制，普通 4× MSAA 不需要手工处理。

阶段间变量默认以像素中心进行插值：

```wgsl
@location(0) value: vec3f
```

边缘像素的中心可能位于三角形外，但部分 MSAA 样本位于三角形内。如果计算要求插值位置一定在被覆盖区域中，可以使用：

```wgsl
@location(0)
@interpolate(perspective, centroid)
value: vec3f
```

`centroid` 会选择三角形覆盖区域内的某个位置进行插值，避免边缘处出现超出三角形范围的插值值。

## 五、和 WebGL 对比

WebGL 创建默认 Canvas 时通常通过 Context 参数请求抗锯齿：

```js
const gl = canvas.getContext("webgl2", {
  antialias: true,
});
```

浏览器决定默认 Framebuffer 是否以及如何启用多重采样。对于离屏纹理，WebGL 2 需要多重采样 Renderbuffer，并通过 `blitFramebuffer` 解析到普通纹理：

```text
Multisample Renderbuffer
  ↓ gl.blitFramebuffer
Single-sample Texture
```

WebGPU 把这些关系显式写进资源和 Render Pass：

| 概念 | WebGL 2 | WebGPU |
| --- | --- | --- |
| 默认 Canvas MSAA | `antialias: true`，由浏览器决定 | 自己创建多重采样附件 |
| 样本数 | 查询实现或设置 Renderbuffer | Pipeline 与 Texture 明确 `count: 4` |
| 中间资源 | Multisample Renderbuffer | `sampleCount: 4` 的 GPUTexture |
| 解析 | `blitFramebuffer` | `resolveTarget` |
| 尺寸变化 | 重建 Renderbuffer | 重建 Multisample Texture |

配套示例把同一个 Canvas 分成左右两半：右半边先经过 4× MSAA 附件并 Resolve，左半边随后以 `loadOp: "load"` 保留右侧内容，再直接单采样绘制。降低“内部渲染比例”可以放大像素，更清楚地观察两侧几何斜边的差异。

这一章暂时记住一句话：

**4× MSAA 需要 count 为 4 的 Pipeline 和颜色/深度附件，并在 Render Pass 结束时通过 resolveTarget 转成单采样结果；它主要改善几何覆盖边缘，不等于纹理过滤或全场景超采样。**

配套示例：[`multisampling.html`](./multisampling.html)

# Immediates（即时变量）

原文：[WebGPU Immediates](https://webgpufundamentals.org/webgpu/lessons/zh_cn/webgpu-immediates.html)

> Immediates 是 2026 年加入 WebGPU 的新核心功能。过渡期内并非所有浏览器都已实现，示例会检测 `GPURenderPassEncoder.prototype.setImmediates`，不支持时自动运行 Uniform Buffer 回退路径。

Immediates 用来把极少量数据直接记录进 Render Pass 或 Compute Pass 命令中，不需要为这几字节创建 GPUBuffer、BindGroup 和 Binding。

它很像一个迷你 Uniform Buffer，但更适合“这一条 Draw/Dispatch 命令马上要用”的索引、标志和 ID。

## 一、Uniform 与 Immediate 的区别

Uniform 路径需要资源和绑定关系：

```text
TypedArray
  ↓ queue.writeBuffer
GPUBuffer
  ↓ createBindGroup
BindGroup
  ↓ pass.setBindGroup
var<uniform>
```

Immediate 路径直接把数据写入 Pass 的当前状态：

```text
TypedArray
  ↓ pass.setImmediates
var<immediate>
```

基本 WGSL：

```wgsl
struct DrawParameters {
  color: vec4f,
  offset: vec2f,
};

var<immediate> drawParameters: DrawParameters;
```

JavaScript 在 Draw 之前设置：

```js
pass.setImmediates(0, new Float32Array([
  1, 0, 0, 1,  // color
  -0.4, 0.2,   // offset
]));
pass.draw(3);
```

`setImmediates` 的参数形式：

```js
pass.setImmediates(
  byteOffset,
  source,
  sourceOffset?,
  size?,
);
```

- `byteOffset` 是 Immediate 存储区域中的字节偏移。
- `source` 是 `ArrayBuffer` 或 `ArrayBufferView`。
- `sourceOffset` 和 `size` 按 source 的元素计算，不一定是字节。
- 省略后两个参数表示复制整个 source。

它与 Uniform 对比：

| 问题 | Uniform Buffer | Immediates |
| --- | --- | --- |
| WGSL | `var<uniform>` | `var<immediate>` |
| 是否需要 Binding | 需要 | 不需要 |
| 是否需要 GPUBuffer | 需要 | 不需要 |
| 容量 | 受 Uniform Binding 限制 | 核心保证至少 64 字节 |
| 数量 | 可以有多个绑定 | 每个 Shader 只有一个 Immediate 变量 |
| 生命周期 | Buffer 内容持续存在 | Pass 状态中的短期数据 |
| 典型用途 | 相机矩阵、全局参数、大块 Draw 数据 | 索引、ID、标志、少量标量 |

## 二、容量、布局和初始化规则

核心规范保证的 Immediate 容量是 64 字节，可以通过 Device Limit 查看：

```js
device.limits.maxImmediateSize
```

某些 Adapter 可能提供更大上限，并允许通过 `requiredLimits` 申请。但跨设备应用不能默认容量一定超过 64 字节。

Immediate 使用和 Uniform、Storage Buffer 相同的 WGSL 内存布局规则。下面这个结构不是 24 字节布局就可以随意拼接：

```wgsl
struct Parameters {
  color: vec4f, // offset 0，16 字节
  offset: vec2f, // offset 16，8 字节
};
```

成员的对齐、offset 和 padding 仍需按 WGSL 布局计算。不能因为数据没有进入 GPUBuffer，就忽略对齐规则。

Immediate 内容不会像新 GPUBuffer 一样自动初始化为 0。Shader 会读取到的所有 Immediate 字节都必须在 Draw/Dispatch 前通过 `setImmediates` 初始化，否则会产生验证错误。

Immediate 状态会在这些边界变回未定义：

- 开始新的 Render Pass 或 Compute Pass。
- 执行 Render Bundle 时。
- Render Bundle 执行结束后。

因此不能依赖“上一个 Pass 已经设置过”。每个会使用 Immediate 的 Pass 都要重新完整设置。

浏览器过渡期检测方法：

```js
const canUseImmediates =
  typeof GPURenderPassEncoder !== "undefined" &&
  typeof GPURenderPassEncoder.prototype.setImmediates === "function";
```

只有检测通过后才能编译包含 `var<immediate>` 的 WGSL；旧浏览器连这种语法都可能无法解析，所以不能先无条件创建 ShaderModule 再决定是否调用。

## 三、最实用的模式：传递索引

64 字节看起来很小，但可以把大数据放在 Storage Buffer 中，只通过 Immediate 选择本次绘制使用的记录：

```wgsl
struct Model {
  matrix: mat4x4f,
};

struct Material {
  color: vec4f,
  roughness: f32,
};

@group(0) @binding(0)
var<storage, read> models: array<Model>;

@group(0) @binding(1)
var<storage, read> materials: array<Material>;

struct DrawIndices {
  modelIndex: u32,
  materialIndex: u32,
};

var<immediate> drawIndices: DrawIndices;
```

Vertex Shader 和 Fragment Shader 根据两个索引读取真正的数据：

```wgsl
let model = models[drawIndices.modelIndex];
let material = materials[drawIndices.materialIndex];
```

每次 Draw 只传 8 字节：

```js
pass.setImmediates(
  0,
  new Uint32Array([modelIndex, materialIndex]),
);
pass.draw(vertexCount);
```

这种设计把数据分成三层：

```text
全局 Uniform：相机、时间等所有 Draw 共享的数据
Storage Buffer：全部模型与全部材质的大数组
Immediates：本次 Draw 选择的 model/material 索引
```

相比为每个对象创建一个小 Uniform Buffer 和 BindGroup，它减少了资源对象数量、BindGroup 切换和逐 Draw 内存管理。它不一定减少 Draw Call 数量；它解决的是少量逐命令参数如何低成本传入。

## 四、何时使用，何时不要使用

适合放进 Immediates：

- `modelIndex`、`materialIndex`、`objectId`。
- 位标志和分支模式。
- 很小的颜色、偏移、缩放或阈值。
- Compute Dispatch 的任务索引或少量尺寸参数。

不适合：

- 大型矩阵数组、骨骼数据和灯光列表。
- 大量材质属性。
- 需要许多 Shader 同时共享和长期保留的数据。
- 频繁变化但已经能通过实例化一次 Draw 处理的数据。

不要因为 4×4 矩阵恰好是 64 字节，就默认把每个矩阵都塞进 Immediates。传一个 `modelIndex` 往往更灵活：矩阵留在 GPU Storage Buffer 中，同一记录还能被多个 Pass 使用。

Immediates 也不是实例化的替代品。大量相同几何通常应该优先考虑一次 `draw(..., instanceCount)`，使用 `instance_index` 选择数据；当对象必须分别 Draw、但只需改变几个参数时，Immediates 才更合适。

## 五、和 WebGL 对比及兼容回退

WebGL 的 `gl.uniform*` 看起来也能在 Draw 前直接设置少量值：

```js
gl.uniform2f(offsetLocation, x, y);
gl.drawArrays(gl.TRIANGLES, 0, 3);
```

但 WebGL Uniform 是 Program 的全局状态，通过 Location 修改；WebGPU Immediates 是 Command Pass 明确记录的一块小型状态，不使用 Uniform Location，也不创建绑定资源。

在尚未支持 Immediates 的浏览器中，可以退回：

- 每个 Draw 一个小 Uniform Buffer 与 BindGroup。
- 一个大 Uniform Buffer 配合 Dynamic Offset。
- 把数据放进 Storage Buffer，并用 `instance_index` 或其他已有索引选择。
- 合并对象为 Instanced Draw，减少逐 Draw 参数更新。

配套示例在支持时真正运行 `var<immediate>`；不支持时为 48 个 Draw 准备小 Uniform Buffer 与 BindGroup，传入完全相同的两个 u32。页面显示当前路径和逐 Draw 资源数量，因此能直接看到新 API 要消除的管理成本。

这一章暂时记住一句话：

**Immediates 是每个 Pass 中一块至少 64 字节、无需 Binding 的小型参数区；最有价值的用法是传索引和标志，让 Shader 去大型 Buffer 中选择真正的模型与材质数据。**

配套示例：[`immediates.html`](./immediates.html)

# Constants（管线可覆盖常量）

原文：[WebGPU 着色器常量](https://webgpufundamentals.org/webgpu/lessons/zh_cn/webgpu-constants.html)

这一章只讲一个新概念：WGSL 的 `override`。

它是“写在 Shader 中、创建 Pipeline 时才确定最终值”的常量。它适合创建少量固定的 Shader 变体，不适合传递每帧都会变化的数据。

## 一、override 到底解决什么问题

先在 WGSL 中声明可覆盖常量：

```wgsl
override red = 0.0;
override green = 0.0;
override blue = 0.0;

@fragment
fn fs() -> @location(0) vec4f {
  return vec4f(red, green, blue, 1.0);
}
```

如果创建 Pipeline 时什么都不传，就使用 WGSL 中的默认值，得到黑色。也可以在 `fragment.constants` 中覆盖它们：

```js
const pipeline = device.createRenderPipeline({
  layout: "auto",
  vertex: {
    module,
    entryPoint: "vs",
  },
  fragment: {
    module,
    entryPoint: "fs",
    targets: [{ format }],
    constants: {
      red: 1,
      green: 0.5,
      blue: 1,
    },
  },
});
```

这里最重要的生命周期是：

```text
WGSL 源码
   ↓ createShaderModule（此时 override 还可以没有最终值）
GPUShaderModule
   ↓ createRenderPipeline + constants（在这里确定最终值）
GPURenderPipeline
   ↓ draw（绘制时不能再修改这条 Pipeline 的 override）
```

改变原来的 JavaScript `constants` 对象不会改变已经创建好的 Pipeline。要使用另一组值，必须创建另一条 Pipeline。

`override` 只能是标量，即 `bool`、整数或浮点数，不能直接是 `vec3f`、矩阵、数组或结构体。示例把颜色拆成 `red`、`green`、`blue`，只是为了让结果容易观察；实际项目通常不会用 Override 频繁改变物体颜色。

## 二、默认值、必填值和数字 ID

三种写法放在一起看最清楚：

```wgsl
override red: f32;                 // 没有默认值：Pipeline 必须提供
@id(123) override green = 0.0;    // 有默认值，也可以通过数字 ID 覆盖
override blue = 0.0;              // 有默认值，可以省略
```

对应的 Pipeline 配置：

```js
fragment: {
  module,
  entryPoint: "fs",
  targets: [{ format }],
  constants: {
    red: 1,      // 使用变量名
    "123": 0.5, // 使用 @id；对象的键最终是字符串
    blue: 1,
  },
}
```

- 有默认值：JavaScript 不传时使用 WGSL 默认值。
- 没有默认值：当前入口点如果用到了它，创建 Pipeline 时就必须传入。
- `@id(123)`：既可以使用 `green`，也可以使用 `"123"` 作为键；保留 ID 后，WGSL 变量改名不会影响 JavaScript 配置。
- 漏传必填值、传入不存在的键或值无法转换成声明类型，都会使 Pipeline 创建失败。

配套示例中的 `@id(7) override stripeWidth: f32` 没有默认值，因此每一条 Pipeline 的 `fragment.constants` 都必须提供 `"7"`。

## 三、为什么 Vertex 和 Fragment 能得到不同的值

`constants` 不在 Pipeline 顶层，而是分别属于 `vertex`、`fragment` 或 `compute` 阶段。即使两个入口点来自同一个 ShaderModule，并且使用同名的 Override，它们也可以获得不同的值：

```js
const pipeline = device.createRenderPipeline({
  vertex: {
    module,
    entryPoint: "vs",
    constants: {
      red: 1,
      green: 1,
      blue: 0,
    },
  },
  fragment: {
    module,
    entryPoint: "fs",
    targets: [{ format }],
    constants: {
      red: 1,
      green: 0.2,
      blue: 0.5,
    },
  },
});
```

原因是 WebGPU 会独立评估每个入口点：

```text
同一个 GPUShaderModule
  ├─ VS 能访问的代码 + vertex.constants   → Vertex Stage
  └─ FS 能访问的代码 + fragment.constants → Fragment Stage
```

可以把它理解成：创建 Vertex Stage 时，与 `vs` 无关的代码暂时不存在；创建 Fragment Stage 时，与 `fs` 无关的代码也暂时不存在。Override 先应用到当前阶段，然后才生成这个入口点对应的 Shader。

所以，某个没有默认值的 Override 如果只被 Fragment Shader 使用，就只需要在 `fragment.constants` 中提供。配套示例中的：

- `inset` 只影响顶点位置，因此放在 `vertex.constants`。
- `stripeWidth` 只影响片元条纹，因此放在 `fragment.constants`。
- `red/green/blue` 两个阶段都使用，但每个阶段可以得到不同颜色。

## 四、和 WebGL 对比：不要把 Override 当成 Uniform

WebGL 没有与 `override` 完全相同的 API。最接近它的是“修改 GLSL 宏或源码，然后重新编译并链接 Program”。

### WebGL 的编译期变体

```js
const fragmentSource = `#version 300 es
  precision highp float;

  #define RED   1.0
  #define GREEN 0.5
  #define BLUE  1.0

  out vec4 outColor;

  void main() {
    outColor = vec4(RED, GREEN, BLUE, 1.0);
  }
`;

const fragmentShader = gl.createShader(gl.FRAGMENT_SHADER);
gl.shaderSource(fragmentShader, fragmentSource);
gl.compileShader(fragmentShader);

// 还需要把 Vertex Shader 和 Fragment Shader 链接成新 Program。
const program = gl.createProgram();
gl.attachShader(program, vertexShader);
gl.attachShader(program, fragmentShader);
gl.linkProgram(program);
```

如果把 `RED` 从 `1.0` 改成 `0.2`，就需要生成另一份 GLSL、重新编译 Shader，并重新链接 Program。这种“宏值在编译期固定”的语义最接近 WebGPU Override。

WebGPU 把这些变化从 WGSL 字符串中提取出来：

```js
const module = device.createShaderModule({ code }); // 同一个模块

const pinkPipeline = device.createRenderPipeline({
  // ...
  fragment: {
    module,
    targets: [{ format }],
    constants: { red: 1, green: 0.5, blue: 1 },
  },
});

const bluePipeline = device.createRenderPipeline({
  // ...
  fragment: {
    module,
    targets: [{ format }],
    constants: { red: 0.2, green: 0.5, blue: 1 },
  },
});
```

两条 Pipeline 共用同一个 ShaderModule，但仍然是两条不同的 Pipeline。Override 省掉的是“由应用自己拼接许多 WGSL 字符串并创建许多 ShaderModule”，不是让 Pipeline 可以免费、随时修改。

### WebGL Uniform 是另一种生命周期

WebGL 中也可以用 Uniform 改颜色：

```glsl
uniform vec3 u_color;

void main() {
  outColor = vec4(u_color, 1.0);
}
```

```js
gl.useProgram(program);
gl.uniform3f(colorLocation, 1, 0.5, 1);
gl.drawArrays(gl.TRIANGLES, 0, 3);

gl.uniform3f(colorLocation, 0.2, 0.5, 1); // 不用重新链接 Program
gl.drawArrays(gl.TRIANGLES, 0, 3);
```

这对应的是 WebGPU Uniform Buffer，而不是 Override：Uniform 是运行时数据，可以在 Draw 之间改变；Override 是创建 Pipeline 时的固定配置，Pipeline 创建后不能改变。

| 想表达的内容 | WebGL | WebGPU |
| --- | --- | --- |
| 永远写死在 Shader 中 | GLSL `const` | WGSL `const` |
| 少量编译期 Shader 变体 | `#define` / 拼接 GLSL，再编译和链接 Program | WGSL `override`，在创建 Pipeline 时传 `constants` |
| 每帧或每次 Draw 改值 | `uniform` + `gl.uniform*` | Uniform Buffer；极少量逐 Draw 数据也可考虑 Immediates |
| 改值后是否要创建新执行对象 | 宏变体要创建新 Program；Uniform 不需要 | Override 要创建新 Pipeline；Uniform 不需要 |

入口点独立性也能对应起来：WebGL 的 Vertex Shader 和 Fragment Shader 原本就是两个分开编译的 Shader，因此可以给两个阶段拼入不同的 `#define`。WebGPU 即使把 VS 和 FS 写在同一个 WGSL ShaderModule 中，也能分别通过 `vertex.constants` 和 `fragment.constants` 得到相同效果。

配套示例用一个 ShaderModule 创建三条 Pipeline。中间栏的控件只是在修改准备传给下一条 Pipeline 的参数；只有点击“应用并重建 Pipeline B”，画面才会改变，Pipeline 计数也会从 3 增加到 4。

这一章记住：

**WebGPU `override` 最像 WebGL 中用 `#define` 生成的 Shader 变体，而不像 `uniform`。它的值在创建具体 Pipeline 时确定；改变它需要另一条 Pipeline。**

配套示例：[`constants.html`](./constants.html)

# Shader Miscellaneous Input（着色器杂项输入）

原文：[WebGPU 着色器杂项输入](https://webgpufundamentals.org/webgpu/lessons/zh_cn/webgpu-miscellaneous-input.html)

前面的章节介绍了向 Shader 传数据的主要路径：Inter-stage、Uniform Buffer、Storage Buffer、Vertex Buffer、Texture、Immediates 和 Override。本章补充一种很小但实用的入口：`draw` 和 `drawIndexed` 的参数本身也会影响 Shader Builtin。

重点是 `firstInstance`。即使本次只绘制一个实例，也能把它当成一个无需 Buffer 的 `u32` 索引传给 Vertex Shader。

## 一、Draw 参数怎样进入 Shader

两个绘制函数的完整参数：

```js
pass.draw(
  vertexCount,
  instanceCount = 1,
  firstVertex = 0,
  firstInstance = 0,
);

pass.drawIndexed(
  indexCount,
  instanceCount = 1,
  firstIndex = 0,
  baseVertex = 0,
  firstInstance = 0,
);
```

它们与 Vertex Shader Builtin 的关系：

| Draw 参数 | 影响的 Builtin | 含义 |
| --- | --- | --- |
| `firstInstance` | `@builtin(instance_index)` | 本次 Draw 的实例编号从哪里开始 |
| `firstVertex` | 非索引绘制的 `@builtin(vertex_index)` | 顶点编号从哪里开始 |
| `firstIndex` | 没有直接同名 Builtin | 从 Index Buffer 的哪个元素开始读取 |
| `baseVertex` | 索引绘制的 `@builtin(vertex_index)` | 在读出的顶点索引上追加偏移 |

最重要的计算关系是：

```text
instance_index = firstInstance + 当前实例在本次 Draw 中的编号
```

因此：

```js
pass.draw(3, 1, 0, 7);
```

只绘制一个三角形，但它的三次 Vertex Shader 调用都会看到：

```wgsl
@builtin(instance_index) instanceIndex == 7u
```

如果是真正的三个实例：

```js
pass.draw(3, 3, 0, 7);
```

三个实例看到的 `instance_index` 依次是 7、8、9。

## 二、把 firstInstance 当成逐 Draw 索引

官方示例使用 `instance_index` 选择硬编码的位置和颜色：

```wgsl
struct VSOutput {
  @builtin(position) position: vec4f,
  @location(0) @interpolate(flat, either) colorIndex: u32,
};

@vertex
fn vs(
  @builtin(vertex_index) vertexIndex: u32,
  @builtin(instance_index) instanceIndex: u32,
) -> VSOutput {
  let positions = array(
    vec2f( 0.0,  0.5),
    vec2f(-0.5, -0.5),
    vec2f( 0.5, -0.5),
  );

  let offsets = array(
    vec2f( 0.0,  0.5),
    vec2f(-0.5, -0.5),
    vec2f( 0.5, -0.5),
  );

  return VSOutput(
    vec4f(positions[vertexIndex] + offsets[instanceIndex], 0, 1),
    instanceIndex,
  );
}
```

JavaScript 用三次 Draw 传入三个索引：

```js
pass.draw(3, 1, 0, 0); // instance_index = 0
pass.draw(3, 1, 0, 1); // instance_index = 1
pass.draw(3, 1, 0, 2); // instance_index = 2
```

`instance_index` 只存在于 Vertex Shader。如果 Fragment Shader 也需要这个索引，就要像普通 Inter-stage 数据一样传过去：

```wgsl
@location(0) @interpolate(flat, either) colorIndex: u32
```

- `u32` 是整数，不能进行产生小数的普通插值，所以必须是 `flat`。
- `either` 允许选择图元第一个或最后一个顶点的值。三个顶点的 instance index 相同，所以结果没有区别；原文使用它是因为这种写法也适合兼容性模式。

更实际的用法不是索引 Shader 中的硬编码数组，而是索引 Storage Buffer：

```wgsl
struct PerObject {
  matrix: mat4x4f,
  color: vec4f,
};

@group(0) @binding(0)
var<storage, read> objects: array<PerObject>;

@vertex
fn vs(
  @location(0) position: vec4f,
  @builtin(instance_index) objectIndex: u32,
) -> VSOutput {
  let object = objects[objectIndex];
  // 使用 object.matrix 变换当前对象……
}
```

这时 `firstInstance` 相当于“本次 Draw 使用 objects 中第几条记录”。一个整数就能间接选择完整的模型矩阵、材质和其他对象数据。

## 三、firstInstance、实例化和 Immediates 怎么选

下面两组调用能让 Shader 都看到 0、1、2，但含义与 Draw Call 数量不同：

```js
// 三次独立 Draw；每次把 firstInstance 当作逐 Draw 索引。
pass.draw(3, 1, 0, 0);
pass.draw(3, 1, 0, 1);
pass.draw(3, 1, 0, 2);

// 一次实例化 Draw；GPU 自动让三个实例得到 0、1、2。
pass.draw(3, 3, 0, 0);
```

如果几何、Pipeline 和资源都相同，通常优先考虑真正的实例化，因为一次 Draw 就能处理多个对象。`firstInstance` 当索引最适合这些情况：

- 对象因为几何或其他状态不同，本来就必须分开 Draw。
- Shader 已经有一个大型 Storage Buffer，只缺本次 Draw 的记录编号。
- 只需要传一个非负整数，不值得为它单独准备 Buffer 或 Immediate TypedArray。

与 Immediates 对比：

| 问题 | `firstInstance` | Immediates |
| --- | --- | --- |
| 能传多少 | 一个 `u32` 起始索引 | 核心保证至少 64 字节 |
| 设置位置 | `draw/drawIndexed` 参数 | `pass.setImmediates()` |
| Shader 入口 | Vertex `instance_index` | 使用 `var<immediate>` 的阶段 |
| 是否需要 TypedArray | 不需要 | 需要 ArrayBuffer 或 View |
| 典型用途 | 选择对象、材质、纹理层记录 | 多个索引、标志或少量逐 Draw 参数 |

`firstVertex` 也能以类似方式改变 `vertex_index`，但它通常真的用于选择 Vertex Buffer 中的顶点范围。为了传普通业务数据而占用它，往往会和正常顶点读取冲突，所以远不如 `firstInstance` 常见。

## 四、和 WebGL 对比

WebGL 2 的实例化入口是：

```js
gl.drawArraysInstanced(
  gl.TRIANGLES,
  first,
  count,
  instanceCount,
);
```

GLSL 中使用：

```glsl
int instanceIndex = gl_InstanceID;
```

但 WebGL 2 核心 API 没有 `firstInstance` 参数，`gl_InstanceID` 每次 Draw 都从 0 开始。如果想为每次 Draw 传入基础对象编号，通常需要 Uniform：

```glsl
uniform uint u_firstInstance;

void main() {
  uint objectIndex = u_firstInstance + uint(gl_InstanceID);
}
```

```js
gl.uniform1ui(firstInstanceLocation, objectIndex);
gl.drawArraysInstanced(gl.TRIANGLES, 0, 3, 1);
```

对应关系：

| 功能 | WebGL 2 | WebGPU |
| --- | --- | --- |
| 当前实例编号 | `gl_InstanceID` | `@builtin(instance_index)` |
| 指定实例起始编号 | 核心 API 没有；常用 Uniform 手动相加 | `draw/drawIndexed` 的 `firstInstance` |
| 非索引绘制的顶点起点 | `drawArrays` 的 `first` | `draw` 的 `firstVertex` |
| 索引绘制追加顶点偏移 | 核心 API 没有 `baseVertex` | `drawIndexed` 的 `baseVertex` |
| 传一个逐 Draw 整数 | `gl.uniform1ui` | `firstInstance`；更复杂时用 Immediates/Buffer |

WebGL 的 Uniform 更通用，但需要找到 Location 并修改 Program 状态；WebGPU 的 `firstInstance` 只表达一个起始索引，却已经是 Draw 命令的一部分，不需要额外资源或状态调用。

配套示例左右并排展示两条路径：左侧三次 Draw 分别设置 `firstInstance = 0/1/2`，右侧一次 `draw(3, 3, 0, 0)` 完成真正实例化。两侧共用一个 ShaderModule、一条 Pipeline，并且都不创建 Buffer 和 BindGroup。

这一章记住：

**`firstInstance` 会成为 Vertex Shader 的 `instance_index` 起点；即使 `instanceCount = 1`，它也能充当一个免费的逐 Draw `u32` 索引。WebGL 2 没有核心等价参数，通常要用 Uniform 模拟。**

配套示例：[`miscellaneous-input.html`](./miscellaneous-input.html)

# Memory Layout（数据内存布局）

原文：[WebGPU 数据内存布局](https://webgpufundamentals.org/webgpu/lessons/zh_cn/webgpu-memory-layout.html)

JavaScript 对象只表达“属性和值”，通常不需要关心属性位于内存中的第几个字节；但 Uniform Buffer 和 Storage Buffer 是一段原始二进制数据。WGSL 只知道结构体定义，不知道 JavaScript 对象，因此两侧必须对每个成员的**类型、字节偏移和总尺寸**达成完全一致。

布局错误通常不会产生清晰的 JavaScript 异常：Buffer 仍然能上传，Shader 也仍然能运行，只是会从错误字节读取数据，最终表现为颜色错误、模型消失或矩阵计算异常。

## 一、ArrayBuffer 是内存，TypedArray 是查看方式

WGSL v1 常用的四种标量是：

| WGSL 标量 | 含义 | 尺寸 |
| --- | --- | --- |
| `f32` | 32 位浮点数 | 4 bytes |
| `i32` | 32 位有符号整数 | 4 bytes |
| `u32` | 32 位无符号整数 | 4 bytes |
| `f16` | 16 位浮点数，需要可选特性 | 2 bytes |

如果结构体只有三个标量，布局确实可以连续排列：

```wgsl
struct Motion {
  velocity: f32,      // byte 0～3
  acceleration: f32,  // byte 4～7
  frameCount: u32,    // byte 8～11
};                    // 总计 12 bytes
```

JavaScript 可以让多个 TypedArray 共享同一个 `ArrayBuffer`：

```js
const data = new ArrayBuffer(12);
const floats = new Float32Array(data);
const uints = new Uint32Array(data);

floats[0] = 1.2; // velocity
floats[1] = 3.4; // acceleration
uints[2] = 56;   // frameCount：同一段内存按 u32 写入

device.queue.writeBuffer(gpuBuffer, 0, data);
```

这里不是创建了两份数据。`floats.buffer === uints.buffer === data`，两个 View 只是用不同类型解释同一组字节。

TypedArray 构造方式最容易混淆的是“长度”和“字节偏移”：

```js
new Float32Array(12);                  // 新建 12 个 f32，也就是 48 bytes
new Float32Array(buffer);              // 查看整个已有 ArrayBuffer
new Float32Array(buffer, 16, 3);       // 从 byte 16 开始，查看 3 个 f32
someFloat32Array.subarray(4, 7);       // 共享原内存，查看索引 4～6
```

`new Float32Array(otherTypedArray)` 则不同：它会创建新内存并逐个转换、复制数值，不会共享原来的二进制字节。

## 二、布局计算看两个量：size 和 align

每种 WGSL 类型都有两个不同概念：

- `size`：值本身保存多少字节。
- `align`：这个值的**起始地址**必须是哪个数字的整数倍。

常见 `f32` 类型：

| 类型 | size | align | 关键理解 |
| --- | ---: | ---: | --- |
| `f32` | 4 | 4 | 可从 4 的倍数开始 |
| `vec2f` | 8 | 8 | 可从 8 的倍数开始 |
| `vec3f` | 12 | 16 | 保存 12 字节，但起点必须是 16 的倍数 |
| `vec4f` | 16 | 16 | 保存和对齐都是 16 字节 |
| `mat3x3f` | 48 | 16 | 3 列 `vec3f`，每列步长 16，而不是紧凑的 36 字节 |
| `mat4x4f` | 64 | 16 | 4 列 `vec4f` |

结构体成员按声明顺序放置。每放一个成员，都先把当前位置向该成员的 `align` 取整：

```text
memberOffset = roundUp(memberAlign, previousMemberEnd)
memberEnd    = memberOffset + memberSize

structAlign  = 所有成员 align 的最大值
structSize   = roundUp(structAlign, lastMemberEnd)
```

例如配套示例：

```wgsl
struct Params {
  scale: f32,
  color: vec3f,
};
```

计算过程：

| 区域 | 字节范围 | 原因 |
| --- | --- | --- |
| `scale` | 0～3 | `f32` 从 byte 0 开始 |
| 内部填充 | 4～15 | 下一个 16 字节对齐位置是 byte 16 |
| `color` | 16～27 | `vec3f` 的 size 是 12 |
| 尾部填充 | 28～31 | 结构体总尺寸向最大 align 16 取整 |

所以 `color` 的偏移是 16，`Params` 的尺寸是 32。下面的紧凑写法不会报上传错误，却会让 Shader 读错：

```js
const wrongValues = new Float32Array(32 / 4);
const correctValues = new Float32Array(32 / 4);
wrongValues[0] = correctValues[0] = 0.72;

wrongValues.set([0.1, 0.82, 0.5], 1); // 错：从 byte 4 开始
correctValues.set([0.1, 0.82, 0.5], 4); // 对：从 byte 16 开始
```

注意，`vec3f` 不是在所有场景中都“强制独占 16 字节”。它的 `size` 仍是 12，例如后面紧跟一个满足对齐的 `f32` 时，这个标量可以位于 `vec3f` 后面的第 12 字节。真正必须记住的是：**`vec3f` 的起点按 16 对齐；数组元素和矩阵列还要遵守各自的 stride。**

## 三、数组、矩阵和嵌套结构体为什么最容易算错

数组不能只用“元素 size × 数量”猜尺寸。元素之间使用固定步长：

```text
arrayStride = roundUp(elementAlign, elementSize)
```

这是类型的基础步长规则。用于 `var<uniform>` 时，如果设备没有启用 `uniform-buffer-standard-layout` 特性，数组元素还必须按 16 字节边界排列；因此 `array<f32>` 也不能按每 4 字节紧凑排列。Storage Buffer 没有这条额外的 Uniform 限制。

因此：

```wgsl
array<vec3f, 4>
```

每个 `vec3f` 保存 12 字节，但下一个元素必须从新的 16 字节边界开始，所以四个元素的偏移为 0、16、32、48，总计 64 字节，而不是 48 字节。

矩阵按**列向量数组**理解最直接：

```wgsl
mat3x3f // 3 列，每列是 vec3f；列步长 16，总计 48 bytes
mat4x4f // 4 列，每列是 vec4f；列步长 16，总计 64 bytes
```

嵌套结构体也有自己的 `align` 和经过尾部取整的 `size`。把它放进外层结构体时，应该把它当成一个完整类型重新对齐，而不是把内部最后一个成员后面的位置直接接着使用。

手动维护布局时，实用做法是：

```js
const BUFFER_SIZE = 32;
const SCALE_INDEX = 0;       // byte 0 / 4
const COLOR_INDEX = 16 / 4;  // byte 16 / 4 = Float32 索引 4

const values = new Float32Array(BUFFER_SIZE / 4);
values[SCALE_INDEX] = 0.72;
values.set([0.1, 0.82, 0.5], COLOR_INDEX);
```

- 常量名明确写出字节或 TypedArray 索引，避免把两种单位混用。
- 修改 WGSL 结构体后，同步重新核对 JavaScript 的偏移、Buffer `size` 和绑定范围。
- 混合 `f32`、`u32` 时，可在同一 `ArrayBuffer` 上建立多个 View，或使用 `DataView` 明确按字节写入。
- 大型结构体可以使用原文推荐的 [`webgpu-utils`](https://github.com/greggman/webgpu-utils) 解析 WGSL 并创建 Structured View，减少手算错误。

还要区分两个不同限制：本章的 `align` 决定**结构体成员在 Buffer 内部的位置**；`minUniformBufferOffsetAlignment` 通常是 256，约束的是使用动态 Offset 绑定多份 Uniform 数据时，每一份绑定从整块 Buffer 的哪里开始。两者不能互相替代。

## 四、和 WebGL 对比

WebGL 使用普通 Uniform 时，应用传的是“Uniform Location + 数值”，驱动负责内部布局：

```glsl
uniform float u_scale;
uniform vec3 u_color;
```

```js
gl.uniform1f(scaleLocation, 0.72);
gl.uniform3f(colorLocation, 0.1, 0.82, 0.5);
```

这种方式不需要 JavaScript 计算 `u_color` 位于第几个字节。WebGPU 没有对应的 `gl.uniform*` 状态调用；数据放进 Uniform/Storage Buffer 后，应用必须按 WGSL 布局准备二进制内存。

但 WebGL 2 的 Uniform Buffer Object 同样存在布局问题：

```glsl
layout(std140) uniform Params {
  float scale;
  vec3 color;
};
```

在 `std140` 中，`color` 同样需要从 16 字节边界开始。WebGL 2 还能用 `gl.getActiveUniforms` 查询 `UNIFORM_OFFSET`、`UNIFORM_ARRAY_STRIDE` 和 `UNIFORM_MATRIX_STRIDE`；WebGPU 项目通常根据 WGSL 规则计算，或使用 Shader Reflection/`webgpu-utils` 生成布局 View。

| 场景 | WebGL | WebGPU |
| --- | --- | --- |
| 少量普通 Uniform | `gl.uniform*`，驱动处理布局 | 写入 Uniform Buffer，应用准备字节布局 |
| Buffer 中的 Uniform | WebGL 2 UBO + `std140` | WGSL `var<uniform>` |
| 查询成员偏移 | `gl.getActiveUniforms` 可查询 Program 反射结果 | 核心 API 不直接返回结构体成员偏移，常用规则计算或工具反射 |
| 典型错误表现 | UBO 读错值 | Uniform/Storage Buffer 读错值 |

配套示例用同一条 Pipeline 绘制两次：左侧把 `color` 错写到 byte 4，Shader 从 byte 16 读到零；右侧按正确偏移写入，因此显示明亮绿色。两份 Buffer 都是 32 字节，证明“Buffer 足够大”并不代表“成员布局正确”。

这一章记住：

**传给 WGSL 的不是 JavaScript 对象，而是一串字节。成员偏移由 size 和 align 共同决定；尤其要警惕 `vec3f`、数组、矩阵和嵌套结构体产生的填充与 stride。**

配套示例：[`memory-layout.html`](./memory-layout.html)

# Transparency and Blending（透明度与混合）

原文：[WebGPU 透明度与混合](https://webgpufundamentals.org/webgpu/lessons/zh_cn/webgpu-transparency.html)

透明不是“Fragment Shader 返回一个小于 1 的 Alpha 就自动完成”。WebGPU 中至少有两层不同的混合：

1. Render Pass 内，新片段与颜色附件已有像素之间的混合，由 RenderPipeline 的 `blend` 决定。
2. WebGPU Canvas 最终与 HTML 页面之间的混合，由 `context.configure()` 的 `alphaMode` 决定。

不区分这两层，就很容易遇到“Alpha 已经是 0.5，为什么看起来仍然不透明”或“颜色异常发亮”的问题。

## 一、Canvas alphaMode 与预乘 Alpha

Canvas 默认是不透明的：

```js
context.configure({
  device,
  format,
  alphaMode: "opaque", // 默认值；Canvas 的 Alpha 不参与和 HTML 的合成
});
```

如果希望页面背景能透过 WebGPU Canvas，需要：

```js
context.configure({
  device,
  format,
  alphaMode: "premultiplied",
});
```

`premultiplied` 不只是“允许透明”，还规定 Canvas 中保存的 RGB 必须已经乘过 Alpha。假设直通颜色是：

```text
RGB = (1.0, 0.5, 0.25)
A   = 0.33
```

合法的预乘颜色是：

```text
RGBA = (1.0 × 0.33, 0.5 × 0.33, 0.25 × 0.33, 0.33)
     = (0.33, 0.165, 0.0825, 0.33)
```

可以在 Fragment Shader 返回前完成预乘：

```wgsl
return vec4f(color.rgb * color.a, color.a);
```

如果对 `alphaMode: "premultiplied"` 的 Canvas 写入 `(1, 0, 0, 0.01)`，RGB 的红色分量 1 远大于 Alpha 0.01，它不是合法的预乘颜色，最终显示结果未定义。正确值应为 `(0.01, 0, 0, 0.01)`。

导入带透明度的图片时，也要明确纹理数据采用哪种约定：

```js
device.queue.copyExternalImageToTexture(
  { source: image },
  { texture, premultipliedAlpha: true },
  [image.width, image.height],
);
```

这会在复制时进行预乘，之后 `textureSample()` 取得的就是预乘颜色。一个项目最好统一纹理和 Shader 使用直通还是预乘 Alpha，不要在不同资源之间随意混用。

## 二、discard 是“不产生这个片段”

`discard` 只能在 Fragment Shader 中使用，它终止当前片段，不把这个片段的颜色、深度等结果写入附件：

```wgsl
@fragment
fn fs(input: FSInput) -> @location(0) vec4f {
  let color = textureSample(texture, sampler, input.uv);

  if (color.a < 0.5) {
    discard;
  }

  return color;
}
```

`return vec4f(rgb, 0)` 和 `discard` 不是一回事：

- 没开启混合时，Alpha 为 0 的 RGB 仍会直接覆盖目标颜色。
- 即使混合后颜色看起来没变化，片段仍可能写入深度纹理，挡住后面绘制的对象。
- `discard` 表示这个片段根本不参加颜色和深度写入。

因此它常用于精灵、字体、铁丝网、树叶和草片等 Alpha Cutout 材质。配套示例先绘制一个四边形，但圆外片元执行 `discard`，所以最终只留下圆形，而不是带透明角落的完整矩形。

硬阈值会产生锯齿，实际项目常结合 MSAA 的 Alpha-to-Coverage、抗锯齿纹理或平滑透明边缘处理；这些属于后续具体技术，本章先分清“丢弃片段”和“参与混合”。

## 三、Blend State 决定 src 怎样与 dst 合成

混合配置写在 RenderPipeline 的 Fragment Target 中：

```js
fragment: {
  module,
  targets: [{
    format,
    blend: {
      color: {
        operation: "add",
        srcFactor: "one",
        dstFactor: "one-minus-src-alpha",
      },
      alpha: {
        operation: "add",
        srcFactor: "one",
        dstFactor: "one-minus-src-alpha",
      },
    },
  }],
}
```

基本计算可以理解为：

```text
result = operation(src × srcFactor, dst × dstFactor)
```

- `src`：当前 Fragment Shader 返回的颜色。
- `dst`：颜色附件这个位置原来保存的颜色。
- `color`：单独计算 RGB。
- `alpha`：单独计算 A。

省略 `blend` 时等价于：

```js
{
  operation: "add",
  srcFactor: "one",
  dstFactor: "zero",
}
```

也就是 `result = src`，新片段直接替换旧像素。Fragment Shader 返回 Alpha 0.5 并不会自动开启半透明。

最常见的 source-over 有两套匹配写法：

| 源数据约定 | Fragment Shader 输出 | color.srcFactor | color.dstFactor |
| --- | --- | --- | --- |
| 直通 Alpha | `vec4(rgb, a)` | `src-alpha` | `one-minus-src-alpha` |
| 预乘 Alpha | `vec4(rgb * a, a)` | `one` | `one-minus-src-alpha` |

两种方式在数据与 Blend Factor 正确配对时结果相同：

```text
直通：result.rgb = src.rgb × src.a + dst.rgb × (1-src.a)
预乘：result.rgb = srcPremult.rgb + dst.rgb × (1-src.a)
```

Alpha 通常使用：

```js
alpha: {
  operation: "add",
  srcFactor: "one",
  dstFactor: "one-minus-src-alpha",
}
```

其他常见模式包括：

- 加法发光：`one + one`。
- Destination Over：根据目标 Alpha 把新内容放到旧内容后面。
- `min` / `max`：直接选择较小或较大分量；这两种 operation 的 Factor 必须使用 `one`。
- `constant` / `one-minus-constant`：因子来自 `pass.setBlendConstant()`，可以在 Draw 之间改变。

Blend State 是 Pipeline 状态。改变 operation 或 Factor 通常意味着选择或创建另一条 Pipeline；Blend Constant 不是 Pipeline 固定值，可以通过 Render Pass Encoder 动态设置。

Draw 顺序同样是混合的一部分。先画蓝色再画红色时，红色是 `src`、蓝色是 `dst`；反过来绘制时角色也反过来。普通 source-over 不是可交换运算，因此透明物体通常需要从后往前排序。配套示例的“反转 Draw 顺序”开关就是为了直接观察这一点。

## 四、和 WebGL 对比

WebGL 的混合数学与 WebGPU 基本相同，主要差别在状态放在哪里。

WebGL 通过全局状态开启和配置混合：

```js
gl.enable(gl.BLEND);
gl.blendEquationSeparate(gl.FUNC_ADD, gl.FUNC_ADD);
gl.blendFuncSeparate(
  gl.ONE,                 // RGB source factor
  gl.ONE_MINUS_SRC_ALPHA, // RGB destination factor
  gl.ONE,                 // Alpha source factor
  gl.ONE_MINUS_SRC_ALPHA, // Alpha destination factor
);
```

这对应 WebGPU 预乘 Alpha 的 source-over：

```js
blend: {
  color: { operation: "add", srcFactor: "one", dstFactor: "one-minus-src-alpha" },
  alpha: { operation: "add", srcFactor: "one", dstFactor: "one-minus-src-alpha" },
}
```

对应关系：

| 功能 | WebGL | WebGPU |
| --- | --- | --- |
| 开启混合 | `gl.enable(gl.BLEND)` | Pipeline Target 存在 `blend` 配置 |
| 混合公式 | `gl.blendEquationSeparate` | `color/alpha.operation` |
| 混合因子 | `gl.blendFuncSeparate` | `color/alpha.srcFactor`、`dstFactor` |
| 混合常量 | `gl.blendColor` | `pass.setBlendConstant` |
| 丢弃片段 | GLSL `discard` | WGSL `discard` |
| Canvas 与页面透明 | 创建 Context 时设置 `alpha`、`premultipliedAlpha` | `context.configure({ alphaMode })` |
| 状态归属 | WebGL Context 的可变全局状态 | RenderPipeline 的固定状态 |

WebGL 改 Blend Factor 后可以继续使用同一个 Program；WebGPU 通常切换到另一条已经准备好的 Pipeline。这延续了 WebGPU 的核心设计：把影响渲染行为的大部分状态提前固定进 Pipeline，Draw 时只选择明确的执行配置。

两者的 `discard`、预乘规则和绘制顺序问题没有本质区别。迁移时最需要改变的思维是：WebGL 在 Draw 前修改 Context 状态，WebGPU 在创建 Pipeline 时描述状态。

这一章记住：

**Alpha 只是数据，不会自动产生透明。Canvas 与页面是否透明看 `alphaMode`；片段与颜色附件如何合成看 Pipeline `blend`；完全不应写入的片段使用 `discard`。直通与预乘 Alpha 都能正确工作，但 Shader 输出与 Blend Factor 必须配套。**

配套示例：[`transparency.html`](./transparency.html)

# Bind Group Layouts（绑定组布局）

原文：[WebGPU 绑定组布局](https://webgpufundamentals.org/webgpu/lessons/zh_cn/webgpu-bind-group-layouts.html)

前面的示例经常使用 `layout: "auto"`，所以 Bind Group Layout 看起来像一个可以忽略的内部对象。简单程序确实可以这样写；但当资源类型超出自动布局默认值、需要动态 Buffer Offset，或者希望一个 BindGroup 跨多条 Pipeline 复用时，就必须显式描述布局。

这章最重要的是分清三个对象：**BindGroupLayout 是接口，PipelineLayout 是 group 接口列表，BindGroup 是满足接口的一组实际资源。**

## 一、Layout 描述接口，BindGroup 提供资源

WGSL 先声明 Shader 希望在什么位置看到什么资源：

```wgsl
@group(0) @binding(0) var<uniform> camera: Camera;
@group(0) @binding(1) var linearSampler: sampler;
@group(0) @binding(2) var colorTexture: texture_2d<f32>;
```

JavaScript 中的对象关系是：

```text
GPUBindGroupLayout       描述某个 group 的 binding 编号、资源类型、可见阶段等
        ↓
GPUPipelineLayout        按数组索引把 Layout 分配给 group 0、group 1……
        ↓
Render/Compute Pipeline  使用这份完整资源接口

GPUBindGroupLayout
        ↓
GPUBindGroup             按接口装入实际 Buffer、Sampler、TextureView
        ↓
pass.setBindGroup(n, bg) 把实际资源设置到第 n 组
```

例如显式声明一个 Uniform 接口：

```js
const bindGroupLayout = device.createBindGroupLayout({
  entries: [{
    binding: 0,
    visibility: GPUShaderStage.VERTEX | GPUShaderStage.FRAGMENT,
    buffer: {
      type: "uniform",
      minBindingSize: 32,
    },
  }],
});

const pipelineLayout = device.createPipelineLayout({
  bindGroupLayouts: [bindGroupLayout], // 数组索引 0 对应 @group(0)
});

const pipeline = device.createRenderPipeline({
  layout: pipelineLayout,
  // vertex、fragment……
});

const bindGroup = device.createBindGroup({
  layout: bindGroupLayout,
  entries: [{
    binding: 0,
    resource: { buffer: uniformBuffer },
  }],
});
```

创建 BindGroup 时，WebGPU 已能根据 BindGroupLayout 检查大部分资源类型和范围。Draw 或 Dispatch 时只需检查当前 group 位置上的 BindGroup Layout 是否与 PipelineLayout 对应位置兼容，因此热路径上的验证更简单。

`binding` 和 `group` 是两个层级：`binding: 2` 表示组内第 2 个槽位；`pass.setBindGroup(2, bg)` 表示把整个 BindGroup 设置到 `@group(2)`，不要把二者混为同一个编号。

## 二、layout: auto 什么时候不够用

使用：

```js
layout: "auto"
```

WebGPU 会根据 Pipeline 使用的 Shader 入口自动创建 `GPUPipelineLayout` 和其中的 `GPUBindGroupLayout`。优点是代码少，适合单 Pipeline、小型示例和快速原型。

显式布局主要解决两类问题：

1. 自动推导的资源要求不是你真正需要的要求。
2. 多条 Pipeline 需要共享同一批 BindGroup。

原文使用 `rgba32float` 说明第一类问题。下面的声明配合自动布局时，普通浮点纹理默认会被推导为可过滤的 `float` 采样类型和 `filtering` Sampler：

```wgsl
@group(0) @binding(0) var ourSampler: sampler;
@group(0) @binding(1) var ourTexture: texture_2d<f32>;
```

但 `rgba32float` 默认不可过滤；只有支持并请求 `float32-filterable` 可选特性时才能线性过滤。没有该特性时，将它绑定到自动生成的 `sampleType: "float"` 接口会产生验证错误。

解决方式是明确声明不可过滤组合：

```js
const bindGroupLayout = device.createBindGroupLayout({
  entries: [
    {
      binding: 0,
      visibility: GPUShaderStage.FRAGMENT,
      sampler: { type: "non-filtering" },
    },
    {
      binding: 1,
      visibility: GPUShaderStage.FRAGMENT,
      texture: {
        sampleType: "unfilterable-float",
        viewDimension: "2d",
        multisampled: false,
      },
    },
  ],
});
```

Sampler 也必须真正使用最近点采样；如果 `magFilter`、`minFilter` 或 `mipmapFilter` 设置为 `"linear"`，它就属于 Filtering Sampler，不能放进 `non-filtering` 槽位。

自动布局还有一个重要限制：由 `layout: "auto"` 生成的 BindGroupLayout 是对应 Pipeline 的专用自动布局。即使另一条 Pipeline 的 WGSL 声明看起来相同，也不能假设由第一条 Pipeline 的自动布局创建的 BindGroup 可以给第二条使用。需要跨 Pipeline 共享时，应由应用显式创建并共同传入同一份布局。

## 三、动态 Offset：同一个 BindGroup 选择 Buffer 不同区域

普通 BindGroup 创建后，Buffer 的 `offset` 和 `size` 就固定了：

```js
resource: {
  buffer,
  offset: 0,
  size: 64,
}
```

如果希望在不创建新 BindGroup 的情况下改变数据窗口，需要在布局中启用动态偏移：

```js
const bindGroupLayout = device.createBindGroupLayout({
  entries: [{
    binding: 0,
    visibility: GPUShaderStage.COMPUTE,
    buffer: {
      type: "storage",
      hasDynamicOffset: true,
      minBindingSize: 12,
    },
  }],
});
```

设置 BindGroup 时再传入 Offset：

```js
pass.setBindGroup(0, bindGroup, [0]);
pass.dispatchWorkgroups(3);

pass.setBindGroup(0, bindGroup, [regionStride]);
pass.dispatchWorkgroups(3);
```

最终窗口起点是：

```text
effectiveOffset = BindGroup resource.offset + dynamicOffset
```

需要注意：

- Dynamic Uniform Offset 必须满足 `device.limits.minUniformBufferOffsetAlignment`。
- Dynamic Storage Offset 必须满足 `device.limits.minStorageBufferOffsetAlignment`。
- 常见限制是 256 bytes，但应该查询 Device Limits，不能把 256 当作所有设备的固定常量。
- `resource.size` 必须明确限制当前窗口的长度，否则非零动态 Offset 可能让“默认绑定整个 Buffer”的范围越界。
- 一个 group 中有多个动态 Buffer Binding 时，Offset 数组按动态 Binding 编号从小到大对应，而不是随意排列。

动态偏移的范围检查只能推迟到 `setBindGroup()`，因此比完全固定的 BindGroup 略贵。调用次数不多时通常无需担心；大量 Draw 时应测量，并考虑分组资源、固定 BindGroup 或其他批处理方式。

配套示例使用同一块 Storage Buffer：数据 A 从 byte 0 开始，数据 B 从 `minStorageBufferOffsetAlignment` 开始。一个 BindGroup 的资源窗口始终是 12 bytes，动态 Offset 决定本次 Dispatch 看到 A 还是 B。

## 四、跨 Pipeline 共享与布局实践

显式布局的第二个主要价值是让多条 Pipeline 拥有同一份资源契约：

```js
const pipelineLayout = device.createPipelineLayout({
  bindGroupLayouts: [sharedBindGroupLayout],
});

const times2Pipeline = device.createComputePipeline({
  layout: pipelineLayout,
  compute: { module: times2Module },
});

const plus3Pipeline = device.createComputePipeline({
  layout: pipelineLayout,
  compute: { module: plus3Module },
});

const bindGroup = device.createBindGroup({
  layout: sharedBindGroupLayout,
  entries: [/* 实际资源 */],
});
```

切换 Pipeline 后，只要对应 group 的布局兼容，已经设置的 BindGroup 就可以继续使用。配套示例明确再次调用 `setBindGroup` 是为了切换动态 Offset，而不是因为 BindGroup 本身必须重建。

3D 渲染器常按更新频率组织 Group：

```text
group 0：全局/每帧数据   摄像机、灯光、时间
group 1：每材质数据     纹理、Sampler、材质参数
group 2：每对象数据     模型矩阵、对象索引
```

对应的渲染循环：

```text
setBindGroup(0, globals)
for each material:
  setBindGroup(1, material)
  for each object using material:
    setBindGroup(2, object)
    draw()
```

这样能减少不必要的资源重绑，还能让主渲染 Pipeline、阴影 Pipeline 等共享全局和对象 BindGroup。

显式描述 Entry 时重点检查：

- `binding` 必须与 WGSL 的 `@binding(n)` 一致。
- `visibility` 应包含真正访问资源的 Shader Stage；多个阶段使用位或组合，例如 `VERTEX | FRAGMENT`。
- `texture: {}` 默认是 `sampleType: "float"`、`viewDimension: "2d"`、`multisampled: false`。
- `sampler: {}` 默认是 `type: "filtering"`。
- 固定大小 Buffer 尽量声明 `minBindingSize`，让大小错误在创建 BindGroup 时一次检查，而不是推迟到每次 Draw/Dispatch。
- Runtime-sized Storage Array 可以合法绑定不同长度的范围，这时 `minBindingSize` 常保留为最小头部尺寸或 0。

## 五、和 WebGL 对比

WebGL 2 没有 BindGroup、BindGroupLayout 或 PipelineLayout 这套成组对象。资源状态分散在 Program、Uniform Location、Texture Unit 和 Buffer Binding Point 上。

例如绑定 UBO 的一段范围：

```js
const blockIndex = gl.getUniformBlockIndex(program, "Camera");
gl.uniformBlockBinding(program, blockIndex, 0);

gl.bindBufferRange(
  gl.UNIFORM_BUFFER,
  0,       // binding point
  buffer,
  offset,
  size,
);
```

`gl.bindBufferRange` 和 WebGPU Dynamic Uniform Offset 都能选择大 Buffer 中的一段，并且都受对齐限制；WebGL 2 对应限制是 `gl.UNIFORM_BUFFER_OFFSET_ALIGNMENT`。但 WebGL 2 没有 Storage Buffer 和 Compute Shader，因此没有 WebGPU Dynamic Storage Offset 的直接等价物。

纹理资源在 WebGL 中也要分别设置：

```js
gl.activeTexture(gl.TEXTURE0);
gl.bindTexture(gl.TEXTURE_2D, texture);
gl.uniform1i(textureLocation, 0);
```

对应关系：

| 概念 | WebGL 2 | WebGPU |
| --- | --- | --- |
| Shader 资源接口 | Program 链接结果与反射信息 | `GPUBindGroupLayout` |
| 多组接口的整体布局 | 没有独立对象，由 Program 隐式决定 | `GPUPipelineLayout` |
| 一组实际资源 | 分散在 Texture Unit、Buffer Binding Point、Uniform 状态 | `GPUBindGroup` |
| Buffer 子范围 | `gl.bindBufferRange` | BindGroup 固定范围或 Dynamic Offset |
| 跨 Program/Pipeline 复用 | 依靠相同 Binding Point 并由应用手动约定 | 多条 Pipeline 共用显式 Layout 和 BindGroup |
| 资源匹配错误 | 许多状态在 Draw 时组合 | 大部分在 Layout、Pipeline、BindGroup 创建时验证 |

WebGL 的 Binding Point 思想与 `@group/@binding` 有相似之处，但 WebGPU 把分散状态封装成不可变、可提前验证的对象。代价是初始描述更详细，收益是资源接口更明确，也更适合复用和多线程式命令编码。

这一章记住：

**BindGroupLayout 是资源接口，不是资源本身。`layout: "auto"` 适合简单单 Pipeline；需要非默认资源类型、动态 Offset 或跨 Pipeline 共享 BindGroup 时，就显式创建 BindGroupLayout 和 PipelineLayout。**

配套示例：[`bind-group-layouts.html`](./bind-group-layouts.html)

# Copying Data（复制数据）

原文：[WebGPU 数据拷贝](https://webgpufundamentals.org/webgpu/lessons/zh_cn/webgpu-copying-data.html)

WebGPU 中的数据复制分成三类：CPU 直接向 GPU Queue 写入、CommandEncoder 录制 GPU 内部复制、通过可映射 Buffer 在 GPU 与 JavaScript 之间中转。它们的调用位置、Usage Flag 和对齐规则不同，不能只把所有操作都理解成普通的数组复制。

## 一、Queue 直接上传：writeBuffer 与 writeTexture

`queue.writeBuffer()` 是把 JavaScript 二进制数据写入 GPUBuffer 最直接的方法：

```js
device.queue.writeBuffer(
  destinationBuffer,
  destinationByteOffset,
  sourceData,
  sourceElementOffset,
  elementCount,
);
```

- 目标 Buffer 必须包含 `GPUBufferUsage.COPY_DST`。
- `destinationByteOffset` 是目标 Buffer 中的**字节偏移**。
- 当源是 TypedArray 时，`sourceElementOffset` 和 `elementCount` 使用该 TypedArray 的**元素单位**。
- 当源是 ArrayBuffer 时，一个元素就是一个字节。
- 省略源 Offset 时从 0 开始；省略 Size 时复制源 View 剩余部分。

例如：

```js
const source = new Float32Array([99, 88, 1.25, 2.5, 5, 10, 77]);

device.queue.writeBuffer(
  gpuBuffer,
  0,      // 目标从 byte 0 开始
  source,
  2,      // 源从 Float32 元素 2 开始，即源 byte 8
  4,      // 复制 4 个 f32，即 16 bytes
);
```

最终写入 `[1.25, 2.5, 5, 10]`。这里最容易犯的错误是把 `2` 当成源 byte 2。

`queue.writeTexture()` 直接把 CPU 数据写入 Texture：

```js
device.queue.writeTexture(
  {
    texture,
    mipLevel: 0,
    origin: [0, 0, 0],
    aspect: "all",
  },
  sourceData,
  {
    offset: 0,
    bytesPerRow,
    rowsPerImage,
  },
  [width, height, depthOrArrayLayers],
);
```

- Texture 必须包含 `GPUTextureUsage.COPY_DST`。
- 复制超过一个块行时，需要 `bytesPerRow`，它表示源内存中相邻两个块行起点之间隔多少字节。
- 复制超过一个数组层或 3D 切片时，需要 `rowsPerImage`，表示相邻两层起点之间隔多少块行。
- `writeTexture` 的 `bytesPerRow` 不要求是 256 的倍数；只需满足格式块大小等规则。

“块行”是纹理格式的存储单位。普通 `rgba8unorm` 的块大小是 1×1 像素、每块 4 bytes；BC 等压缩格式可能一个块表示 4×4 像素。压缩纹理的 Copy Size 与 Origin 通常还必须落在块宽、块高边界上。

`GPUExtent3D` 和 `GPUOrigin3D` 都能用数组或对象表达，省略的维度使用默认值：

```js
[3, 2]                                  // width=3, height=2, depth=1
{ width: 3, height: 2 }                 // 同上
{ x: 4, y: 6 }                          // origin x=4, y=6, z=0
```

## 二、CommandEncoder 中的 GPU Copy 命令

`writeBuffer/writeTexture` 是 Queue 方法；下面四种复制则录制进 CommandEncoder，只有 `queue.submit()` 后才执行：

| Copy 命令 | 源 Usage | 目标 Usage | 核心限制 |
| --- | --- | --- | --- |
| `copyBufferToBuffer` | `COPY_SRC` | `COPY_DST` | Size 是字节数，并且是 4 的倍数 |
| `copyBufferToTexture` | Buffer `COPY_SRC` | Texture `COPY_DST` | `bytesPerRow` 必须是 256 的倍数 |
| `copyTextureToBuffer` | Texture `COPY_SRC` | Buffer `COPY_DST` | `bytesPerRow` 必须是 256 的倍数 |
| `copyTextureToTexture` | Texture `COPY_SRC` | Texture `COPY_DST` | 格式相同，或只相差 `-srgb` 后缀；区域遵守块对齐 |

Buffer 到 Buffer：

```js
encoder.copyBufferToBuffer(
  sourceBuffer,
  sourceByteOffset,
  destinationBuffer,
  destinationByteOffset,
  byteSize,
);
```

Buffer 到 Texture：

```js
encoder.copyBufferToTexture(
  {
    buffer,
    offset: 0,
    bytesPerRow: 256,
    rowsPerImage: height,
  },
  { texture, mipLevel: 0, origin: [0, 0, 0] },
  [width, height],
);
```

Texture 到 Buffer 的参数方向相反：

```js
encoder.copyTextureToBuffer(
  { texture },
  { buffer, bytesPerRow: 256, rowsPerImage: height },
  [width, height],
);
```

注意 `writeTexture` 和 Buffer↔Texture Copy 的关键区别：前者可以用紧凑行，后两者的 Buffer Layout 每行必须按 256 bytes 对齐。

例如读取 3×2 的 `rgba8unorm`：

```text
真实像素行：3 × 4 = 12 bytes
GPU Copy 行跨度：roundUp(256, 12) = 256 bytes

row 0：byte   0～11 是像素，byte  12～255 是 padding
row 1：byte 256～267 是像素，byte 268～511 是 padding
Readback Buffer 总尺寸：512 bytes
```

这里的 512 bytes 是按“两行都保留完整 256-byte 槽位”分配的直观尺寸。对于单层 2D Copy，规范要求的最小覆盖范围只需到最后一行有效数据结束，即 `256 + 12 = 268 bytes`；最后一行末尾的 244 bytes 不一定必须实际存在。工程中常按完整行跨度分配，计算多层或复用 Buffer 时更简单。

解析 Readback 时不能把 512 字节连续当成 6 个像素，而要按 `y * bytesPerRow` 找到每行起点，再只读取有效像素部分。

## 三、映射 Buffer：在 JavaScript 和 GPU 之间中转

映射表示暂时让 JavaScript 直接访问 Buffer 内存。WebGPU v1 中常用的可映射 Usage 组合是：

```js
GPUBufferUsage.MAP_READ  | GPUBufferUsage.COPY_DST
GPUBufferUsage.MAP_WRITE | GPUBufferUsage.COPY_SRC
```

典型 Readback 路径：

```text
GPU 工作 Buffer/Texture
        ↓ Copy 命令
MAP_READ | COPY_DST 的 Staging Buffer
        ↓ await mapAsync(READ)
JavaScript ArrayBuffer / TypedArray
```

读取代码：

```js
const readback = device.createBuffer({
  size: 1024,
  usage: GPUBufferUsage.MAP_READ | GPUBufferUsage.COPY_DST,
});

// 先提交把 GPU 数据复制进 readback 的命令……
await readback.mapAsync(GPUMapMode.READ);

const mappedRange = readback.getMappedRange();
const values = new Float32Array(mappedRange);

// 如果 unmap 后仍需使用结果，必须先复制出来。
const result = values.slice();
readback.unmap();
```

三个生命周期规则必须记住：

1. `mapAsync()` 是异步的，它会等到 GPU 不再占用对应范围。
2. Buffer 处于 Mapped 状态时，不能同时被 GPU 命令使用。
3. `unmap()` 后，`getMappedRange()` 返回的 ArrayBuffer 与它的 TypedArray View 会失效；需要保留的数据要在此之前复制。

普通 Vertex、Index、Uniform 或 Storage Buffer 通常不能同时长期作为可映射 Buffer。常见设计是使用专门的 Staging/Readback Buffer 做中转，让真正工作的 GPU Buffer 保持适合 GPU 使用的 Usage。

## 四、mappedAtCreation、Shader 写入与高效映射

`mappedAtCreation: true` 是初始化静态 Buffer 的另一种方式：

```js
const uniformBuffer = device.createBuffer({
  size: 16,
  usage: GPUBufferUsage.UNIFORM,
  mappedAtCreation: true,
});

new Float32Array(uniformBuffer.getMappedRange()).set([1, 2, 3, 4]);
uniformBuffer.unmap();
```

它的特殊点是第一次创建时已经处于可写映射状态，即使 Usage 没有 `MAP_WRITE` 或 `COPY_DST` 也可以完成首次初始化。

但 `mappedAtCreation` 不会自动添加任何 Usage Flag。第一次 `unmap()` 后：

- 如果将来还要 `writeBuffer` 写入，仍需要 `COPY_DST`。
- 如果将来还要重新映射，仍需要对应的 `MAP_READ` 或 `MAP_WRITE`。
- 如果只声明 `UNIFORM`，之后它就只是一块 Uniform Buffer。

Shader 本身也是数据生产者：Compute Shader 能写 Storage Buffer、Storage Texture；Render Pipeline 能写颜色和深度纹理。要把 Shader 生成的数据带回 CPU，仍然通常要 Copy 到 MAP_READ Buffer 再异步映射。

频繁流式上传时，不要在每次需要数据时才创建一个 Buffer 并等待映射。原文建议维护一个已映射 Staging Buffer 池：

```text
取出一个已映射 Buffer → 写入 CPU 数据 → unmap
        ↓
提交 GPU Copy
        ↓
再次 mapAsync
        ↓ Promise 完成后放回可用池
```

池中暂时没有可用 Buffer 时再扩容。这样 CPU 可以继续准备后续数据，而 GPU 使用刚刚取消映射的 Buffer，减少同步等待。

常见选择：

- 少量、零散更新：优先 `queue.writeBuffer/writeTexture`，简单直接。
- GPU 资源之间搬运：使用 Encoder Copy，避免数据绕回 CPU。
- GPU 结果回读：Copy 到 MAP_READ Buffer，再 `mapAsync()`。
- 大量持续上传：考虑复用 MAP_WRITE Staging Buffer 池。
- 创建时只初始化一次：可考虑 `mappedAtCreation`。

## 五、和 WebGL 对比

WebGL 中也有对应的数据上传和复制操作，但它们依赖当前绑定状态：

```js
gl.bindBuffer(gl.ARRAY_BUFFER, buffer);
gl.bufferSubData(gl.ARRAY_BUFFER, byteOffset, typedArray);

gl.bindTexture(gl.TEXTURE_2D, texture);
gl.texSubImage2D(/* target、level、区域、格式、数据 */);
```

WebGPU 不依赖“当前绑定的目标对象”，而是把 Destination 直接作为参数：

```js
device.queue.writeBuffer(buffer, byteOffset, typedArray);
device.queue.writeTexture({ texture }, data, layout, size);
```

WebGL 2 的 GPU 内 Buffer Copy 使用：

```js
gl.bindBuffer(gl.COPY_READ_BUFFER, source);
gl.bindBuffer(gl.COPY_WRITE_BUFFER, destination);
gl.copyBufferSubData(
  gl.COPY_READ_BUFFER,
  gl.COPY_WRITE_BUFFER,
  sourceOffset,
  destinationOffset,
  size,
);
```

WebGPU 则把源、目标和范围全部录制进 CommandEncoder：

```js
encoder.copyBufferToBuffer(source, sourceOffset, destination, destinationOffset, size);
```

对应关系：

| 任务 | WebGL 2 | WebGPU |
| --- | --- | --- |
| CPU → Buffer | `bufferData` / `bufferSubData` | `queue.writeBuffer`、MAP_WRITE Staging、`mappedAtCreation` |
| CPU → Texture | `texImage2D` / `texSubImage2D` | `queue.writeTexture`、`copyExternalImageToTexture`、Buffer→Texture Copy |
| Buffer → Buffer | `copyBufferSubData` | `copyBufferToBuffer` |
| Texture/Framebuffer → CPU | `readPixels`；也可配合 Pixel Pack Buffer | Texture→Buffer→`mapAsync` |
| GPU Buffer → CPU | `getBufferSubData` | Buffer→MAP_READ Buffer→`mapAsync` |
| 行布局 | `PACK_ALIGNMENT`、`UNPACK_ALIGNMENT` 等像素存储状态 | 显式 `bytesPerRow`、`rowsPerImage`；GPU Copy 行跨度按 256 对齐 |
| 资源用途 | 通过绑定 Target 表达当前用途 | 创建时声明 `GPUBufferUsage` / `GPUTextureUsage` |
| GPU 命令 | 调用立即进入 WebGL 命令流 | Encoder 录制，`finish()` 后由 Queue 提交 |

WebGL 的普通 `readPixels` 很容易造成 CPU 等待 GPU；WebGPU 强制通过 Copy + 异步 `mapAsync` 暴露这个等待过程。代码更显式，但也更容易看清同步点并设计多 Buffer 流水线。

这一章记住：

**CPU 直接上传用 Queue Write；GPU 资源之间搬运用 Encoder Copy；GPU 数据回到 JavaScript 要先 Copy 到 MAP_READ Buffer 再异步映射。Texture 的行布局尤其要区分 `writeTexture` 的紧凑行和 Buffer↔Texture Copy 的 256-byte `bytesPerRow` 对齐。**

配套示例：[`copying-data.html`](./copying-data.html)

# Limits and Features（限制与可选特性）

原文：[WebGPU 可选特性与限制](https://webgpufundamentals.org/webgpu/lessons/zh_cn/webgpu-limits-and-features.html)

WebGPU 不会直接把当前显卡的全部能力交给应用。它先通过 Adapter 告诉你“最多能提供什么”，再由应用在创建 Device 时声明“实际需要什么”。这一层能力协商让程序能够明确区分通用基线、必要能力和可选增强，避免在高端开发机上无意写出只能在少数设备运行的代码。

## 一、Adapter 报告可用能力，Device 才是实际能力

请求 Adapter 后，可以读取两类信息：

```js
const adapter = await navigator.gpu?.requestAdapter();

console.log(adapter.limits.maxColorAttachments);
console.log(adapter.features.has("float32-filterable"));
```

- `adapter.limits` 是 `GPUSupportedLimits`，表示当前 Adapter **最多可以提供**的各项数值能力。
- `adapter.features` 是一个只读的 setlike 集合，表示当前 Adapter **可以申请**的可选特性；常用 `has()` 检查，也可以迭代。
- Adapter 支持某项能力，不等于随后创建的 Device 已经获得该能力。
- 真正创建 Buffer、Texture、Pipeline 并提交命令时，应以 `device.limits` 与 `device.features` 为准。

常见 Limit：

| Limit | 控制什么 | 超过后的典型结果 |
| --- | --- | --- |
| `maxBufferSize` | 单个 GPUBuffer 的最大尺寸 | `createBuffer` 验证失败 |
| `maxUniformBufferBindingSize` | 单次 Uniform Buffer Binding 可见的最大范围 | BindGroup 创建失败 |
| `maxStorageBufferBindingSize` | 单次 Storage Buffer Binding 可见的最大范围 | BindGroup 创建失败 |
| `maxTextureDimension2D` | 2D Texture 的最大宽高 | `createTexture` 验证失败 |
| `maxBindGroups` | Pipeline 可使用的 BindGroup 数量 | Pipeline/Layout 验证失败 |
| `maxComputeWorkgroupStorageSize` | 一个 Compute Workgroup 的共享内存上限 | Shader/Pipeline 验证失败 |

这些字段不是“当前用了多少”，而是 Device 允许应用使用的边界。例如 `maxBufferSize = 268435456` 表示单个 Buffer 最多 256 MiB，并不表示浏览器已经分配了 256 MiB。

WebGPU 规范定义了一组所有合规实现都必须保证的默认基线。应用只依赖这些基线时，覆盖设备范围最广；需要超出基线时，必须显式申请更高 Limit，并接受可运行设备减少这一结果。

## 二、用 requiredLimits 和 requiredFeatures 创建 Device

创建 Device 时可以同时提出数值限制和可选特性要求：

```js
const needMaxBufferSize = 512 * 1024 * 1024;
const feature = "float32-filterable";

if (adapter.limits.maxBufferSize < needMaxBufferSize) {
  throw new Error("需要 512 MiB Buffer，但当前 Adapter 不支持");
}

if (!adapter.features.has(feature)) {
  throw new Error("当前 Adapter 不支持 float32 纹理线性过滤");
}

const device = await adapter.requestDevice({
  requiredLimits: {
    maxBufferSize: needMaxBufferSize,
  },
  requiredFeatures: [feature],
});
```

这里有三个不同阶段：

```text
adapter.limits / adapter.features
        ↓ 先检查是否可提供
requiredLimits / requiredFeatures
        ↓ 声明本应用需要的最小能力集合
device.limits / device.features
        ↓ 后续代码实际可以使用的能力
创建 GPU 资源与 Pipeline
```

如果任一 Required 项无法满足，`requestDevice()` 返回的 Promise 会 reject。它不是“尽量满足”：写进 `requiredFeatures` 就表示没有它不能继续；写进 `requiredLimits` 就表示至少要达到这个阈值。

一个 Adapter 用来协商并创建一个逻辑 Device；不要把同一个 `GPUAdapter` 当成可以反复创建多个 Device 的工厂。若调试示例需要把“默认 Device”和“按需 Device”同时摆出来比较，应分别调用 `requestAdapter()` 获取两个 Adapter，再各调用一次 `requestDevice()`。普通应用通常只需要一次 Adapter → Device 流程。

以原文中的 `float32-filterable` 为例：普通情况下，`rgba32float` 纹理不能与 Filtering Sampler 做线性过滤；Device 显式启用这个 Feature 后才能依赖该组合。只在 Adapter 上看到它而没有请求，不能直接使用。

```js
const canUseLinearFloat32 = adapter.features.has("float32-filterable");

const device = await adapter.requestDevice({
  requiredFeatures: canUseLinearFloat32
    ? ["float32-filterable"]
    : [],
});

if (device.features.has("float32-filterable")) {
  // 增强路径：rgba32float + linear filtering
} else {
  // 回退路径：nearest filtering，或改用其他可过滤格式
}
```

## 三、为什么不能把 Adapter 的全部能力都申请下来

下面的写法看起来省事，但原文明确不推荐：

```js
// 不推荐：把开发机能提供的所有能力全部申请给 Device。
const device = await adapter.requestDevice({
  requiredLimits: copyAllLimits(adapter.limits),
  requiredFeatures: [...adapter.features],
});
```

问题不只是“申请太多”：它会让代码在不知情时依赖开发机的高能力。

假设开发机支持 `float32-filterable`，并把全部 Features 都启用了。后来某段 Shader 使用 `rgba32float + linear sampler`，它会在开发机上自然通过；应用部署到不支持该 Feature 的手机时，Device 创建直接失败。类似地，开发机启用了很大的 `maxBufferSize` 后，代码可能悄悄创建超过通用基线的 Buffer。

`adapter.limits` 也不能简单用对象展开复制：

```js
const limits = { ...adapter.limits }; // 通常得不到所有 Limit
```

这是因为 `GPUSupportedLimits` 的字段由接口原型上的 getter 暴露，而 `requiredLimits` 接收 Web IDL 的 `record`，转换时读取的是对象自身属性。虽然可以循环字段手动复制，但“能够复制”不代表“应该全部申请”。正确做法仍是逐项写出真实需求。

只申请最小集合还有一个调试收益：如果代码以后误用了没有申请的高级能力，WebGPU 会尽早给出验证错误，而不是让这项隐式依赖隐藏到发布后才暴露。

## 四、实际工程：必需能力、增强能力与回退路径

能力协商适合在程序初始化阶段集中完成。可以先把产品需求分成两类：

```js
const REQUIRED_MAX_BUFFER_SIZE = 512 * 1024 * 1024;

// 必需能力：不满足就不能运行当前方案。
if (adapter.limits.maxBufferSize < REQUIRED_MAX_BUFFER_SIZE) {
  showUnsupportedMessage();
  return;
}

// 增强能力：有则启用，没有就采用兼容路径。
const useFloat32LinearFiltering =
  adapter.features.has("float32-filterable");

const device = await adapter.requestDevice({
  requiredLimits: {
    maxBufferSize: REQUIRED_MAX_BUFFER_SIZE,
  },
  requiredFeatures: useFloat32LinearFiltering
    ? ["float32-filterable"]
    : [],
});
```

建议把决策结果保存成明确的应用配置，而不是让各个渲染模块反复查询：

```js
const capabilities = {
  useFloat32LinearFiltering:
    device.features.has("float32-filterable"),
  maxBufferSize: device.limits.maxBufferSize,
};
```

随后由 Pipeline、纹理格式和资源分配代码统一读取 `capabilities`。常见策略是：

- **硬性失败**：核心算法确实需要某 Feature 或更高 Limit，并且没有合理替代方案。
- **降低质量**：减少 Texture 尺寸、灯光数量、同时可见对象或采样数量。
- **更换实现**：线性过滤改 nearest、压缩纹理改未压缩格式、一次大 Buffer 改成分块处理。
- **能力分档**：初始化时确定 low / medium / high 档，后续逻辑只使用已经选定的档位。

不要用“在我机器上 Adapter 报告的值”当成通用常量，也不要为了追求最高数值而申请应用根本不会使用的 Limit。申请得越高，能满足要求的设备范围通常越小。

## 五、和 WebGL 对比

WebGL 同样需要查询限制与扩展，但能力模型不同。WebGL 通常先创建 Context，再从这个 Context 查询：

```js
const gl = canvas.getContext("webgl2");

const maxTextureSize = gl.getParameter(gl.MAX_TEXTURE_SIZE);
const colorBufferFloat = gl.getExtension("EXT_color_buffer_float");

if (colorBufferFloat) {
  // 扩展存在，并且 getExtension 已将它启用在当前 Context 上。
}
```

WebGPU 把“实现可提供”与“当前逻辑设备已启用”拆成两层：

```js
const adapter = await navigator.gpu.requestAdapter();

if (!adapter.features.has("float32-filterable")) {
  // 在创建 Device 前决定失败还是回退。
}

const device = await adapter.requestDevice({
  requiredFeatures: ["float32-filterable"],
});
```

| 能力问题 | WebGL 2 | WebGPU |
| --- | --- | --- |
| 查询数值限制 | `gl.getParameter(gl.MAX_...)` | `adapter.limits` 与 `device.limits` |
| 查询可选能力 | `gl.getExtension(name)` | `adapter.features.has(name)` |
| 启用可选能力 | 获取 Extension 对象后使用扩展 API/行为 | 创建 Device 时放入 `requiredFeatures` |
| 要求更高数值能力 | 创建 Context 后查询，不满足则应用自行退出/降级 | 创建 Device 前用 `requiredLimits` 协商，无法满足则 Promise reject |
| 能力所属对象 | WebGLRenderingContext | Adapter 报告可用能力，Device 保存已授予能力 |
| 可移植性策略 | 查询 Context 后分支 | 先检查 Adapter，再申请最小 Device 能力集合 |

WebGL 的 Extension 对象经常还会提供额外常量和函数；WebGPU Feature 通常不返回一个功能对象，而是解锁已有 API、格式或验证规则。两者都需要能力检测，但 WebGPU 把协商时机提前到 Device 创建阶段，并把应用依赖写进了显式描述对象。

这一章记住：

**Adapter 表示“可提供什么”，Device 表示“已经获得什么”。先按需求检查 Adapter，只申请真正需要的 Limits 与 Features；必需能力不满足就明确失败，可选增强不满足就走预先设计的回退路径。**

配套示例：[`limits-and-features.html`](./limits-and-features.html)

# Timing（计时与性能）

原文：[WebGPU 计时与性能](https://webgpufundamentals.org/webgpu/lessons/zh_cn/webgpu-timing.html)

渲染性能不能用一个数字完整描述。本章区分三项最常见的指标：FPS 表示页面呈现节奏，JavaScript 时间表示 CPU 侧每帧准备和编码命令的开销，GPU Timestamp 表示某个 Render Pass 或 Compute Pass 在 GPU 时间轴上的持续时间。三者测量边界不同，必须一起理解。

## 一、FPS、JavaScript 时间和 GPU 时间不是一回事

`requestAnimationFrame` 会把一个高精度时间戳传给回调。相邻两次回调的间隔可以估算 FPS：

```js
let then = 0;

function render(now) {
  const deltaTime = now - then; // 毫秒
  then = now;

  const fps = 1000 / deltaTime;
  requestAnimationFrame(render);
}

requestAnimationFrame(render);
```

FPS 表示浏览器实际调用动画回调的节奏，但它不只由 GPU 决定，还会受到显示器刷新率、垂直同步、主线程占用、浏览器调度、窗口是否可见等因素影响。60 FPS 对应的帧间隔约为 `16.67 ms`，不代表 GPU 一定工作了 16.67 ms。

JavaScript 每帧时间可以用 `performance.now()` 包住同步代码：

```js
function render(now) {
  const jsStart = performance.now();

  updateObjects();
  device.queue.writeBuffer(/* ... */);
  encodeCommands();
  device.queue.submit([commandBuffer]);

  const jsTime = performance.now() - jsStart;
  requestAnimationFrame(render);
}
```

这个数值可以覆盖对象更新、数组写入、WebGPU API 调用、命令编码和提交等 CPU 侧工作，但通常**不包含 GPU 真正完成命令的时间**。WebGPU 的命令执行是异步的，`queue.submit()` 返回只表示命令已交给 Queue，并不表示 GPU 已经画完。

因此不能这样测 GPU：

```js
const start = performance.now();
device.queue.submit([commandBuffer]);
const gpuTime = performance.now() - start; // 错：主要只是提交调用耗时
```

三者的边界可以记成：

| 指标 | 时间轴 | 主要包含 | 不直接代表 |
| --- | --- | --- | --- |
| FPS / 帧间隔 | 浏览器呈现循环 | rAF 调度到下一次 rAF 的整体间隔 | 单独的 JS 或 GPU 工作耗时 |
| JavaScript 时间 | CPU 主线程 | 数据更新、命令编码、API 调用、提交 | GPU 完成命令的时间 |
| GPU Timestamp | GPU 时间轴 | 指定 Render/Compute Pass 的 GPU 持续时间 | 页面总帧时间、最终吞吐量 |

## 二、timestamp-query：先检测 Feature，再创建查询资源

GPU 时间戳是可选的 `timestamp-query` Feature。它必须像上一章的其他可选能力一样先在 Adapter 上检查，再在创建 Device 时显式申请：

```js
const adapter = await navigator.gpu?.requestAdapter();
const canTimestamp = adapter.features.has("timestamp-query");

const device = await adapter.requestDevice({
  requiredFeatures: canTimestamp
    ? ["timestamp-query"]
    : [],
});
```

如果它不是应用的硬性要求，推荐保持回退路径：Feature 可用时显示 GPU 时间，不可用时继续运行 FPS 与 JavaScript 计时。不要因为一个调试指标不可用，就让整个渲染程序无法启动。

启用后需要三个资源：

```js
const querySet = device.createQuerySet({
  type: "timestamp",
  count: 2, // Pass 开始与结束
});

const resolveBuffer = device.createBuffer({
  size: 2 * 8,
  usage:
    GPUBufferUsage.QUERY_RESOLVE |
    GPUBufferUsage.COPY_SRC,
});

const resultBuffer = device.createBuffer({
  size: 2 * 8,
  usage:
    GPUBufferUsage.COPY_DST |
    GPUBufferUsage.MAP_READ,
});
```

`GPUQuerySet` 像一个 GPU 查询结果数组。开始和结束时间各占一个元素，所以 `count` 至少为 2；每个 Timestamp 是 64-bit，即 8 bytes。

为什么要两个 Buffer：

- `resolveBuffer` 接收 `resolveQuerySet()` 的结果，需要 `QUERY_RESOLVE`；它还要作为后续 Copy 的源，所以带 `COPY_SRC`。
- `resultBuffer` 是 JavaScript Readback Staging Buffer，需要 `COPY_DST | MAP_READ`。
- QuerySet 不能直接映射；如果结果只在 GPU 内继续使用，可以停在 Resolve Buffer，不一定要复制回 JavaScript。

## 三、从 Pass 时间戳到 BigUint64Array

在 Render Pass 或 Compute Pass 描述符上设置开始、结束索引：

```js
const renderPassDescriptor = {
  colorAttachments: [/* ... */],
  ...(canTimestamp && {
    timestampWrites: {
      querySet,
      beginningOfPassWriteIndex: 0,
      endOfPassWriteIndex: 1,
    },
  }),
};
```

Pass 结束后，在同一个 CommandEncoder 中依次解析和复制：

```text
Render / Compute Pass
        ↓ timestampWrites 写入索引 0、1
GPUQuerySet
        ↓ encoder.resolveQuerySet()
QUERY_RESOLVE | COPY_SRC Buffer
        ↓ encoder.copyBufferToBuffer()
COPY_DST | MAP_READ Buffer
        ↓ mapAsync(READ)
JavaScript BigUint64Array
```

对应代码：

```js
pass.end();

encoder.resolveQuerySet(querySet, 0, 2, resolveBuffer, 0);

if (resultBuffer.mapState === "unmapped") {
  encoder.copyBufferToBuffer(
    resolveBuffer, 0,
    resultBuffer, 0,
    resultBuffer.size,
  );
}

device.queue.submit([encoder.finish()]);
```

`GPUBuffer.mapState` 有三种状态：

| 状态 | 含义 | 能否作为 GPU Copy 目标 |
| --- | --- | --- |
| `unmapped` | 没有映射，也没有等待映射 | 可以 |
| `pending` | 已调用 `mapAsync`，正在等 GPU | 不可以 |
| `mapped` | JavaScript 正在访问映射内存 | 不可以 |

Readback Buffer 忙碌时可以跳过当前帧的 Copy，继续使用最近一次 GPU 时间，而不是在动画循环中 `await mapAsync()` 强行等待 GPU。更完整的性能工具通常会维护多个 Readback Buffer 组成池或环形队列，以提高采样频率并减少争用。

异步读取时使用 `BigUint64Array`：

```js
resultBuffer.mapAsync(GPUMapMode.READ).then(() => {
  const times = new BigUint64Array(
    resultBuffer.getMappedRange(),
  );

  // 先做 bigint 减法，再转成 number。
  const nanoseconds = Number(times[1] - times[0]);
  const microseconds = nanoseconds / 1000;

  resultBuffer.unmap();
});
```

Timestamp 的原始结果是纳秒单位的 `u64`。`BigUint64Array` 元素是 `bigint`，不能直接与普通 `number` 混合运算；应先用两个 `bigint` 相减，再把较小的时间差转换为 `number`。转换整个绝对时间戳更容易超过 JavaScript `number` 的 53-bit 精确整数范围。

## 四、稳定数值与正确解读性能

FPS、JS 和 GPU 时间都会逐帧抖动。原文使用非负滚动平均：保留最近 N 个有效样本，同时维护总和；加入新样本时减去被替换的最旧样本。

```js
class NonNegativeRollingAverage {
  constructor(size = 30) {
    this.size = size;
    this.samples = [];
    this.cursor = 0;
    this.total = 0;
  }

  add(value) {
    if (!Number.isFinite(value) || value < 0) return;

    this.total -= this.samples[this.cursor] ?? 0;
    this.total += value;
    this.samples[this.cursor] = value;
    this.cursor = (this.cursor + 1) % this.size;
  }

  get average() {
    return this.total / this.samples.length;
  }
}
```

只接受有限非负值，是因为时间戳实现可能产生不可用样本。滚动平均能让趋势更容易观察，但窗口越大，显示越稳定、对变化的反应也越慢；它不会修复错误的测量边界。

更重要的是：`timestamp-query` 适合调试和在**同一台设备、相同场景**中比较实现，不适合当成跨用户、跨 GPU 的绝对性能结论。

- 不同 GPU 的调度、缓存、并行执行和跨 Pass 优化方式不同。
- 某方案在 Timestamp 中显示 Pass 更短，不一定拥有更高的整帧吞吐量。
- 浏览器可能为了降低指纹识别风险而量化时间戳；原文指出 Chrome 默认可能按 `100 µs` 粒度量化。
- Readback 本身是异步的，页面显示的通常是最近一次完成的样本，不保证来自当前正在呈现的这一帧。

原文给出的教训很典型：Mipmap Compute 方案的 Timestamp 曾显示比 Render 方案快 5 倍，但改用“60 FPS 下每秒能处理多少张 2048×2048 纹理”的吞吐量测试后，Render 方案反而在两台机器上分别快 20% 和 8%。

因此评估优化时建议结合：

1. Timestamp：定位具体 Pass 或技术实现的 GPU 时间。
2. JavaScript 时间：检查 CPU 数据准备与命令编码成本。
3. FPS / Frame Time：观察最终交互是否稳定。
4. 吞吐量测试：逐步增加真实工作量，找出保持目标帧率时能处理的最大规模。
5. 多设备实测：避免用一块 GPU 的结果替代全部用户。

## 五、和 WebGL 对比

FPS 与 JavaScript 时间在 WebGL 和 WebGPU 中测法相同，都使用 `requestAnimationFrame` 和 `performance.now()`。GPU 时间都需要可选能力和异步读取，不能用 CPU 包围一次 Draw/Submit 来替代。

WebGL 2 常用 `EXT_disjoint_timer_query_webgl2`：

```js
const ext = gl.getExtension(
  "EXT_disjoint_timer_query_webgl2",
);

const query = gl.createQuery();
gl.beginQuery(ext.TIME_ELAPSED_EXT, query);

drawScene(gl);

gl.endQuery(ext.TIME_ELAPSED_EXT);
```

之后在后续帧轮询结果，不能同步等待：

```js
const available = gl.getQueryParameter(
  query,
  gl.QUERY_RESULT_AVAILABLE,
);
const disjoint = gl.getParameter(ext.GPU_DISJOINT_EXT);

if (available && !disjoint) {
  const nanoseconds = gl.getQueryParameter(
    query,
    gl.QUERY_RESULT,
  );
}
```

WebGPU 的对应路径更显式：

| 计时步骤 | WebGL 2 | WebGPU |
| --- | --- | --- |
| 能力检测 | `getExtension("EXT_disjoint_timer_query_webgl2")` | `adapter.features.has("timestamp-query")` |
| 启用能力 | 获得 Extension 对象 | `requiredFeatures: ["timestamp-query"]` |
| 标记范围 | `beginQuery/endQuery(TIME_ELAPSED_EXT)` | Pass Descriptor 的 `timestampWrites` |
| 查询容器 | `WebGLQuery` | `GPUQuerySet` 的两个索引 |
| 获取结果 | 轮询 `QUERY_RESULT_AVAILABLE` | `resolveQuerySet` → Copy → `mapAsync` |
| 异常样本 | 检查 `GPU_DISJOINT_EXT` | 丢弃非有限或负的差值，并接受实现定义/量化结果 |
| 结果单位 | 纳秒 | `u64` 纳秒，读取为 `bigint` |

WebGL Extension 将“测量时间段”包在命令流的 `beginQuery/endQuery` 之间；WebGPU 把 Pass 边界、QuerySet 索引、Resolve 和 Readback 都写成显式资源与命令。WebGPU 代码更长，但资源用途、异步同步点和数据流也更清楚。

这一章记住：

**FPS 测呈现节奏，`performance.now()` 测 CPU/JavaScript 工作，`timestamp-query` 测 GPU Pass；时间戳必须异步 Resolve 和 Readback，并且只能作为调试线索，最终性能结论要结合真实吞吐量与多设备测试。**

配套示例：[`timing.html`](./timing.html)

# WGSL（WebGPU Shading Language）

原文：[WebGPU WGSL](https://webgpufundamentals.org/webgpu/lessons/zh_cn/webgpu-wgsl.html)

扩展阅读：[Tour of WGSL](https://google.github.io/tour-of-wgsl/) · [W3C WGSL 规范](https://www.w3.org/TR/WGSL/)

WGSL 是 WebGPU 的着色语言。它描述 Vertex、Fragment 和 Compute 阶段在 GPU 上执行的程序，也声明这些程序需要的 Buffer、Texture、Sampler 与阶段接口。WGSL 是严格类型语言；浏览器会先解析、验证 Shader Module，再结合入口点和 Pipeline 状态验证完整接口。

## 一、严格类型、字面量与显式转换

WGSL 的主要标量类型：

| 类型 | 含义 | 常见用途 |
| --- | --- | --- |
| `i32` | 32-bit 有符号整数 | 循环、带符号索引@group(0)和计算 |
| `u32` | 32-bit 无符号整数 | `vertex_index`、`instance_index`、位运算 |
| `f32` | 32-bit 浮点数 | 位置、颜色、矩阵和绝大多数图形计算 |
| `bool` | 布尔值 | 条件判断与比较结果 |
| `f16` | 16-bit 浮点数 | 降低带宽与提高部分设备的吞吐量；需可选 `shader-f16` Feature |

变量、函数参数和返回值都有确定类型：

```wgsl
var scale: f32 = 1.0;
let count: u32 = 4u;

fn doubleValue(value: f32) -> f32 {
  return value * 2.0;
}
```

能从右侧确定类型时可以省略声明类型：

```wgsl
var a = 1;       // 具体化为 i32
let b = 2.0;     // 具体化为 f32
let c = 3u;      // u32
let d = false;   // bool
```

数值后缀可以把意图写清楚：

```wgsl
2i     // i32
3u     // u32
4f     // f32
4.5f   // f32
5h     // f16
5.6h   // f16
6      // AbstractInt
7.0    // AbstractFloat
```

`AbstractInt` 与 `AbstractFloat` 是编译期尚未具体化的数值。例如 `1 + 2.0` 可以根据上下文具体化为浮点运算；一旦值已经成为 `i32` 或 `f32`，不同数值类型不能随意混算：

```wgsl
let integerValue: i32 = 3;
let floatValue: f32 = 2.5;

// let wrong = integerValue + floatValue; // 错：i32 + f32
let result = f32(integerValue) + floatValue;
```

WGSL 不用 JavaScript 式的隐式类型强制转换。`f32(value)`、`i32(value)`、`u32(value)` 既表达转换，也让溢出、截断和精度变化的位置清晰可见。循环计数常使用整数，参与坐标或颜色计算前再显式转成 `f32`。

`f16` 不是默认能力，使用前要像其他可选 Feature 一样协商：

```js
const canUseF16 = adapter.features.has("shader-f16");
const device = await adapter.requestDevice({
  requiredFeatures: canUseF16 ? ["shader-f16"] : [],
});
```

没有启用 `shader-f16` 的 Device 不能成功使用包含 `f16` 类型的 WGSL Module。

## 二、let、var、const 与复合数据类型

WGSL 中三个声明关键字与 JavaScript 同名，但含义不能照搬：

```wgsl
const PI: f32 = 3.141592653589793; // 编译期常量

fn update(runtimeInput: f32) -> f32 {
  let doubled = runtimeInput * 2.0; // 运行期不可变值

  var result = doubled;             // 有存储、可以重新赋值
  result += 1.0;
  return result;
}
```

| 声明 | WGSL 含义 | 能否重新赋值 | 初始化时机 |
| --- | --- | --- | --- |
| `const` | 编译期常量 | 否 | 必须是编译期可求值表达式 |
| `let` | 运行期计算出的不可变值 | 否 | 可以依赖函数参数、Uniform、Texture 结果等 |
| `var` | 拥有存储的变量 | 可以 | 可以是函数局部，也可以声明 GPU 地址空间资源 |

因此下面是错误的：

```wgsl
fn bad(runtimeInput: f32) {
  // const value = runtimeInput * 2.0;
  // 错：const 不能依赖运行期参数

  let value = runtimeInput * 2.0;
  // value = 3.0;
  // 错：let 不可重新赋值
}
```

Module 作用域的资源通常使用带地址空间的 `var`：

```wgsl
@group(0) @binding(0)
var<uniform> params: Params;

@group(0) @binding(1)
var<storage, read> values: array<f32>;

@group(0) @binding(2)
var<storage, read_write> results: array<vec4f>;
```

这里的 `uniform`、`storage` 描述数据所在的 GPU 地址空间，`read/read_write` 描述 Storage Buffer 的访问模式；它们不是普通函数局部变量。

WGSL 的复合类型是图形计算的主体：

```wgsl
let position: vec2f = vec2f(0.25, -0.5);
let color: vec4f = vec4f(1.0, 0.5, 0.2, 1.0);
let indices: vec3u = vec3u(0u, 1u, 2u);

let transform: mat2x2f = mat2x2f(
  1.0, 0.0,
  0.0, 1.0,
);
```

`vec2f` 是 `vec2<f32>` 的快捷写法；类似地还有 `vec3i`、`vec4u`、`vec2h`。向量支持逐分量算术和 Swizzle：

```wgsl
let rgba = vec4f(0.2, 0.4, 0.6, 1.0);
let blue = rgba.z;       // 也可写 rgba.b
let blueRed = rgba.zx;   // vec2f(0.6, 0.2)
let repeated = rgba.zzy; // vec3f(0.6, 0.6, 0.4)
```

WGSL v1 不能把 Swizzle 放在赋值左侧：

```wgsl
var color = vec4f(0.2, 0.4, 0.6, 1.0);
// color.rgb = color.bgr; // 错
color = vec4f(color.bgr, color.a); // 正确：构造完整新值
```

矩阵类型写作 `mat列数x行数<类型>`，因此 `mat3x4f` 是 3 个 `vec4f` 列向量。`matrix[index]` 取得一列；常用 `mat4x4f * vec4f` 完成变换。矩阵的列数、行数顺序不要凭视觉猜测。

固定数组和结构体：

```wgsl
struct Material {
  baseColor: vec4f,
  roughness: f32,
};

let corners = array<vec2f, 3>(
  vec2f(-1.0, -1.0),
  vec2f( 3.0, -1.0),
  vec2f(-1.0,  3.0),
);
```

构造器能推断元素类型与长度，所以也可以写 `array(value0, value1, value2)`。固定数组长度是类型的一部分；原文指出 WGSL v1 没有通用方式在 Shader 中查询固定数组长度。

运行时长度数组只能出现在 Storage Buffer 的根声明，或结构体最后一个字段：

```wgsl
struct MeshData {
  color: vec4f,
  vertices: array<vec3f>, // 必须是最后一个字段
};

@group(0) @binding(0)
var<storage, read> meshes: MeshData;

fn readCount() -> u32 {
  return arrayLength(&meshes.vertices);
}
```

它的实际元素数量由 BindGroup 绑定的 Buffer 范围决定，而不是写死在 WGSL 类型中。

## 三、函数、入口点与资源可达性

普通函数使用 `fn name(parameters) -> ReturnType`：

```wgsl
fn rotate2D(point: vec2f, angle: f32) -> vec2f {
  let c = cos(angle);
  let s = sin(angle);
  return mat2x2f(c, s, -s, c) * point;
}
```

入口点是在普通函数基础上增加阶段属性：

```wgsl
@vertex fn vertexMain(/* ... */) -> VertexOutput {
  // 每个顶点调用一次
}

@fragment fn fragmentMain(/* ... */) -> @location(0) vec4f {
  // 每个片段调用一次
}

@compute @workgroup_size(64)
fn computeMain(/* ... */) {
  // 每个 Compute Invocation 调用一次
}
```

一个 `GPUShaderModule` 可以同时包含多个普通函数和多个入口点。Pipeline Descriptor 通过 `entryPoint` 选择本条 Pipeline 实际使用的函数：

```js
const pipeline = device.createRenderPipeline({
  layout: "auto",
  vertex: {
    module,
    entryPoint: "vertexMain",
  },
  fragment: {
    module,
    entryPoint: "fragmentPattern",
    targets: [{ format }],
  },
});
```

最重要的规则之一是：**一个入口点只需要它直接或间接访问到的 Module 声明。**

```wgsl
@group(0) @binding(0)
var<uniform> params: vec4f;

fn readParams() -> vec4f {
  return params;
}

@fragment fn fragmentSolid() -> @location(0) vec4f {
  return vec4f(0.2, 0.3, 0.4, 1.0);
}

@fragment fn fragmentPattern() -> @location(0) vec4f {
  return readParams(); // 间接访问 params
}
```

- `fragmentSolid` 不可达 `params`，所以使用它的自动 Pipeline Layout 不要求 `@group(0) @binding(0)`。
- `fragmentPattern` 通过 `readParams()` 间接访问 Uniform，所以使用它的 Pipeline 必须提供对应 BindGroup。
- 同一个 Module 中“声明了资源”并不等于每个入口点都需要它。
- `_ = params;` 虽然丢弃结果，但仍算访问，可用来有意让某资源进入入口点接口。

配套示例正是用同一个 WGSL Module 创建两条 Pipeline：Pattern 绘制时设置 BindGroup；Solid 绘制时完全不设置 BindGroup，仍通过真实 WebGPU 验证。

这个可达性规则也解释了为什么 `layout: "auto"` 必须结合具体 Pipeline 和入口点理解。自动布局不是简单扫描整个 Shader Module 的全部 `@group/@binding`，而是根据被选入口点实际可达的资源接口生成。

## 四、属性、Built-in 与控制流

WGSL 中以 `@` 开头的是语言属性。`@location` 负责用户自定义阶段接口，`@builtin` 负责 WebGPU 固定语义。

`@location` 在三个位置的含义：

```wgsl
struct VertexInput {
  @location(0) position: vec2f, // 来自 Vertex Buffer attribute
  @location(1) color: vec4f,
};

struct VertexOutput {
  @builtin(position) position: vec4f,
  @location(0) color: vec4f,    // 传给 Fragment location 0
};

struct FragmentOutput {
  @location(0) albedo: vec4f,   // 写 Color Attachment 0
  @location(1) normal: vec4f,   // 写 Color Attachment 1
};
```

阶段间字段名与顺序可以不同，只要 `@location` 和类型匹配：

```wgsl
struct VSOut {
  @builtin(position) position: vec4f,
  @location(0) color: vec4f,
  @location(1) uv: vec2f,
};

struct FSIn {
  @location(1) textureCoordinates: vec2f,
  @location(0) diffuse: vec4f,
};
```

常见 Built-in：

| Built-in | 阶段与方向 | 类型 | 用途 |
| --- | --- | --- | --- |
| `vertex_index` | Vertex 输入 | `u32` | 当前 Draw 中的顶点索引 |
| `instance_index` | Vertex 输入 | `u32` | 当前实例索引 |
| `position` | Vertex 输出 | `vec4f` | 裁剪空间齐次位置 |
| `position` | Fragment 输入 | `vec4f` | 当前片段的 Framebuffer 坐标与深度 |
| `front_facing` | Fragment 输入 | `bool` | 当前片段是否来自正面图元 |
| `frag_depth` | Fragment 输出 | `f32` | 覆盖默认片段深度 |
| `sample_index` / `sample_mask` | Fragment | `u32` | MSAA 样本索引和覆盖掩码 |
| `global_invocation_id` | Compute 输入 | `vec3u` | Invocation 在整个 Dispatch 网格中的坐标 |
| `local_invocation_id` | Compute 输入 | `vec3u` | Invocation 在 Workgroup 内的坐标 |
| `workgroup_id` | Compute 输入 | `vec3u` | 当前 Workgroup 坐标 |

WGSL 提供 `for`、`while`、`loop`、`if`、`switch`、`break`、`continue` 和 `continuing`。它们与 C 系语言相似，但有几条容易从 JavaScript/GLSL 带错的习惯：

```wgsl
if value < 0.5 {             // 条件不要求括号
  value = 0.5;
}

for (var i: i32 = 0; i < 4; i++) {
  value += f32(i);
}

switch mode {                // 只接收 i32/u32
  case 0u: { value = 0.0; }
  case 1u, 2u: { value = 1.0; }
  default: { value = 0.5; }
}
```

- 没有 `condition ? a : b` 三元运算符；简单选择使用 `select(falseValue, trueValue, condition)`。
- `i++`、`i--` 是语句，不返回值；没有 `++i`，也不能写 `let old = i++`。
- `+=`、`-=` 等也是赋值语句，不是可以嵌套的表达式。
- `discard` 只能在 Fragment Shader 中终止当前片段。
- `break if condition;` 可在 `loop` 的 `continuing` 区域表达循环退出条件。
- `switch` 的条件只能是 `i32/u32`，Case 值必须是常量整数。

这些限制减少了表达式中的隐藏副作用。WGSL 允许的写法通常更显式，也更适合在不同 GPU 后端上做一致验证。

## 五、和 WebGL GLSL ES 对比

WebGL 2 使用 GLSL ES 3.00，WebGPU 使用 WGSL。两者都是 GPU 着色语言，也都有严格类型、向量、矩阵、内置函数和阶段接口，但 Shader 组织与资源模型不同。

一个最小顶点接口对比：

```glsl
// WebGL 2 / GLSL ES 3.00
#version 300 es

layout(location = 0) in vec2 position;
out vec2 uv;

uniform mat4 matrix;

void main() {
  gl_Position = matrix * vec4(position, 0.0, 1.0);
  uv = position * 0.5 + 0.5;
}
```

```wgsl
// WebGPU / WGSL
struct Uniforms {
  matrix: mat4x4f,
};

@group(0) @binding(0)
var<uniform> uniforms: Uniforms;

struct VSOut {
  @builtin(position) position: vec4f,
  @location(0) uv: vec2f,
};

@vertex fn vertexMain(
  @location(0) position: vec2f,
) -> VSOut {
  var output: VSOut;
  output.position = uniforms.matrix * vec4f(position, 0.0, 1.0);
  output.uv = position * 0.5 + vec2f(0.5);
  return output;
}
```

| 概念 | WebGL 2 / GLSL ES 3.00 | WebGPU / WGSL |
| --- | --- | --- |
| Shader 阶段组织 | Vertex 与 Fragment 通常是两份独立源码，编译后 Link 成 Program | 一个 Module 可包含 Vertex、Fragment、Compute 和多个入口点 |
| 默认入口点 | 固定为 `void main()` | 任意命名函数加 `@vertex/@fragment/@compute`，Pipeline 用 `entryPoint` 选择 |
| 顶点位置 | 写内置全局变量 `gl_Position` | 返回带 `@builtin(position)` 的值或结构字段 |
| 顶点输入 | `in` + `layout(location=N)` | `@location(N)` 参数或结构字段 |
| 阶段间变量 | Vertex `out` 与 Fragment `in`，按 Location/接口匹配 | 两端用 `@location(N)` 匹配 |
| Fragment 输出 | `out vec4 color` + Location | 返回 `@location(N)` 值或结构 |
| 普通 Uniform | Program Link 后用名称查询 `getUniformLocation` | `@group/@binding var<uniform>` + Buffer + BindGroup |
| Texture/Sampler | Sampler Uniform 关联 Texture Unit | Texture 与 Sampler 是独立 Binding 资源 |
| Shader 诊断 | `getShaderParameter`、`getShaderInfoLog`、Program Link Log | `GPUShaderModule.getCompilationInfo()` + Pipeline Validation/Error Scope |
| Compute Shader | WebGL 2 没有 | WGSL `@compute` + `dispatchWorkgroups` |

GLSL 同样不是 JavaScript：它也有 `int/uint/float/bool`、`vec*`、`mat*` 和构造器转换。但 WGSL 把地址空间、资源访问权限、BindGroup 位置和入口点属性放进同一套显式语法，浏览器能在创建 Pipeline 前后更系统地验证它们。

资源接口的差别尤其重要。WebGL Program 的 Uniform、Attribute 和 Sampler 状态分散在 Location、Texture Unit、UBO Binding Point 等位置；WGSL 则让 Shader 直接声明 `@group/@binding`，再由 Pipeline Layout 和 BindGroup 把 JavaScript 资源与声明对应起来。

这一章记住：

**WGSL 是严格类型语言：用明确类型和转换组织数据，用 `@vertex/@fragment/@compute` 定义入口点，用 `@location/@builtin` 连接 Pipeline 阶段，用 `@group/@binding` 声明资源；Pipeline 只要求当前入口点直接或间接可达的资源。**

配套示例：[`wgsl.html`](./wgsl.html)

# How It Works（WebGPU 工作原理）

官方原文：[WebGPU 工作原理](https://webgpufundamentals.org/webgpu/lessons/zh_cn/webgpu-how-it-works.html)

这一章不是继续罗列 API，而是在回答一个更根本的问题：执行 `pass.draw(3)` 之后，JavaScript、Shader、固定功能硬件和 Canvas 之间究竟发生了什么。

最重要的结论是：

> **JavaScript 不会逐个调用 Vertex Shader 或 Fragment Shader。JavaScript 只配置资源并编码 Draw 命令；GPU 根据 Draw 的规模批量运行 Shader，完成图元组装、光栅化、阶段变量插值和 Attachment 写入。**

## 一、Shader 是由 GPU 系统批量调用的函数

WGSL 中的 Vertex Shader 和 Fragment Shader 看起来都是普通函数，但它们不是由 JavaScript 直接调用的普通函数：

```wgsl
@vertex
fn vertexMain(input: VertexInput) -> VertexOutput {
  // 处理当前这一次 Vertex Invocation 对应的顶点
}

@fragment
fn fragmentMain(input: VertexOutput) -> @location(0) vec4f {
  // 处理光栅化器生成的当前片段
}
```

JavaScript 真正执行的是：

```js
const pass = encoder.beginRenderPass(renderPassDescriptor);
pass.setPipeline(pipeline);
pass.setVertexBuffer(0, vertexBuffer);
pass.setBindGroup(0, bindGroup);
pass.draw(3);            // 描述“画 3 个顶点”，并不是调用 vertexMain 3 次
pass.end();

device.queue.submit([encoder.finish()]);
```

`draw(3)` 提供调用规模。后面的工作由 WebGPU 实现、驱动和 GPU 完成：

```text
JavaScript 编码 draw(3)
        ↓
系统为 3 个顶点安排 Vertex Shader Invocation
        ↓
Vertex Shader 产生 3 份顶点输出
        ↓
固定功能硬件将 3 个顶点组装成三角形并光栅化
        ↓
系统为三角形覆盖的片段安排 Fragment Shader Invocation
```

可以用下面的 JavaScript 伪代码理解调用关系：

```js
function draw(count, vertexShader, fragmentShader) {
  const vertexOutputs = [];

  // 这层循环是 GPU 绘制系统的职责，不是实际 WebGPU 应用代码。
  for (let vertexIndex = 0; vertexIndex < count; ++vertexIndex) {
    const attributes = fetchVertexAttributes(vertexIndex);
    vertexOutputs.push(vertexShader(vertexIndex, attributes, bindings));
  }

  const triangles = assembleTriangles(vertexOutputs);
  const fragments = rasterize(triangles);

  for (const fragment of fragments) {
    const interpolated = interpolate(fragment, vertexOutputs);
    const color = fragmentShader(interpolated, bindings);
    writeColorAttachment(fragment.position, color);
  }
}
```

它只是一种帮助理解的 CPU 类比。真实 GPU 不会按这段代码串行执行，而会同时运行大量 Invocation。

Vertex Shader 的调用次数来自 Draw 参数和索引/实例配置；Fragment Shader 的调用次数则不是 `draw` 参数直接指定的，而取决于三角形覆盖范围、裁剪、深度测试、采样数等因素。示例中 `draw(3)` 只有 3 次顶点处理，却产生了数万个片段，这正是二者最直观的区别。

## 二、Shader 的六种数据来源

Shader 被系统调用时，必须有数据可读。原文把常见来源归纳为六类：

| 数据来源 | 从哪里来 | 典型用途 | 本章示例 |
| --- | --- | --- | --- |
| WGSL Constant | 写在 Shader Module 中 | 编译期固定参数 | 顶点 Z 值、输出 Alpha |
| Vertex Attribute | Vertex Buffer，经 Pipeline 的布局解释 | 每个顶点不同的位置、颜色、UV | 一个交错 Vertex Buffer |
| Uniform | Uniform Buffer，经 BindGroup 绑定 | 一次 Draw 中大量 Invocation 共享的小型参数 | 缩放、纹理混合比例、Offset 影响量 |
| Storage Buffer | Storage Buffer，经 BindGroup 绑定 | 更大、更灵活的数组；可按声明只读或读写 | 每个顶点的一组额外 Offset |
| Texture | Texture View 和 Sampler，经 BindGroup 绑定 | 图像、查表和过滤采样 | 2×2 RGBA 纹理与线性采样器 |
| Inter-stage Variable | 前一个 Shader 阶段输出，由固定功能硬件传给后一个阶段 | 在 Vertex 与 Fragment 之间传颜色、UV 等 | Vertex 输出的 `color` 与 `uv` |

### 1. Constant：直接编进 Shader

```wgsl
const POSITION_Z = 0.0;
const OUTPUT_ALPHA = 1.0;
```

Constant 不需要 JavaScript 创建 GPU 资源，也不能在每次 Draw 前动态更新。它适合算法中真正固定的值；经常变化的值应放入 Uniform 或其他 Buffer。

### 2. Vertex Attribute：随顶点变化的数据

WGSL 只声明 Location：

```wgsl
struct VertexInput {
  @location(0) position: vec2f,
  @location(1) color: vec3f,
  @location(2) uv: vec2f,
};
```

真正说明“每个顶点占多少字节、每个字段是什么格式、在什么 Offset”的是 Pipeline：

```js
buffers: [{
  arrayStride: 7 * 4,
  attributes: [
    { shaderLocation: 0, offset: 0,     format: "float32x2" },
    { shaderLocation: 1, offset: 2 * 4, format: "float32x3" },
    { shaderLocation: 2, offset: 5 * 4, format: "float32x2" },
  ],
}]
```

系统根据 `vertexIndex`、Buffer Slot 和这份布局取出数据，然后作为当前 Vertex Shader Invocation 的输入。Shader 不需要自己计算交错 Buffer 的字节地址。

### 3. Uniform：一次 Draw 共享的小参数

```wgsl
struct Uniforms {
  scale: f32,
  textureMix: f32,
  bufferInfluence: f32,
};

@group(0) @binding(0)
var<uniform> uniforms: Uniforms;
```

JavaScript 把参数写入 Uniform Buffer，再通过 BindGroup 接到 `@group(0) @binding(0)`。本次 Draw 的所有 Vertex/Fragment Invocation 都可以读到同一份参数。修改滑块时，示例重新写 Buffer 并提交新 Draw，而不是重新生成 WGSL。

### 4. Storage Buffer：更大的结构化数据

```wgsl
@group(0) @binding(1)
var<storage, read> vertexOffsets: array<vec2f>;
```

Storage Buffer 可以保存更大的数组，并允许 Shader 用索引访问。示例使用 `vertex_index` 取当前顶点的 Offset：

```wgsl
let offset = vertexOffsets[vertexIndex] * uniforms.bufferInfluence;
```

它与 Attribute 都能提供“每个顶点不同”的数据，但数据入口不同：Attribute 由 Vertex Fetch 固定功能按 Pipeline 布局自动取值；Storage Buffer 则是 Shader 自己用索引读取普通数组。

### 5. Texture 与 Sampler：专门的采样资源

```wgsl
@group(0) @binding(2) var colorTexture: texture_2d<f32>;
@group(0) @binding(3) var colorSampler: sampler;

let texel = textureSample(colorTexture, colorSampler, input.uv);
```

Texture 保存纹素，Texture View 描述访问哪部分纹理，Sampler 决定过滤和寻址规则。`textureSample` 不只是读取某个数组元素，它还会根据 UV、过滤模式和边界模式计算采样结果。

### 6. Inter-stage Variable：连接 Vertex 与 Fragment

```wgsl
struct VertexOutput {
  @builtin(position) position: vec4f,
  @location(0) color: vec3f,
  @location(1) uv: vec2f,
};
```

`position` 交给固定功能阶段决定三角形在屏幕上的覆盖范围；`color` 和 `uv` 则沿三角形插值后，成为 Fragment Shader 的输入。它们不是 JavaScript 再次写进去的，也不是 Fragment Shader直接读取原始 Vertex Buffer 得到的。

## 三、Vertex → 光栅化 → Fragment → Attachment

一次 Render Pipeline 可以按四段理解。

### 1. Vertex Shader 生成裁剪空间顶点

本章示例中的核心逻辑是：

```wgsl
@vertex
fn vertexMain(input: VertexInput) -> VertexOutput {
  var output: VertexOutput;

  let offset = vertexOffsets[input.vertexIndex] * uniforms.bufferInfluence;
  let transformed = input.position * uniforms.scale + offset;

  output.position = vec4f(transformed, POSITION_Z, 1.0);
  output.color = input.color;
  output.uv = input.uv;
  return output;
}
```

每次 Invocation 只处理当前顶点。最关键的输出是 `@builtin(position)`：它是裁剪空间齐次坐标 `(x, y, z, w)`，不是 Canvas 像素坐标。

### 2. 固定功能阶段组装并光栅化图元

Pipeline 的 `topology: "triangle-list"` 表示每 3 个顶点组成一个独立三角形。固定功能硬件随后负责：

- 用 Vertex Shader 输出组装三角形；
- 对图元进行裁剪和面剔除等处理；
- 做透视除法，将裁剪空间转换为 NDC；
- 通过 Viewport 映射到 Attachment；
- 判断三角形覆盖哪些采样点，生成片段。

这部分没有 WGSL 函数可供我们调用，所以称为固定功能阶段。WebGPU 允许通过 Pipeline 状态配置它，但不能像 Shader 一样随意改写算法。

### 3. 阶段变量在三角形内部被插值

假设三个顶点颜色分别为红、绿、蓝，Fragment Shader 并不会只收到这三个颜色。光栅化器根据当前片段在三角形中的位置计算重心权重，再插值得到该片段自己的颜色与 UV：

```text
fragmentColor = color0 × w0 + color1 × w1 + color2 × w2
fragmentUV    = uv0    × w0 + uv1    × w1 + uv2    × w2
```

默认浮点阶段变量通常执行透视正确插值。若某个值不应该插值，例如材质编号，可以使用 `@interpolate(flat)`，让整个图元使用一个离散值。

### 4. Fragment Shader 计算颜色并写入 Attachment

```wgsl
@fragment
fn fragmentMain(input: VertexOutput) -> @location(0) vec4f {
  let sampled = textureSample(colorTexture, colorSampler, input.uv);
  let vertexColor = vec4f(input.color, OUTPUT_ALPHA);
  return mix(vertexColor, sampled, uniforms.textureMix);
}
```

Fragment Shader 读到的是已经插值的 `color/uv`，再结合 Texture、Sampler 和 Uniform 计算当前片段的候选颜色。返回值中的 `@location(0)` 对应 Render Pass 的第 0 个 Color Attachment。

```js
colorAttachments: [{
  view: context.getCurrentTexture().createView(),
  loadOp: "clear",
  storeOp: "store",
}]
```

“候选颜色”不一定无条件覆盖像素。若 Pipeline 开启深度、模板、混合或多重采样，固定功能阶段还会依据相应规则决定是否写入以及怎样与目标颜色合成。示例没有开启混合，因此通过测试的结果直接进入 Canvas 当前纹理。

完整数据流可以压缩为：

```text
Attribute ─┐
Uniform ───┼─→ Vertex Shader × 顶点数
Storage ───┘           ↓
                 图元组装、裁剪、光栅化
                          ↓
                 Inter-stage 插值
                          ↓
Texture + Sampler ─→ Fragment Shader × 被覆盖片段数
                          ↓
              Depth / Stencil / Blend / MSAA
                          ↓
                  Canvas Color Attachment
```

## 四、GPU 的并行模型及其限制

CPU 类比代码用了两个 `for` 循环，但 GPU 的价值恰恰在于不按一个长循环串行处理。它会把大量 Vertex、Fragment 或 Compute Invocation 分配给许多执行单元并行运行。

因此写 Shader 时必须接受几个基本事实。

### 调用顺序不能依赖

不能假设 Vertex Shader 会按照 `vertex_index = 0, 1, 2` 的顺序完成，也不能假设屏幕左上角 Fragment 一定比右下角先运行。驱动可能分批、乱序或重叠调度 Invocation。

下面这种思路是不成立的：

```text
顶点 0 先计算一个普通变量
顶点 1 再读取顶点 0 的普通变量
```

每次 Invocation 的函数局部变量属于它自己，不能被另一次 Invocation 直接读取。

### 共享资源需要避免数据竞争

大量 Invocation 同时读取同一份 Uniform、只读 Storage Buffer 或 Texture 通常没有问题；多个 Invocation 同时写同一地址则可能产生数据竞争，结果不能用“源码先后顺序”推断。

常见的安全设计有：

- 让每个 Invocation 写不同索引；
- 资源只读，把结果写到独立输出；
- 确实需要共享计数时使用 WGSL 原子类型与原子操作；
- Compute Shader 在 Workgroup 内使用工作组内存与同步屏障，但同步范围必须明确。

Render Pipeline 对同一像素的可见性冲突，通常交由固定功能的深度测试、模板测试和 Blend State 处理，而不是在 Fragment Shader 中假设谁先执行。

### JavaScript 与 GPU 也不是同步串行关系

`queue.submit` 提交命令后，JavaScript 通常继续向下运行，GPU 异步消费命令。频繁把 GPU 结果读回 CPU 会迫使双方等待，破坏并行性。因此典型做法是：

1. 在 CPU 侧批量更新 Buffer；
2. 编码尽量完整的一帧命令；
3. 一次或少量几次提交；
4. 只有确实需要结果时才异步 Map/Readback。

本章示例并排实现 CPU 光栅化，就是为了展示职责边界，而不是建议实际项目用 JavaScript 像素循环代替 GPU。CPU 版清楚但串行；GPU 版只提交资源和 Draw，由硬件并行执行数万个 Fragment Invocation。

## 五、和 WebGL 对比

WebGL 与 WebGPU 的底层图形原理并没有换一套：二者都有 Vertex Shader、图元组装、光栅化、插值、Fragment Shader 和 Framebuffer/Attachment。变化最大的是 JavaScript 如何描述状态、资源和提交过程。

| 概念 | WebGL 2 | WebGPU |
| --- | --- | --- |
| Shader 语言与组织 | GLSL ES；分别编译 Vertex/Fragment Shader，再 Link 成 Program | WGSL；Shader Module 可含多个入口点，由 Render Pipeline 选择 |
| Vertex 数据解释 | `bindBuffer`、`vertexAttribPointer`、VAO 保存当前 Attribute 状态 | `GPUVertexState.buffers` 在 Pipeline 中显式声明 Buffer Layout |
| 普通参数 | `uniform*` 设置 Program Uniform；也可使用 UBO | 通常写 Uniform Buffer，再通过 BindGroup 绑定 |
| 大型结构化数据 | WebGL 2 主要依赖 UBO、Texture；没有通用 SSBO | Storage Buffer 是标准资源，可声明只读或读写 |
| Texture | Active Texture Unit + Texture Bind + Sampler Uniform，Sampler 状态也可单独对象化 | Texture View 与 Sampler 是显式 Binding 资源 |
| 阶段间数据 | Vertex `out` → Fragment `in`，由 Location 匹配并插值 | Vertex 返回值 → Fragment 参数，由 `@location` 匹配并插值 |
| 固定功能状态 | 通过 `enable`、`blendFunc`、`depthFunc` 等修改全局状态机 | 大部分状态固化在 Render Pipeline Descriptor 中 |
| 发出 Draw | 在当前全局状态上调用 `drawArrays/drawElements` | 在 Render Pass 中设置 Pipeline、Buffer、BindGroup 后编码 `draw/drawIndexed` |
| 命令提交 | API 调用进入较隐式的命令流，通常由浏览器决定刷新时机 | CommandEncoder → CommandBuffer → `queue.submit`，命令边界更明确 |
| 渲染目标 | 默认 Framebuffer 或当前绑定 FBO | Render Pass Descriptor 中显式提供 Color/Depth Attachment View |
| Compute | WebGL 2 不支持 Compute Shader | Compute Pipeline + `dispatchWorkgroups` |

同一个最小绘制流程的差异如下。

WebGL：

```js
gl.useProgram(program);
gl.bindVertexArray(vao);
gl.uniform1f(scaleLocation, scale);
gl.drawArrays(gl.TRIANGLES, 0, 3);
```

WebGPU：

```js
device.queue.writeBuffer(uniformBuffer, 0, uniformValues);

const encoder = device.createCommandEncoder();
const pass = encoder.beginRenderPass(renderPassDescriptor);
pass.setPipeline(pipeline);
pass.setVertexBuffer(0, vertexBuffer);
pass.setBindGroup(0, bindGroup);
pass.draw(3);
pass.end();

device.queue.submit([encoder.finish()]);
```

WebGL 的 `drawArrays` 同样不会在 JavaScript 中逐顶点调用 GLSL，GPU Pipeline 本质相同。WebGPU 主要把 WebGL 中分散在全局状态机、Texture Unit、Program Uniform 和 Framebuffer Binding 里的信息，重新组织为更明确的 Pipeline、BindGroup、Render Pass 和 Command Buffer。

所以这一章不要记成“WebGPU 有一堆新对象”，而要记成两层职责：

```text
JavaScript：创建资源 → 描述 Pipeline → 编码 Draw → 提交 Command Buffer
GPU：批量调用 Shader → 组装图元 → 光栅化 → 插值 → 测试/混合 → 写 Attachment
```

配套示例：[`how-it-works.html`](./how-it-works.html)

# Compatibility Mode（兼容性模式）

官方原文：[WebGPU 兼容性模式](https://webgpufundamentals.org/webgpu/lessons/zh_cn/webgpu-compatibility-mode.html)

Compatibility Mode 是 WebGPU 的一个受限 Feature Level。它通过减少部分能力、收紧资源使用规则，让 WebGPU 可以映射到更多旧 GPU 和旧图形后端。

它不是 WebGL 兼容层，也不是发生错误后自动切换到 WebGL。应用仍然使用 WGSL、Pipeline、BindGroup、CommandEncoder 和 `queue.submit`，只是主动承诺遵守一组更接近 WebGL 2 级硬件的限制。

原文给出的现实判断是：**几乎所有 WebGL 2 程序都可以转换为 Compatibility Mode WebGPU 程序。**

## 一、Compatibility、Core、Adapter 和 Device 的关系

默认请求得到的是 Core Adapter：

```js
const adapter = await navigator.gpu.requestAdapter();
const device = await adapter?.requestDevice();
```

主动请求 Compatibility Adapter：

```js
const adapter = await navigator.gpu.requestAdapter({
  featureLevel: "compatibility",
});
const device = await adapter?.requestDevice();
```

`featureLevel` 是 `requestAdapter` 的选项，不是 `requestDevice` 的普通 Feature。请求 Compatibility 的含义是：

```text
应用愿意遵守 Compatibility 限制
                ↓
浏览器可以返回能映射到较旧设备的 Adapter
                ↓
同一套代码也仍然是合法的 Core WebGPU 代码
```

Compatibility 是 Core WebGPU 的能力子集。因此一个符合 Compatibility 规则的应用可以在 Compatibility Device 上运行，也可以在 Core Device 上运行；反过来则不一定成立。

一个 Compatibility Adapter 可能同时支持 Core 能力。此时 Adapter 会暴露 `core-features-and-limits`：

```js
const adapter = await navigator.gpu.requestAdapter({
  featureLevel: "compatibility",
});

const canUpgradeToCore = adapter.features.has("core-features-and-limits");
```

如果应用想在较旧设备走 Compatibility 路径、在较新设备自动升级 Core，可以把这个 Feature 加入 Device 请求：

```js
const device = await adapter.requestDevice({
  requiredFeatures: [
    ...(canUpgradeToCore ? ["core-features-and-limits"] : []),
  ],
});
```

判断最终拿到的 Device 属于哪种级别，应检查 **Device**，不能只检查 Adapter：

```js
const isCore = device.features.has("core-features-and-limits");
const isCompatibilityMode = !isCore;
```

原因是 Adapter 即使“可以升级 Core”，应用也可能故意不请求升级，从而创建真正执行 Compatibility 约束的 Device。本章示例正是这样测试：Adapter 支持升级，但 `requestDevice()` 没有请求该 Feature，最终 Device 中没有 `core-features-and-limits`。

兼容模式在 Chrome 146 开始正式发布。若较旧浏览器无法返回 Adapter，需要先区分两种情况：浏览器尚未实现 Compatibility Mode，还是当前机器连 Compatibility Adapter 都无法提供。不能把 `requestAdapter()` 返回 `null` 简单解释成 WGSL 写错了。

## 二、最重要的限制：Vertex Stage 可能没有 Storage Buffer

原文认为最容易影响已有 WebGPU 程序的限制是：大约 45% 的目标旧设备不支持在 Vertex Shader 中使用 Storage Buffer。

Compatibility Mode 为此增加了更细的 Limit：

| Limit | Compatibility 默认值 | 含义 |
| --- | ---: | --- |
| `maxStorageBuffersInVertexStage` | 0 | Vertex Shader 默认不能读取 Storage Buffer |
| `maxStorageTexturesInVertexStage` | 0 | Vertex Shader 默认不能访问 Storage Texture |
| `maxStorageBuffersInFragmentStage` | 4 | Fragment Stage 默认最多 4 个 Storage Buffer |
| `maxStorageTexturesInFragmentStage` | 4 | Fragment Stage 默认最多 4 个 Storage Texture |

Adapter 可能提供高于默认值的能力，但兼容程序不能假设它一定更高。若算法必须使用这些资源，应先检查 `adapter.limits`，再通过 `requiredLimits` 请求真正需要的数值。

Core WebGPU 中常见的写法是把许多对象的顶点数据放进 Storage Buffer，由 `vertex_index` 或 `instance_index` 随机读取：

```wgsl
@group(0) @binding(0)
var<storage, read> positions: array<vec2f>;

@vertex
fn vertexMain(@builtin(vertex_index) index: u32) -> @builtin(position) vec4f {
  return vec4f(positions[index], 0.0, 1.0);
}
```

这种方案灵活，因为 Shader 可以用任意索引访问数组。但它不能作为 Compatibility 的通用基线。

最直接的兼容改造是把普通顶点字段改回 Vertex Buffer：

```wgsl
struct VertexInput {
  @location(0) position: vec2f,
  @location(1) uv: vec2f,
};

@vertex
fn vertexMain(input: VertexInput) -> VertexOutput {
  // position 和 uv 由固定功能 Vertex Fetch 提供。
}
```

```js
const pipeline = device.createRenderPipeline({
  vertex: {
    module,
    buffers: [{
      arrayStride: 4 * 4,
      attributes: [
        { shaderLocation: 0, offset: 0,     format: "float32x2" },
        { shaderLocation: 1, offset: 2 * 4, format: "float32x2" },
      ],
    }],
  },
  // ...
});
```

两条路径的差异是：

| Storage Buffer 顶点数据 | Vertex Buffer 顶点数据 |
| --- | --- |
| Shader 自己根据索引读取 | Vertex Fetch 根据 Pipeline Layout 自动取值 |
| 可以随机访问其他顶点或任意数组元素 | 当前 Invocation 主要接收当前顶点的 Attribute |
| 更适合不规则数据组织和通用计算 | 更适合位置、法线、颜色、UV 等标准顶点字段 |
| Core 设备通常支持 | Compatibility 基线普遍支持 |

如果算法确实需要随机读取其他顶点，例如某些 Wireframe 生成算法，就不能机械地把 Storage Buffer 改名为 Vertex Buffer，而要重新组织数据或提供 Core 增强路径。

## 三、纹理视图限制与兼容 Mipmap 的核心改造

Compatibility Mode 对 `TEXTURE_BINDING` 的限制可以归结为两条：

1. 一个 Texture 作为 Shader Binding 使用时，只能有一种 Binding View Dimension；
2. 创建 Binding View 时不能只选择 Array Layer 的一个子集。

Core WebGPU 中，一个包含 6 层的二维纹理可以被解释成不同视图：

```js
const texture = device.createTexture({
  size: [width, height, 6],
  format: "rgba8unorm",
  usage: GPUTextureUsage.TEXTURE_BINDING |
         GPUTextureUsage.RENDER_ATTACHMENT,
});

const asArray = texture.createView({ dimension: "2d-array" });
const asLayer = texture.createView({
  dimension: "2d",
  baseArrayLayer: 3,
  arrayLayerCount: 1,
});
const asCube = texture.createView({ dimension: "cube" });
```

Compatibility Mode 不允许同一个 Texture 在 BindGroup 中一会儿作为 `2d-array`、一会儿作为 `2d`、一会儿又作为 `cube`。必须在创建 Texture 时固定用途：

```js
const cubeTexture = device.createTexture({
  size: [width, height, 6],
  format: "rgba8unorm",
  usage: GPUTextureUsage.TEXTURE_BINDING |
         GPUTextureUsage.RENDER_ATTACHMENT,

  // 提前声明它作为 Shader Binding 时必须按 cube 使用。
  textureBindingViewDimension: "cube",
});
```

默认规则是：单层二维纹理默认为 `2d`，多层二维纹理默认为 `2d-array`。如果需要 `cube` 等非默认方式，就必须显式声明。

这个限制只针对 `TEXTURE_BINDING`。例如 Cube Texture 的某一层仍然可以建立 `2d` View，作为某次 Render Pass 的 `RENDER_ATTACHMENT`；不能做的是把这个单层 `2d` View 放进 BindGroup 当采样纹理使用。

### 为什么生成 Mipmap 会同时撞上两条限制

Core 模式常见的 GPU Mipmap 生成流程是：

```text
把上一层 Mip 的某个 Array Layer 建成单层 2D Binding View
                         ↓ 采样并缩小
把下一层 Mip 的同一个 Array Layer 建成 2D Render Attachment
```

对 `2d-array` 或 `cube` 来说，输入端既把 View Dimension 改成了 `2d`，又只选了一个 Array Layer，所以在 Compatibility Mode 中不合法。

兼容改造的原则是：

```text
BindGroup：始终绑定与创建时维度一致的完整纹理视图
Shader：根据图层编号选择真正要读取的 Array Layer / Cube Face
Render Attachment：仍然可以选择当前要写入的单层和 Mip Level
```

对于二维数组，Shader 使用 `texture_2d_array`：

```wgsl
struct VertexOutput {
  @builtin(position) position: vec4f,
  @location(0) uv: vec2f,
  @location(1) @interpolate(flat, either) layer: u32,
};

@group(0) @binding(0) var textureSampler: sampler;
@group(0) @binding(1) var textureArray: texture_2d_array<f32>;

@fragment
fn fragmentMain(input: VertexOutput) -> @location(0) vec4f {
  return textureSample(textureArray, textureSampler, input.uv, input.layer);
}
```

图层编号可以借用 `firstInstance → instance_index` 传入，不需要为了一个整数创建 Uniform Buffer：

```wgsl
@vertex
fn vertexMain(
  @builtin(vertex_index) vertexIndex: u32,
  @builtin(instance_index) layer: u32,
) -> VertexOutput {
  // 把 layer 继续传给 Fragment Shader。
}
```

```js
// vertexCount = 3，instanceCount = 1，firstVertex = 0，firstInstance = layer
pass.draw(3, 1, 0, layer);
```

整数图层值不能做线性插值。Core 中经常能写 `@interpolate(flat)`；Compatibility 要使用 `@interpolate(flat, either)`。`either` 表示实现可以取图元首顶点或末顶点的值。这里所有顶点都收到同一个 `instance_index`，所以取哪一个都相同。

原文的完整 Mipmap 生成器还做了两件事：

- 为 `2d`、`2d-array`、`cube` 准备不同 Fragment 入口点，因为 WGSL Texture 类型不同；
- Pipeline Cache 的 Key 从单纯的 Texture Format 扩展为 `format + textureBindingViewDimension`。

这样改出的 `generateMips` 同时符合 Compatibility 与 Core。真正通用的兼容方案不是在运行失败后打补丁，而是让资源创建、BindGroup、Shader 类型和 Pipeline Cache 从一开始就使用同一份 View Dimension 信息。

## 四、其他限制、默认 Limits 与测试方式

原文剩余限制数量很多，但可以按影响范围合并理解：

| 范围 | Compatibility Mode 约束 |
| --- | --- |
| Color Attachment | 同一 Pipeline 的所有 Color Target 必须使用相同 Blend 设置 |
| Copy | 压缩纹理不支持 `copyTextureToBuffer/copyTextureToTexture`；MSAA Texture 不支持 `copyTextureToTexture` |
| Texture View | 不支持 `cube-array`；同一次 Draw/Dispatch 中的 Binding View 不能使用不同 Aspect 或 Mip Level；不能重解释 SRGB/非 SRGB Format |
| Texture Format | 不支持 `bgra8unorm-srgb`；`rg32uint/rg32sint/rg32float` 不能作 Storage Texture；整数格式以及 `rgba16float/r32float` 不能 MSAA |
| Texture 层数 | `depthOrArrayLayers` 必须匹配 Binding View Dimension：`2d` 必须 1 层，`cube` 必须 6 层 |
| Fragment Built-in | 不支持 `@builtin(sample_mask)` 与 `@builtin(sample_index)` |
| Interpolation | 不支持 `linear` 和 `sample` 插值；Flat 必须使用 `@interpolate(flat, either)` |
| Depth Texture | `texture_depth*` 不能配合 `textureLoad`；不能使用普通非比较 Sampler，只能走 Compare Sampling 路径 |
| Derivative | 不支持 `dpdxFine/dpdyFine/fwidthFine`，仍可使用默认或 Coarse 版本 |
| Depth Bias | Pipeline 的 `depthBiasClamp` 必须为 0 |

纹理格式不能重解释的含义是：Core 中可能允许创建 `rgba8unorm` Texture，再通过 View 当作 `rgba8unorm-srgb` 使用；Compatibility 要求创建格式和查看格式保持一致。

深度纹理限制针对 WGSL 中声明成 `texture_depth_2d`、`texture_depth_2d_array`、`texture_depth_cube` 的 Binding。如果把深度格式 Texture 绑定到合法的 `texture_2d<f32>` 等普通 Texture 类型，仍可按普通非过滤纹理的规则使用。

Compatibility 对 Texture + Sampler 的组合数量也更严格。Core 可以绑定 16 个以上 Texture 与 16 个以上 Sampler，并使用大量交叉组合；Compatibility 每个 Shader Stage 通常最多使用：

```text
maxCombinationsPerStage = min(
  maxSampledTexturesPerShaderStage,
  maxSamplersPerShaderStage,
)
```

计算依据是 Pipeline Layout 中对当前 Stage 可见的 Texture Binding，以及 Shader 实际把每个 Texture 与多少 Sampler 组合使用。External Texture 因为内部可能展开为 Y/U/V Texture 和 LUT，消耗的组合数更多。

几个重要默认 Limit 对比：

| Limit | Compatibility 默认值 | Core 默认值 |
| --- | ---: | ---: |
| `maxColorAttachments` | 4 | 8 |
| `maxComputeInvocationsPerWorkgroup` | 128 | 256 |
| `maxComputeWorkgroupSizeX` | 128 | 256 |
| `maxComputeWorkgroupSizeY` | 128 | 256 |
| `maxInterStageShaderVariables` | 15 | 16 |
| `maxTextureDimension1D` | 4096 | 8192 |
| `maxTextureDimension2D` | 4096 | 8192 |
| `maxUniformBufferBindingSize` | 16384 | 65536 |
| `maxVertexAttributes` | 16 | 16 |

在 Compatibility Mode 中，`vertex_index` 和 `instance_index` 各自还会占用一个 Vertex Attribute 名额。表中只是默认保证值，具体 Adapter 可以更高，所以仍应按“检查实际 Limit → 只请求业务所需值”的方式创建设备。

测试应用是否真正遵守 Compatibility 限制时，不要申请 `core-features-and-limits`：

```js
const adapter = await navigator.gpu.requestAdapter({
  featureLevel: "compatibility",
});
const device = await adapter.requestDevice();

const constraintsAreEnforced =
  !device.features.has("core-features-and-limits");
```

如果 Device 没有该 Feature，才说明这些 Compatibility 验证规则正在被执行。原文还介绍了 `webgpu-dev-extension`：它能强制 `requestAdapter` 使用 Compatibility、屏蔽 Core Feature，并在 DevTools 中显示 Adapter/Device 信息，适合快速检查既有项目，但应用本身仍应具备正规的检测和回退逻辑。

## 五、和 WebGL 2 对比

Compatibility Mode 的能力目标接近大量 WebGL 2 设备，但它仍然是 WebGPU API。可以把它理解为“用 WebGPU 的显式架构表达一组 WebGL 2 级硬件普遍能完成的工作”。

| 概念 | WebGL 2 | WebGPU Compatibility Mode |
| --- | --- | --- |
| API 模型 | `WebGL2RenderingContext` 全局状态机 | Adapter、Device、Pipeline、BindGroup、Command Buffer |
| Shader | GLSL ES 3.00，Program Link | WGSL，Shader Module + Pipeline |
| 兼容目标 | WebGL 2 本身就是较广泛的图形能力基线 | 在 WebGPU 中主动选择的受限 Feature Level |
| 顶点数据 | Vertex Buffer/VAO/Attribute 是标准路径 | Vertex Buffer 是最可靠路径；Vertex Storage Buffer 默认可能不可用 |
| Storage Buffer | WebGL 2 没有通用 SSBO | API 有 Storage Buffer，但各 Stage 数量受到更低 Limit 约束 |
| Texture 类型 | 绑定到 `TEXTURE_2D`、`TEXTURE_2D_ARRAY`、`TEXTURE_CUBE_MAP` 等固定 Target | 创建时用 `textureBindingViewDimension` 固定 Shader Binding 视图类型 |
| 数组图层选择 | Shader 用三维坐标采样 Array Texture；FBO 可选择 Layer | Binding 使用完整 Array View，Shader 选择输入 Layer；Attachment 仍可选单层 |
| MRT | WebGL 2 至少保证较小数量的 Draw Buffer/Color Attachment | `maxColorAttachments` 默认 4，且同一 Pipeline 的 Blend 设置必须匹配 |
| Compute | 不支持 Compute Shader | 仍支持 Compute，但 Workgroup 默认规模更低，资源限制更多 |
| 提交 | `drawArrays/drawElements` 进入隐式命令流 | Render/Compute Pass 编码后通过 `queue.submit` 显式提交 |
| 能力检测 | `getParameter`、Extension | Adapter Features/Limits → `requiredFeatures/requiredLimits` → Device Features |

WebGL 2 程序之所以通常容易迁移到 Compatibility Mode，是因为它本来就不会依赖 Vertex Shader Storage Buffer、Cube Array、Compute Shader 或任意 Texture View 重解释等高级能力。它常用的 Vertex Buffer、Uniform Buffer、2D/Array/Cube Texture、Depth Test 和基本 MRT 都有兼容路径。

但“容易迁移”不等于 API 可以逐行替换。例如 WebGL 中：

```js
gl.bindVertexArray(vao);
gl.activeTexture(gl.TEXTURE0);
gl.bindTexture(gl.TEXTURE_2D_ARRAY, texture);
gl.drawArrays(gl.TRIANGLES, 0, 3);
```

在 WebGPU Compatibility 中仍要显式组织：

```js
const adapter = await navigator.gpu.requestAdapter({
  featureLevel: "compatibility",
});
const device = await adapter.requestDevice();

const pass = encoder.beginRenderPass(renderPassDescriptor);
pass.setPipeline(pipeline);
pass.setVertexBuffer(0, vertexBuffer);
pass.setBindGroup(0, bindGroup);
pass.draw(3, 1, 0, selectedLayer);
pass.end();

device.queue.submit([encoder.finish()]);
```

这一章最终要形成的设计判断是：

```text
想覆盖更多旧设备：
  以 Compatibility Limits 设计基础渲染路径
  + 用 Vertex Buffer 等普遍能力组织数据
  + 创建 Texture 时提前固定 Binding View Dimension
  + 在 Shader 内选择 Array Layer

想利用新设备：
  检查 core-features-and-limits
  + 创建 Core Device
  + 启用 Storage Buffer、更多 Attachment、更高 Limit 等增强路径
```

配套示例：[`compatibility-mode.html`](./compatibility-mode.html)

完整顶点变换可以先记成一条式子：

```text
clipPosition = Projection × View × World × localPosition
```

对应职责是：

```text
World       模型从 Local Space 放进 World Space
View        把世界反向变换到 Camera Space
Projection  把 Camera Space 的可见体积映射到 WebGPU Clip Space
```

## 一、从 JavaScript 矩阵到 WGSL 顶点位置

原文最初让 Shader 直接接收 `resolution`、`translation`、`rotation`、`scale`，并在 Vertex Shader 中逐步处理：

```wgsl
let scaled = vert.position * uni.scale;

let rotated = vec2f(
  scaled.x * uni.rotation.x - scaled.y * uni.rotation.y,
  scaled.x * uni.rotation.y + scaled.y * uni.rotation.x,
);

let position = rotated + uni.translation;
```

随后还要把像素空间转换到裁剪空间：

```wgsl
let zeroToOne = position / uni.resolution;
let zeroToTwo = zeroToOne * 2.0;
let flippedClipSpace = zeroToTwo - 1.0;
let clipSpace = flippedClipSpace * vec2f(1, -1);
```

最后一行翻转 Y，是因为教程的二维顶点按 Canvas 像素习惯构造：原点在左上，正 Y 向下；WebGPU Clip Space 的正 Y 向上。

这种写法能解释每个数学步骤，但工程上有两个问题：

- 每增加或调整一种变换，都可能修改 WGSL；
- 变换顺序被写死在 Shader 中，换顺序就要改 Shader。

矩阵把这些变化收回 JavaScript。最终 WGSL 可以稳定成：

```wgsl
struct Uniforms {
  worldViewProjection: mat4x4f,
};

@group(0) @binding(0)
var<uniform> uniforms: Uniforms;

struct VertexInput {
  @location(0) position: vec3f,
  @location(1) color: vec4f,
};

struct VertexOutput {
  @builtin(position) position: vec4f,
  @location(0) color: vec4f,
};

@vertex
fn vertexMain(input: VertexInput) -> VertexOutput {
  var output: VertexOutput;
  output.position =
    uniforms.worldViewProjection * vec4f(input.position, 1.0);
  output.color = input.color;
  return output;
}
```

这时 Vertex Shader 不需要知道应用采用哪种相机、哪种投影，也不需要知道 World Matrix 是由 TRS、骨骼还是场景图生成。它只遵守一份稳定接口：读取一个 `mat4x4f`，把 Local Position 变成 Clip Position。

一个 `mat4x4f` 包含 16 个 `f32`，正好占 64 字节：

```js
const uniformBuffer = device.createBuffer({
  size: 16 * 4,
  usage: GPUBufferUsage.UNIFORM | GPUBufferUsage.COPY_DST,
});

const bindGroup = device.createBindGroup({
  layout: pipeline.getBindGroupLayout(0),
  entries: [
    { binding: 0, resource: { buffer: uniformBuffer } },
  ],
});

device.queue.writeBuffer(uniformBuffer, 0, worldViewProjection);
```

这里要分清四个对象：

| 对象 | 职责 |
| --- | --- |
| JavaScript `Float32Array(16)` | 保存 CPU 计算出的矩阵数值 |
| `GPUBuffer` | GPU 可访问的 64 字节 Uniform 内存 |
| `GPUBindGroup` | 把 Buffer 连接到 `@group(0) @binding(0)` |
| WGSL `mat4x4f` | Shader 读取这些字节时采用的类型 |

`queue.writeBuffer` 是数据上传，不是 Shader 调用，也不是 Draw。只有后面编码 `setBindGroup` 和 `draw/drawIndexed`，该 Buffer 才成为本次绘制的输入。

本章示例绘制三个对象。它们共享 Pipeline、Vertex Buffer 和 Index Buffer，但各自拥有 Uniform Buffer 与 BindGroup：

```js
for (const object of objects) {
  device.queue.writeBuffer(
    object.uniformBuffer,
    0,
    object.worldViewProjection,
  );
}

const pass = encoder.beginRenderPass(renderPassDescriptor);
pass.setPipeline(pipeline);
pass.setVertexBuffer(0, vertexBuffer);
pass.setIndexBuffer(indexBuffer, "uint16");

for (const object of objects) {
  pass.setBindGroup(0, object.bindGroup);
  pass.drawIndexed(36);
}
```

不能在提交前对同一个 64 字节 Buffer 连续写三个矩阵，然后期望三个 Draw 分别看到三个历史值。Queue 执行 Draw 时，那个内存通常只剩最后一次写入的内容。通用方案有独立 Buffer、动态 Uniform Offset、一个大 Uniform/Storage Array，或者把每对象数据组织成实例数据。本例采用最容易观察的“每对象一个 Uniform Buffer + BindGroup”。

## 二、TRS 与 Matrix Math：WebGPU 真正关心的是最终字节

平移、旋转和缩放的数学结论可以压缩为：

- Translation 改变齐次矩阵最后一列；
- Rotation 使用 `sin/cos` 构造正交基；
- Scale 改变坐标轴长度，负 Scale 还会翻转几何朝向；
- 所有变换围绕当前原点发生；需要其他 Pivot 时，先把 Pivot 移到原点，变换后再移回去。

这些矩阵的乘法不可交换：

```text
T × R × S ≠ S × R × T
```

本例采用列向量与 `matrix * vector`，World Matrix 写成：

```js
let world = translation(tx, ty, tz);
world = multiply(world, zRotation(rz));
world = multiply(world, yRotation(ry));
world = multiply(world, xRotation(rx));
world = multiply(world, scaling(sx, sy, sz));
```

对应：

```text
world = T × Rz × Ry × Rx × S
```

矩阵作用到列向量时从右向左执行，所以顶点实际经历：

```text
Local Position
  → Scale
  → Rotate X
  → Rotate Y
  → Rotate Z
  → Translate
  → World Position
```

如果把 Translation 放到 Scale 右侧，Translation 本身也会被 Scale；如果把 Translation 放到 Rotation 右侧，平移方向也会被旋转。这就是原文用两个顺序不同的 F 得到完全不同运动轨迹的原因。

**WebGPU 不规定应用必须怎样组织 World Matrix。** Pipeline 和 Shader 只看最后上传的 16 个浮点数。变换组合、层级关系、Pivot、动画系统属于引擎 CPU 侧设计。

WGSL 矩阵采用列主序概念。`mat4x4f` 可以理解为 4 个连续的 `vec4f` 列：

```text
column 0: float[0..3]
column 1: float[4..7]
column 2: float[8..11]
column 3: float[12..15]
```

所以常见列主序数组中，Translation 位于索引 12、13、14：

```js
matrix[12] = tx;
matrix[13] = ty;
matrix[14] = tz;
```

“数学书把 Translation 画在最后一列，但数组代码看起来像最后一行”的困惑，来自一维数组展示方式。不要靠肉眼猜，统一约定：

```text
数组索引 = column × 4 + row
WGSL 表达式 = matrix × columnVector
```

原文先用二维 `mat3x3f` 讲矩阵。这里还有一个 WebGPU 内存陷阱：Uniform 中的 `mat3x3f` 不是紧凑的 9 个 `f32`。它由三个按 16 字节对齐的 `vec3f` 列组成，通常占 48 字节：

```text
column 0: x y z padding
column 1: x y z padding
column 2: x y z padding
```

直接把 9 个连续浮点数写入 `mat3x3f` Uniform 会错位。三维阶段直接使用 `mat4x4f` 反而简单：4 个 `vec4f` 天然是连续 64 字节，无需额外列 Padding。

原文还给出“变换点”和“变换空间”两种理解：

- 从右向左读：顶点依次被 S、R、T、V、P 改变；
- 从左向右读：每个矩阵都在重新定义后续顶点所处的坐标空间。

两种理解得到同一个结果。实现时更重要的是不要混用行向量库、列向量库和不同乘法顺序。只要 JavaScript 矩阵库与 WGSL 约定一致，WebGPU 不会替你转置矩阵。

## 三、进入 3D Pipeline：Vertex Format、绕序、剔除和 Depth Texture

从 2D 到 3D，WGSL 的主要变化只是把位置扩展为 `vec3f`，矩阵扩展为 `mat4x4f`。真正新增的 WebGPU 工作集中在几何布局、面朝向和深度资源。

本章示例将 Position 与 Color 交错存放：

```text
一个顶点共 16 字节
┌───────────────────────────┬───────────────────┐
│ position: 3 × float32     │ color: 4 × uint8  │
│ offset 0，12 bytes        │ offset 12，4 bytes│
└───────────────────────────┴───────────────────┘
```

Pipeline 负责把二进制解释成 WGSL 输入：

```js
buffers: [{
  arrayStride: 16,
  attributes: [
    { shaderLocation: 0, offset: 0,  format: "float32x3" },
    { shaderLocation: 1, offset: 12, format: "unorm8x4" },
  ],
}]
```

`unorm8x4` 的意义不是 WGSL 收到 `vec4u`，而是 Vertex Fetch 把四个 0～255 无符号字节归一化为四个 0～1 浮点数，因此 WGSL 仍声明：

```wgsl
@location(1) color: vec4f
```

原文的 3D F 最初使用索引共享顶点，但不同面需要不同颜色。同一个共享顶点只能携带一组 Attribute，因此一个几何角点若属于三个不同颜色的面，就必须复制成三个逻辑顶点，或者改用 `@interpolate(flat)` 加合适的数据组织。示例立方体采用每个面四个独立顶点，再用 Index Buffer 在面内复用。

**Front/Back Facing 在 Vertex Shader 变换之后判断。** Pipeline 中：

```js
primitive: {
  topology: "triangle-list",
  frontFace: "ccw",
  cullMode: "back",
}
```

表示顶点进入 Clip Space 后，逆时针三角形视为正面，背面被丢弃。负 Scale、Y 翻转或模型矩阵都可能改变绕序。例如原文为了沿用 2D 的正 Y 向下坐标，在 Projection 中翻转 Y，这会把所有三角形的朝向一起反转，所以必须相应调整 Vertex Order 或 Culling 设置。

Back-face Culling 不能替代深度测试。剔除只能去掉背向相机的面，无法解决两个正面三角形谁遮住谁。真正的遮挡需要 Depth Texture：

```js
const pipeline = device.createRenderPipeline({
  // ...
  depthStencil: {
    format: "depth24plus",
    depthWriteEnabled: true,
    depthCompare: "less",
  },
});
```

Render Pass 还必须提供匹配的 Depth Attachment：

```js
const depthTexture = device.createTexture({
  size: [canvas.width, canvas.height],
  format: "depth24plus",
  usage: GPUTextureUsage.RENDER_ATTACHMENT,
});

const pass = encoder.beginRenderPass({
  colorAttachments: [{
    view: context.getCurrentTexture().createView(),
    loadOp: "clear",
    storeOp: "store",
  }],
  depthStencilAttachment: {
    view: depthTexture.createView(),
    depthClearValue: 1,
    depthLoadOp: "clear",
    depthStoreOp: "store",
  },
});
```

`depthCompare: "less"` 表示新片段深度更小时才通过；`depthWriteEnabled: true` 表示通过后将新深度写回。因为 WebGPU NDC 深度越接近 0 越靠 Near Plane，清屏值应设为最远的 1。

Depth Texture 的宽高、Sample Count 必须与对应 Color Attachment 匹配。Canvas 像素尺寸改变时，`context.getCurrentTexture()` 会获得新尺寸，所以旧 Depth Texture 也必须销毁并重建。CSS 显示尺寸与 Canvas Drawing Buffer 尺寸是两个概念：

```text
canvas.clientWidth / clientHeight  CSS 显示尺寸
canvas.width / height              GPU Attachment 像素尺寸
```

常规高分屏处理会按 `clientSize × devicePixelRatio` 更新 `canvas.width/height`。Projection 的 Aspect 应反映实际显示比例；Depth Texture 则必须严格使用最终 Attachment 像素尺寸。

## 四、Orthographic、Perspective 与 Camera 在 WebGPU 中的边界

正交投影和透视投影最终都只是一个 `mat4x4f`。切换投影时不需要重建 Shader、BindGroup Layout 或 Pipeline，只需在 JavaScript 生成不同 Projection Matrix，再覆盖 Uniform Buffer。

正交投影直接把长方体范围映射到 Clip Space：

```js
const projection = orthographic(
  left,
  right,
  bottom,
  top,
  near,
  far,
);
```

它保留平行关系，物体不会因为更远而变小，适合 CAD、编辑器视图、UI、2.5D 和阴影贴图等场景。

透视投影把 Frustum 映射到 Clip Space：

```js
const projection = perspective(
  fieldOfViewRadians,
  canvas.width / canvas.height,
  zNear,
  zFar,
);
```

它通过齐次坐标 `w` 实现透视除法。Vertex Shader 只输出 Clip Position：

```wgsl
output.position = projection * view * world * localPosition;
```

固定功能阶段随后自动执行：

```text
ndc = clip.xyz / clip.w
```

不要在 WGSL 中再次手动除以 W。原文先用 `x/z` 的直觉解释“远处更小”，再把它整理进 Perspective Matrix；最终应用代码仍然只输出齐次 Clip Position。

WebGPU 的可见 Clip/NDC 范围为：

```text
-w ≤ clip.x ≤ w
-w ≤ clip.y ≤ w
 0 ≤ clip.z ≤ w

NDC:
-1 ≤ x/w ≤ 1
-1 ≤ y/w ≤ 1
 0 ≤ z/w ≤ 1
```

尤其注意 Z 是 `0..1`。Near Plane 映射到 0，Far Plane 映射到 1；超出范围的图元会被裁剪。这也与 `depthClearValue: 1`、`depthCompare: "less"` 对应。

教程中的 Perspective Matrix 假设：

- 相机位于 View Space 原点；
- 相机朝 `-Z` 方向观察；
- 正 Y 向上；
- 可见对象位于 `-zNear` 到 `-zFar` 之间。

所以模型不能留在相机原点，也不能放在正 Z 后方。原文把 150 单位高的 F 移到较大的负 Z，是因为 Near Plane 处的 Frustum 截面很小，模型需要离开相机一定距离才能完整落入视锥。

真实项目一般不靠移动整个模型来模拟相机，而是计算 View Matrix。

Camera Matrix 表示相机在世界里的位置和朝向：

```text
Camera Matrix: Camera Local → World
View Matrix:   World → Camera Local

View = inverse(Camera Matrix)
```

对于 Look At 相机：

```js
const zAxis = normalize(eye - target); // 相机局部后方，Camera 看向 -Z
const xAxis = normalize(cross(up, zAxis));
const yAxis = cross(zAxis, xAxis);
```

把 `xAxis/yAxis/zAxis/eye` 组成 Camera Matrix，再求逆得到 View Matrix。对于三个轴正交且单位化的刚体 Camera Matrix，可以用“旋转部分转置 + 反向平移”快速求逆；通用带 Scale/Shear 的矩阵则要使用完整 4×4 Inverse。

最终组合：

```js
const cameraMatrix = cameraAim(eye, target, up);
const view = inverse(cameraMatrix);
const viewProjection = multiply(projection, view);
const worldViewProjection = multiply(viewProjection, world);
```

相机本身并不是 GPU 对象。WebGPU 没有 `GPUCamera`；所谓 Camera 最终只是一组 JavaScript 参数和一个写进 Uniform Buffer 的 View/Projection 结果。

`lookAt` 通常直接返回 View Matrix；`aim` 通常返回让对象某个轴朝向目标的 World Matrix。二者使用相同的正交基构造，只是轴的方向与是否求逆不同。这套逻辑也能用于炮塔瞄准、角色头部跟踪和路径朝向，并不局限于相机。

## 五、WebGL 对照与 WebGPU 引擎组织方式

TRS、Projection 和 Camera 的数学在 WebGL 与 WebGPU 中基本相同。真正需要迁移的是 Clip Z 约定、资源上传方式和固定功能状态的位置。

| 概念 | WebGL 2 | WebGPU |
| --- | --- | --- |
| Shader 矩阵类型 | GLSL `mat4` | WGSL `mat4x4f` |
| 顶点变换 | `gl_Position = u_matrix * vec4(a_position, 1.0)` | 返回带 `@builtin(position)` 的 `uniforms.matrix * vec4f(position, 1)` |
| 矩阵上传 | `uniformMatrix4fv(location, false, matrix)` | `queue.writeBuffer(uniformBuffer, 0, matrix)` + BindGroup |
| Uniform 归属 | Program 的 Uniform Location 或 UBO Binding Point | Buffer 是独立资源，BindGroup 把它接到 Pipeline Layout |
| 顶点布局 | `vertexAttribPointer`，通常保存在 VAO | `GPUVertexBufferLayout` 固化在 Pipeline |
| 归一化颜色 | `vertexAttribPointer(..., UNSIGNED_BYTE, true, ...)` | Attribute Format 直接写 `unorm8x4` |
| Culling | `enable(CULL_FACE)`、`frontFace`、`cullFace` 修改全局状态 | `primitive.frontFace/cullMode` 属于 Render Pipeline |
| Depth | 开启全局 Depth Test，绑定默认深度缓冲或 FBO Renderbuffer/Texture | Pipeline 声明 Depth Format/Test；Render Pass 显式提供 Depth Texture View |
| 绘制 | 在当前 Program/VAO/Framebuffer 状态上 `drawElements` | Render Pass 中设置 Pipeline/Buffer/BindGroup 后 `drawIndexed` |
| Clip/NDC Z | `-1..1` | `0..1` |

最容易踩坑的是 Projection Matrix。把面向 OpenGL/WebGL 的透视矩阵原样复制到 WebGPU，X/Y 可能看起来正常，但 Z 会按错误范围映射，导致 Near/Far 裁剪和 Depth Test 异常。

WebGL 的标准 NDC：

```text
x: -1..1
y: -1..1
z: -1..1
```

WebGPU：

```text
x: -1..1
y: -1..1
z:  0..1
```

如果使用现成数学库，必须确认它能生成 WebGPU/D3D/Metal/Vulkan 风格的 Zero-to-One Depth Projection，而不是只看函数名是不是 `perspective`。

WebGL 上传单个矩阵通常是：

```js
gl.useProgram(program);
gl.uniformMatrix4fv(matrixLocation, false, worldViewProjection);
gl.bindVertexArray(vao);
gl.drawElements(gl.TRIANGLES, 36, gl.UNSIGNED_SHORT, 0);
```

WebGPU 则把“数据”“资源接口”“Pipeline 状态”和“Draw 命令”拆开：

```js
device.queue.writeBuffer(uniformBuffer, 0, worldViewProjection);

const encoder = device.createCommandEncoder();
const pass = encoder.beginRenderPass(renderPassDescriptor);
pass.setPipeline(pipeline);
pass.setVertexBuffer(0, vertexBuffer);
pass.setIndexBuffer(indexBuffer, "uint16");
pass.setBindGroup(0, bindGroup);
pass.drawIndexed(36);
pass.end();

device.queue.submit([encoder.finish()]);
```

对于引擎，可以把本章内容分成三层：

```text
Transform / Scene 层（CPU）
  Local TRS、Parent-Child、World Matrix、Camera Transform

Render Data 层（CPU → GPU）
  View/Projection、WVP、Uniform Buffer、Dynamic Offset、BindGroup

Render Pipeline 层（GPU）
  Vertex Layout、WGSL、Culling、Depth State、Render Pass、Draw
```

每帧的典型顺序是：

```text
1. 更新 Local TRS
2. 沿场景层级计算 World Matrix
3. 从 Camera Transform 计算 View Matrix
4. 按 Canvas Aspect 计算 Projection Matrix
5. 为可见对象计算 WVP 或拆分后的矩阵数据
6. 批量上传 Uniform / Storage / Instance Buffer
7. 按 Pipeline 和材质排序，编码 Render Pass
8. 设置对象资源并 Draw
9. submit Command Buffer
```

在小示例里上传完整 WVP 最简单；真正引擎常拆成：

- Frame/Camera BindGroup：View、Projection、Camera Position；
- Material BindGroup：纹理、Sampler、材质参数；
- Object BindGroup 或 Dynamic Offset：World Matrix、Object ID；
- Vertex/Instance Buffer：几何和大量实例变换。

这样 Camera 数据一帧上传一次，Material 数据按材质复用，只有 World Matrix 随对象变化。数学没有改变，改变的是数据更新频率和 BindGroup 组织。

这一合并章最后只需要牢牢记住：

> **WebGPU 没有内置 Transform 或 Camera。应用在 JavaScript 中生成矩阵，把它们按 WGSL 内存布局写进 Buffer；Pipeline 决定顶点布局、剔除和深度规则，Render Pass 提供实际 Color/Depth Attachment，Draw 才让 GPU 使用这些数据。**

配套示例：[`transforms-camera.html`](./transforms-camera.html)

# Matrix Stacks（矩阵栈）

原文章节：[WebGPU Matrix Stacks](https://webgpufundamentals.org/webgpu/lessons/webgpu-matrix-stacks.html)

这一章的重点不是新的矩阵公式，而是怎样组织已经学过的矩阵：绘制一个层级对象时，先保存父对象的坐标系，在这个基础上变换并绘制子对象，完成后再恢复父坐标系。它解决的是“子对象如何自然继承父对象变换，同时又不污染兄弟对象”的问题。

## 一、矩阵栈保存的是父坐标系

Matrix Stack 本质上是 JavaScript 中的一个矩阵数组，再加一份“当前工作矩阵”。它不是 WebGPU API，也不是 GPU 资源；所有压栈、出栈和矩阵乘法都发生在 CPU 上。

```text
当前矩阵 = 父节点的 World Matrix
    │
  save()       保存父矩阵，并复制出一份工作矩阵
    │
  TRS          在父坐标系中追加子节点的 Local Transform
    │
  draw         当前矩阵就是子节点的 Model/World Matrix
    │
  restore()    丢弃子节点变换，回到原来的父坐标系
```

本章示例里的核心实现是：

```js
class MatrixStack {
  #matrix = identity();
  #stack = [];

  save() {
    // 栈中保留父矩阵对象。
    this.#stack.push(this.#matrix);

    // 子层级必须修改副本，不能修改刚保存的父矩阵。
    this.#matrix = copy(this.#matrix);
    return this;
  }

  restore() {
    // 丢弃当前子矩阵，恢复最近保存的父矩阵。
    this.#matrix = this.#stack.pop();
    return this;
  }

  translate([x, y, z]) {
    this.#matrix = multiply(this.#matrix, translation(x, y, z));
    return this;
  }
}
```

`save()` 中的 `copy` 是关键。假设矩阵运算会原地修改 `Float32Array`，如果只把同一个数组引用压入栈中，子节点执行 Translate、Rotate 或 Scale 时，栈里的父矩阵也会一起改变，`restore()` 恢复的仍然是已经被污染的矩阵。

这里使用 `save/restore`，是为了与 Canvas 2D 的 `ctx.save()`、`ctx.restore()` 保持相同直觉；传统栈术语也可以叫 `push/pop`。正确性约束不变：

```text
每个 save 必须对应一次 restore
一帧结束时 stack depth 必须回到 0
```

如果漏掉 `restore()`，后续兄弟节点就会误继承前一个子节点的变换；如果多调用一次，则会发生栈下溢。示例因此记录 `saveCount`、`restoreCount` 和 `depth`，并在每帧结束时主动检查，而不是等画面“看起来不对”才排查。

矩阵相乘的顺序仍然决定变换语义。示例约定：

```js
current = current * localTransform;
```

因此新变换发生在当前父坐标系中。Matrix Stack 只负责保存和恢复上下文，并不会消除矩阵乘法顺序的问题。

## 二、文件柜：层级函数只关心自己的局部空间

官方原文先把所有物体统一成 Unit Cube，再逐步组合出抽屉、把手、文件柜和一排文件柜：

```text
Cabinets
└─ Cabinet
   ├─ Cabinet Body
   └─ Drawer × N
      ├─ Drawer Body
      └─ Handle
```

每层函数进入自己的局部空间前 `save()`，绘制完成后 `restore()`：

```js
function drawCabinets(ctx, cabinetCount, drawerCount) {
  for (let cabinetIndex = 0; cabinetIndex < cabinetCount; ++cabinetIndex) {
    stack.save()
      .translate([cabinetIndex * cabinetSpacing - centerOffset, 0, 0]);

    drawCabinet(ctx, cabinetIndex, drawerCount);
    stack.restore();
  }
}

function drawCabinet(ctx, cabinetIndex, drawerCount) {
  drawPart(ctx, cabinetSize, cabinetColor, "cabinet body");

  for (let drawerIndex = 0; drawerIndex < drawerCount; ++drawerIndex) {
    stack.save()
      .translate([0, 0.35 + drawerIndex * drawerSpacing, 0.14]);

    drawDrawer(ctx, drawerIndex);
    stack.restore();
  }
}
```

`drawDrawer` 不需要知道它属于第几个文件柜，也不需要接收文件柜的世界位置。调用它时，栈顶已经是对应抽屉插槽的父坐标系；它只负责在局部原点绘制抽屉，并把把手放到抽屉前方。这就是原文强调的可复用性：从单个抽屉扩展到一个文件柜、再扩展到多个文件柜时，`drawDrawer` 完全不必修改。

同一个 Unit Cube 能组成所有零件，是因为几何数据与对象变换分离：

```text
共享 Unit Cube Vertex/Index Buffer
  + 当前 Model Matrix：决定位置、朝向、大小
  + 当前 Color Uniform：区分柜体、抽屉和把手
```

默认示例有 3 个文件柜，每个文件柜有 4 个抽屉：

```text
每柜 Draw 数 = 1 个柜体 + 4 ×（抽屉体 + 把手）= 9
总 Draw 数   = 3 × 9 = 27
```

这里的层级关系只决定“怎样算出每个对象的 Model Matrix”，不会让 GPU 自动合并 Draw。27 个零件仍然是 27 次 `drawIndexed(36)`。Matrix Stack 提升的是变换组织与部件复用，不等于 Instancing、Batching 或 Draw Call 优化。

## 三、递归树：JavaScript 调用栈与矩阵栈一一对应

文件柜的层级深度固定，树则展示同一个模式怎样自然进入递归。每个 Branch 都相对父 Branch 的末端生长：

```js
function drawTreeLevel(ctx, offset, depth, settings) {
  stack.save();

  if (offset !== 0) {
    stack
      .translate([0, branchLength, 0]) // 到父枝末端
      .rotateZ(offset * settings.branchAngle)
      .rotateY(offset * settings.branchTwist)
      .scale([settings.branchScale, settings.branchScale, settings.branchScale]);
  }

  drawBranch(ctx, depth);

  if (depth > 0) {
    drawTreeLevel(ctx, -1, depth - 1, settings);
    drawTreeLevel(ctx, +1, depth - 1, settings);
  }

  stack.restore();
}
```

执行过程是：父 Branch 的矩阵仍在栈中；当前调用复制它，移动到父枝末端，再追加自己的旋转与缩放。左子树返回并恢复父矩阵之后，右子树会从完全相同的父坐标系开始，因此不会继承左枝的变换。

```text
父枝 World Matrix
├─ save → 左枝 Local Transform → 左子树 → restore
└─ save → 右枝 Local Transform → 右子树 → restore
```

递归函数的进入/返回，恰好对应矩阵栈的 `save/restore`。这也是 Matrix Stack 特别适合程序化树木、机械臂、骨架调试图、分形和递归几何的原因。

深度为 `d`、每个节点分出两个子枝时：

```text
Branch 数 = 1 + 2 + 4 + ... + 2^d = 2^(d + 1) - 1
末端数量  = 2^d
```

本地示例默认深度 5，所以有 63 个 Branch 和 32 片末端叶子，总计 95 次 Draw；深度调到 6 后是 127 个 Branch、64 片叶子，总计 191 次 Draw。递归深度只增加 1，节点数量却接近翻倍，所以 Matrix Stack 很轻量并不代表生成的对象数量也很少。

官方原文还演示了 Ornament 不应继承 Branch 的缩放与朝向。若直接使用当前栈顶矩阵，装饰物会随树枝一起倾斜、缩小；原文因此提取当前位置，再从一个纯 Translation Matrix 开始。本地示例对末端叶子使用同样技巧：

```js
const branchTip = multiply(stack.matrix, translation(0, branchLength, 0));
const tipPosition = getTranslation(branchTip);

const leafMatrix = multiply(
  translation(...tipPosition),
  scaling(0.18, 0.18, 0.18),
);

drawObject(leafMatrix, leafColor, "detached leaf");
```

这不是“取消父级”的特殊 WebGPU 功能，而是明确选择只继承父变换中的世界位置，不继承它的 Rotation 与 Scale。现代引擎里也常见类似需求，例如世界空间血条、固定大小的控制点和始终竖直的标签。

## 四、Matrix Stack 怎样接入一次 WebGPU Draw

GPU 不认识 Cabinet、Drawer、Branch 或父子关系。遍历层级之后，Matrix Stack 最终只向渲染代码交付一张 Model Matrix。示例把它与相机矩阵组合：

```text
Matrix Stack 当前矩阵 = Model / World
ViewProjection × Model = WorldViewProjection
WorldViewProjection 写入本对象 Uniform Buffer
BindGroup 绑定该 Buffer
drawIndexed(36)
```

WGSL 只接收最终矩阵和颜色：

```wgsl
struct Uniforms {
  matrix: mat4x4f, // 16 × f32 = 64 bytes
  color: vec4f,    //  4 × f32 = 16 bytes
};                 // 总计 80 bytes

@group(0) @binding(0) var<uniform> uniforms: Uniforms;

@vertex fn vs(input: VertexInput) -> VertexOutput {
  var output: VertexOutput;
  output.position = uniforms.matrix * vec4f(input.position, 1.0);
  output.color = input.color * uniforms.color;
  return output;
}
```

每个 Draw Slot 包含一个 80-byte Uniform Buffer、一个 BindGroup 和对应的 `Float32Array(20)` CPU 镜像。`drawObject` 按需创建 Slot：

```js
if (objectIndex === objectInfos.length) {
  objectInfos.push(createObjectInfo(objectInfos.length));
}

const objectInfo = objectInfos[objectIndex++];
const worldViewProjection = multiply(viewProjection, modelMatrix);

objectInfo.matrixValue.set(worldViewProjection);
objectInfo.colorValue.set(color);
device.queue.writeBuffer(objectInfo.uniformBuffer, 0, objectInfo.uniformValues);

pass.setBindGroup(0, objectInfo.bindGroup);
pass.drawIndexed(36);
```

每帧开始把 `objectIndex` 归零，所以旧 Slot 会按顺序复用；只有场景需要更多 Draw 时，资源池才增长。示例从 27 Draw 的文件柜切到 191 Draw 的树时，Pool 增长到 191；切回文件柜时只使用前 27 个，但 Pool 仍保留 191 个，避免反复创建和销毁 GPU Buffer/BindGroup。这一组织方式紧跟原文把固定数量 `objectInfos` 改成按需创建的做法。

它适合讲清数据流，但不是大量对象的最高效方案：每对象一次 `queue.writeBuffer`、一次 BindGroup 切换和一次 Draw，在复杂场景中会有明显 CPU 与命令编码开销。真实引擎通常会进一步使用：

- 一个较大的 Uniform/Storage Buffer 配合 Dynamic Offset 或对象索引；
- Instancing，把许多同几何对象合成一次 Draw；
- 场景遍历阶段批量生成 World Matrix，再按 Pipeline/Material 排序；
- 静态程序化树直接合并为一份 Mesh，而不是每根枝条单独 Draw。

无论怎样优化，边界都不变：Matrix Stack/Scene Graph 负责 CPU 侧层级变换，Buffer/BindGroup 负责把结果交给 GPU，Render Pipeline 和 Shader 只消费最终数据。

## 五、与 WebGL、旧 OpenGL 和现代引擎的关系

WebGL 2 与 WebGPU 都没有内置 Matrix Stack。旧版桌面 OpenGL 固定管线曾提供 `glPushMatrix/glPopMatrix`，但 WebGL 从一开始就是可编程管线，开发者必须自己在 JavaScript 中维护矩阵；WebGPU 也是如此。不要把“OpenGL 曾有矩阵栈”误认为“WebGL 有矩阵栈”。

| 概念 | WebGL 2 | WebGPU |
| --- | --- | --- |
| 内置矩阵栈 | 没有，通常由 JavaScript 数学库实现 | 没有，同样由 JavaScript/引擎实现 |
| Shader 矩阵 | GLSL `mat4` | WGSL `mat4x4f` |
| 单对象矩阵上传 | `uniformMatrix4fv`，或写入 UBO | `queue.writeBuffer` 写 Uniform/Storage Buffer |
| 资源连接 | Uniform Location，或 UBO Binding Point | BindGroup + Pipeline Layout |
| Draw 前状态 | 绑定 Program、VAO、Uniform/UBO | 在 Render Pass 中设置 Pipeline、Vertex/Index Buffer、BindGroup |
| Draw | `gl.drawElements(...)` | `pass.drawIndexed(...)` |
| 父子层级计算 | CPU 侧，GPU 不理解 Scene Hierarchy | CPU 侧，GPU 同样不理解 Scene Hierarchy |

WebGL 版本的对象绘制可能是：

```js
gl.useProgram(program);
gl.bindVertexArray(cubeVAO);
gl.uniformMatrix4fv(matrixLocation, false, worldViewProjection);
gl.uniform4fv(colorLocation, color);
gl.drawElements(gl.TRIANGLES, 36, gl.UNSIGNED_SHORT, 0);
```

WebGPU 中，Shader 资源接口已经固化进 BindGroup/Pipeline Layout，绘制发生在显式 Render Pass 内：

```js
device.queue.writeBuffer(objectUniformBuffer, 0, uniformValues);
pass.setPipeline(pipeline);
pass.setVertexBuffer(0, cubeVertexBuffer);
pass.setIndexBuffer(cubeIndexBuffer, "uint16");
pass.setBindGroup(0, objectBindGroup);
pass.drawIndexed(36);
```

两者变化的是资源模型和命令组织，不是层级矩阵的数学。相同的 Matrix Stack 类可以同时服务 WebGL 和 WebGPU；只有 `drawObject` 中的上传与 Draw 代码不同。

Matrix Stack 与 Scene Graph 也不完全等价：

```text
Matrix Stack
  适合深度优先、即时遍历；状态只在遍历过程中存在
  常用于递归绘制、程序化生成、调试工具和简单层级

Scene Graph / ECS Transform System
  持久保存 Parent、Local Matrix、World Matrix 和 Dirty 状态
  适合随机访问、局部更新、剔除、动画和大型引擎
```

现代引擎通常沿 Scene Graph 或 ECS 的父子关系计算 World Matrix，而不是把 Matrix Stack 当成完整场景数据库；但深度优先遍历层级时，其算法本质仍然是“进入子节点前保存父状态，退出时恢复父状态”。

打开配套示例后，建议只做三组观察：

1. 在文件柜场景修改柜子和抽屉数量，观察层级结构不变，而 Draw 数按零件数量线性增长。
2. 切到递归树，调整 Depth、Branch Angle、Y Twist 和 Child Scale，观察所有子枝如何继承父坐标系，以及 Draw 数如何随深度指数增长。
3. 查看 Matrix Stack Trace 和最终栈深度；无论场景多复杂，最后都必须回到 `depth = 0`，且 `save = restore`。

本章最后只需记住：

> **矩阵栈是 CPU 侧的层级变换工具：`save()` 固定父坐标系，子节点在其副本上追加 Local Transform，`restore()` 让兄弟节点重新从正确的父坐标系开始。WebGPU 只看到遍历完成后的最终矩阵；应用仍需把矩阵写入 Buffer、绑定 BindGroup，并为每个对象编码 Draw。**

配套示例：[`matrix-stacks.html`](./matrix-stacks.html)
